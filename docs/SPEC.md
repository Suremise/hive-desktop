# Hive — Specification (v0.2)

Hive is a desktop app for AI-assisted ("vibe") coding. It looks and feels like a streamlined VS Code, but its centre of gravity is the **agent session**, not the text editor. It organises code into Workspaces and Projects, runs CLI agent sessions (Claude Code and Codex, up to twelve agents per active project), and manages the skills, MCP servers and shared notes those sessions use.

This document is the source of truth for product decisions. Update it when decisions change.

---

## 1. Goals and non-goals

**Goals**
- Open or create a Workspace; list its Projects in a left-hand pane.
- Run Claude Code and Codex sessions per active Project in embedded terminals, several at once; each agent chooses its provider, so a project can mix them.
- Show per-session stats: tokens, cache use, compactions, estimated re-cache cost on resume.
- Review and edit the agent's memory for a project.
- Manage Hive skills and MCP servers at workspace ("global") scope with project-level opt-outs.
- Per-project model, effort and permission mode, with global defaults.
- Indicate session state (working / waiting / finished) with optional chime and desktop notifications.
- Review changes (git diff) made by the agent.
- Expose an Agent API (HTTP + built-in MCP server) so agents can interact with Hive.
- Minimise and close to the system tray. Ship as a Windows installer.

**Non-goals (for now)**
- A full code editor. Monaco is used for notes, memory, skills and diffs.
- Providers beyond Claude Code and Codex. The provider framework (§10) is built for more; each needs its own adapter.
- Moving a conversation between providers. Work moves through a handover (**Hand Over to…**, §6.2).
- Automatic session restore. Resuming is always a user action.
- Cloud sync, accounts, multi-user. A remote skill repository is a future idea.

## 2. Technology

| Area | Choice |
|---|---|
| Shell | Electron, TypeScript throughout, built with electron-vite |
| UI | React + zustand, VS Code-style layout, `@vscode/codicons` |
| Terminal | `xterm.js` with its WebGL renderer (DOM fallback) + `node-pty` prebuilt (`@lydell/node-pty`, Windows ConPTY) |
| Editor / diff | Monaco (bundled locally, no CDN) |
| File watching | `chokidar` |
| Docs rendering | `marked` |
| Packaging | `electron-builder` (NSIS installer) |
| Tests | Vitest (unit, in CI) and Playwright `_electron` end-to-end suites (`tests/e2e`, local: they need the CLIs) |
| Checks | TypeScript, oxlint (`.oxlintrc.json`; typescript-eslint doesn't support TypeScript 7 yet), GitHub Actions on every push to `main` and on pull requests |

Process model: the **main process** owns the filesystem, ptys, hook server, Agent API and agent adapters. The **renderer** is UI only and talks to main through a typed preload bridge (`contextIsolation: true`, `sandbox: true`, no `nodeIntegration`).

**Windows** (like VS Code): one Hive process, one window per workspace (or the welcome page). Settings, the tray, updates, the Agent API and file locks are shared; each window has its own workspace service. **File → New Window** (`window.new`, Ctrl+K Ctrl+N; VS Code's Ctrl+Shift+N is New Session in Hive). Open Workspace (or Create Workspace) replaces the current window's workspace; if its agents are running, the quit dialog's *Switch workspace?* variant asks first (per **Confirm on quit**, like quitting and closing a window), then they are stopped. **File → Close Workspace** does the same (*Close this workspace?*) and stops every agent of every project in it, keeping the window open (its tooltip says so). Cancel leaves everything running; a workspace already open in another window brings that window forward instead, so one project is never in two windows. Closing a window that isn't the last stops its workspace's agents after the quit dialog's window variant (*Close this window?*, no "when agents finish"); the last window keeps the old behaviour (tray, or quit). **File → Close Window** (`window.close`, Ctrl+Shift+W, just above Exit; also in the palette) is the window's X: it calls `window:close`, which goes through the same close handler. Quitting covers every window; unsaved files are asked about in each window that has them. With several windows open, File → Exit reads **Exit Hive (all windows)** (`Command.liveLabel`, from the window count main sends as `windows-changed` and `window:count`), and the quit dialog's title says it closes all N windows, its text that it stops the sessions in every workspace, and it lists the agents under their workspace's name (`QuitSession.workspace`), grouped by its full path (`workspacePath`, case-insensitive) so two workspaces with the same folder name stay apart: each of those also shows the fewest parent folders that tell them apart (`distinguishingParents`, `shared/folderLabels.ts`), and every heading has the full path on hover; a **Close this window only** row in its body (not the footer, which has no room beside Quit when agents finish; the footer wraps rather than overflow) answers quit choice `'window'`, which closes just the window showing the dialog through the Close Window path (`requestCloseWindow`), asking only about what that dialog didn't cover: from the main dialog nothing more (it listed the agents and dealt with the unsaved files); from the unsaved-files question asked first in another window, "Close this window?" about that window's agents, per Confirm on quit. It doesn't save "Don't ask again". A workspace can't be opened inside, or around, one another window shows (a project must belong to one workspace); an Agent API workspace name that two open workspaces share is refused (409) rather than guessed. Stopping a window's agents also cancels agent starts still being prepared, and turning a provider off lists its agents in every window. The open windows (workspace, bounds) are saved in `config.json` `windows` and reopened at start when *Reopen last workspace* is on; `lastWorkspace` stays the last focused window's for older versions. Events about a project, and its terminals' output, go to the window showing it; app-wide events (settings, updates, plan usage) to every window. **Always on Top**, per window (`main/pin.ts`): the title bar's pin (left of the window buttons, lit while on), **View → Always on Top** (`view.alwaysOnTop`, checked while on), the palette and Ctrl+Alt+O all call `window:setAlwaysOnTop` (`BrowserWindow.setAlwaysOnTop(true)`: above other apps, below system UI; no higher levels). It is remembered by workspace in `config.json` `alwaysOnTop` (lowercased paths), never in `.hive` (a desk preference, not the workspace's): a window takes its workspace's pin when the workspace opens in it, at start too, and is off on the welcome page and for a workspace never pinned.

Robustness and safety rules:

- **Hive's JSON files** (`project.json`, `sessions.json`, `config.json`…) are written to a temporary file and renamed into place, each write with its own temporary file, so a crash or two writes at once never leave a partial file. The files Hive keeps (`config.json`, `workspace.json`, `project.json`, `sessions.json`) also get a `.bak` copy of the last good version with every save; a file that can't be read is set aside as `<file>.corrupt-<time>`, the `.bak` restored and the user told (or, with no good copy, defaults used and the user told), so a damaged file never silently turns into lost settings or session records. Read-modify-write changes to one project's `project.json` or `sessions.json` are serialised, so changes made at the same moment (two agents finishing together) are all kept.
- **Session IDs** from the renderer, the Agent API or the file system are checked (letters, digits, `-`, `_`) before they are used in a file name.
- **Starting an agent** is reserved before anything else happens, so two starts at once (a double click, or the UI and the Agent API) start it only once; the other is refused.
- **The window** only uses the clipboard; every other permission a page can ask for is refused, and a build's CSP allows no network connections. IPC calls are accepted only from Hive's own top-level page (not an embedded preview). Paths from the window are checked against the workspace by their real location too (following links and junctions), for `file:read`/`file:write`, `hive-img:` and shared notes.
- **Files the renderer may open** outside the workspace are limited to what Hive shows from each provider's config folder: Claude Code's user `CLAUDE.md` and auto-memory files and Codex's user `AGENTS.md` (editable), and `SKILL.md` files (read-only), never credentials or settings.
- **The UI** catches errors per view: a failure in one tab or view shows a message there (**Try Again**, **Open Logs**) instead of blanking the window, and running sessions are unaffected.

Primary platform is Windows 11. Code avoids Windows-only assumptions where cheap.

## 3. Concepts

- **Workspace** — a folder that contains Projects. One workspace is open per window. Hive remembers recent workspaces: the 12 last opened (`config.json` `recentWorkspaces`), in File → Open Recent and on the welcome page (#144). Each entry says whether its folder is there (checked whenever the list is shown, and when the welcome page's window comes back to the front; one that isn't is greyed, "not found", and kept, since a drive may come back) and whether another window has it open (choosing it brings that window forward). An entry can be removed (its ✕, or right-click → Remove from Recent), comparing paths without case; **Clear Recently Opened** (File → Open Recent, and the palette) asks, then keeps only the workspaces open in a window. Opening a missing one says it can't be found and offers Remove from Recent. Every change (opened, removed, cleared, a workspace closed) is sent to every window (`recent-changed`), which asks for its own view of the list (`workspace:recent`).
- **Moved workspaces** (#146, `main/workspaceMove.ts`, paths in `shared/movePaths.ts`). Hive records where the workspace and each project were last opened (`lastPath` in workspace.json and project.json; recorded the first time a folder is opened with it). When a workspace opens and the folder differs (paths compared without case, either separator, only at folder boundaries), Hive works out in the background what still points to the old folder; if anything does, a banner says **This workspace was moved from …** (or that projects moved, when only a project folder was renamed or moved in) with **Repair…** (also `workspace.repairMove` in the palette while it's needed); if nothing does, the new folder is simply recorded. Repair… shows the plan (`workspace:movePlan`) and, on **Repair**, does it (`workspace:moveRepair`), refusing while any agent of the workspace (the Assistant included) runs: **worktrees**: each agent worktree is looked for moved along inside its project or the workspace, moved along in the worktrees folder beside the workspace (`<workspace>.worktrees`), then where it was; the first folder with a `.git` file wins; `git worktree repair <paths>` runs in the project, the result is checked (git lists it and its links are right both ways) and only then is `agents[].worktree.path` updated (`mutateProjectConfig`); one not found is listed with **Recreate worktree** (or **Create a new worktree** when its branch is gone, see below; made at its moved-along place, after the repairs above), **Locate…** (a folder picker; the folder must have a `.git` file; the plan is worked out again with it) or **Remove the agent's worktree link** (`worktree` dropped from the agent; nothing deleted); one still at its old place while the project's old folder exists too (a copy) is left to the original; **sessions**: `cwd`s under the old project folder or an old worktree path move to the new ones (`mutateSessions`); **per-path data**: for the project, and for each worktree now at a new place, kept in project.json (`pendingCopies`, written in the same locked change as the agent's new path) until its copy works, so a copy that fails is tried again by the next Repair, after a restart too, without repeating the git or session steps: the provider adapter's `copyPathData` (Claude Code: `~/.claude/projects/<path as name>/`, transcripts and `memory/`) copies to the new path's name for the project and each moved worktree (the Assistant's home too), never moving or deleting, never overwriting: a file already there with the same size and time counts as copied, one that differs is kept and listed; Codex keeps threads by id and has none; **Open Recent**: the old folder replaced by the new; **Working on**: the projects marked at the old folder (`activeProjects`, kept by folder path) marked at the new one too. A plan with files that couldn't be read, or only files already there with other content, still counts (`moveHasWork`): the banner shows it, failures stay pending, conflicts are listed once and never overwritten. The report lists what was done, skipped and failed (logged with `userText()`); Repair is complete only with nothing failed; a project is recorded as repaired (its `lastPath`) only when all its steps worked and nothing is left, the workspace when all are, so the banner stays until then and Repair can run again, repeating nothing done. Nothing at the old location is ever deleted. **Missing worktrees** (`main/agentWorktree.ts`): an agent whose worktree folder is gone, with its branch still in the repository, can have it made again: `git worktree prune`, then `git worktree add <path> <branch>` (no `-b`) at the recorded path (Repair: the moved-along place), or the agent's default worktree location if that can't be used; with the branch gone too, a new worktree on the same branch name from its base (else the project's current branch), as Add Agent makes one. Then the copied ignored files, `needsSetup` so the setup command runs at the next start, and the agent's path updated under the lock; at a new place, the same locked change records the old→new move in `pendingCopies`, so its sessions' `cwd`s and the CLIs' data follow it afterwards (Repair, or `finishPending()` after a Start's recreate) and a failure or exit in between leaves it to retry. Repair keeps a move pending when the sessions.json rewrite fails, too. A project with only such moves left gets the banner's third wording ("A worktree of x was made again at a new folder, and not everything has followed it yet"). Only when the folder is truly missing; refused while the agent runs, while git still lists the folder after the prune (locked), and when the prune would drop another missing worktree's entry (`git worktree prune --dry-run`), which a moved one still needs for `git worktree repair`, naming it (Repair passes the others it is recreating in the same run). Offered by Repair, by Start (New Session, Resume) with a confirm (`agents:missingWorktree`, `agents:recreateWorktree`; with the branch gone: Create a New Worktree or Remove the Worktree Link, `agents:unlinkWorktree`), and named in the error of a start that finds the folder missing. **File → Move Workspace…** was considered and not built: moving needs the old folder deleted, a cross-drive move of a workspace (and its worktrees) while terminals and watchers have it open is fragile, and Explorer does the move better; Repair handles what follows.
- **Project** — any direct child folder of the workspace, excluding dot-folders (so `.hive` is never a project) and folders hidden or removed from Hive (§6.7). Creating a project in Hive creates the folder.
- **Active project** — a project switched on with its toggle. Only active projects get a terminal, watchers, status indicators and notifications. Activating a project **never** starts or resumes a session; it offers "Resume last session" and "New session". Deactivating requires stopping the live session (after confirmation). Active state is personal, so it is stored in app data, not in the workspace.
- **Provider** — the CLI an agent runs: **Claude Code** (Anthropic) or **Codex** (OpenAI). The UI uses product names, and "provider" where a generic word is needed. Providers are enabled in Settings → Providers; a fresh install has none enabled (a banner links to the settings), and an upgrade from 0.1 keeps Claude Code enabled. With none enabled, no agent can start and none can be added.
- **Agent** — one of up to twelve session slots in a project. **All agents are equal** and a new project has **none**: agents are added (Add Agent) and removed (when stopped) freely, and each works in the project folder or in its own **git worktree** (a separate checkout on its own branch). Agents are named ("Agent 1", "Agent 2"…, renamable), have random ids that are never reused, and always store their **provider**, chosen when they are added; defaults never move an existing agent. An agent can override the project's model, effort and permission mode for its provider. Changing an agent's provider clears those overrides and its last session. Each agent has at most one live session. Agents of a disabled provider stay listed, greyed out, and can't start. Upgrading from 0.1 clears every project's agents and layout (their sessions stay and can be resumed by an agent added again).
- **Session** — one conversation of a provider's CLI. Claude Code sessions have a UUID Hive chooses; Codex chooses its own ID, which Hive learns from the first hook (with the first prompt). A session can only be resumed by an agent of the same provider. A project has at most one live session per agent plus any number of past (resumable) and archived sessions.
- **Hive Assistant** — one per workspace, in a panel on the right: the workspace's **overseer**, a provider session like an agent's that looks after every project rather than working in one (§6.5). It never takes one of a project's agent slots.
- **Persona** — who the Assistant is in a conversation: a Markdown file of instructions (a role and a character) in `<Workspace>/.hive/personas`.
- **Task board** — one per workspace: cards (tasks) in four fixed columns, each belonging to a project and optionally given to one of its agents. The user, the Assistant and agents all work on it (§6.6).
- **Global scope** — settings in app data or `<Workspace>/.hive/workspace.json`, applied to every project unless the project overrides them.
- **Project scope** — overrides in `<Project>/.hive/project.json`.

## 4. On-disk layout

### 4.1 Workspace (committed to git if the workspace is a repo)

```
<Workspace>/
  .hive/
    workspace.json        # MCP servers turned on, hidden and removed projects
    shared/               # cross-session notes, handovers, instructions (markdown)
      handovers/
    skills/
      <skill-name>/SKILL.md (+ supporting files)
    mcp/
      <server-name>.json  # one MCP server definition (§7.2)
      <server-name>/      # optional server code
    personas/
      <id>.md             # a Hive Assistant persona (§6.5)
    bundled.json          # which of Hive's bundled skills and personas the workspace was given, and from which version (§7.1)
    tasks/                # the task board (§6.6)
      <number>.json       # one card
      board.json          # the next card number
    assistant/            # the Hive Assistant's home (§6.5); its own .gitignore keeps it out of git
      .hive/              # like a project's: project.json (its one agent), sessions.json, backups, launch-assistant/
    README.md             # explains the folder to humans browsing the repo
```

`<Workspace>/.hive/` is intended to be committed so a team can share skills, MCP definitions and notes. MCP definitions must reference secrets via environment variables (§7.2).

### 4.2 Project (entirely git-excluded)

```
<Workspace>/<Project>/
  .hive/
    project.json          # project overrides
    sessions.json         # session index
    sessions/<id>.jsonl   # backup copy of each session transcript
    archive/<id>.jsonl    # transcripts of archived sessions
    images/<id>/<time>.png  # images pasted or dropped into a session; deleted only by Clean Up… (§4.2.1)
    removed/              # only after Remove from Hive (§6.7): manifest.json, cards.json, handovers/
    project.json.bak, sessions.json.bak   # last good copies (see §2)
    launch-<agent id>/    # Claude Code agents: regenerated on every launch — do not edit
      plugin/.claude-plugin/plugin.json
      plugin/skills/<skill>/...     # copies of enabled Hive skills
      mcp.json
      settings.json                 # hooks Hive injects
      sync.json                     # hash of each item copied
  .agents/skills/hive-<skill>/  # Codex agents: copies of enabled Hive skills (Codex reads skills only here),
                                # each with a .hive-copy marker (only marked folders are replaced or removed);
                                # git-excluded with a /.agents/skills/hive-*/ line in .git/info/exclude
```

Codex takes everything else from `-c` overrides on its command line (§6.4), so it needs no launch folder.

Worktrees Hive creates for agents live **next to the workspace**, in `<Workspace>.worktrees/<Project>/<agent>` (e.g. `D:\Dev\HIVE.worktrees\hive\agent-2`), so the project's own tools (tsc, test runners, search, file watchers) don't scan a second copy of the code, and Hive doesn't take them for projects. Transcripts, backups and images of worktree agents still live in the project's `.hive` folder.

#### 4.2.1 Storage and Clean Up

- **Project Settings → Storage** (also for the Assistant's home, from Settings → Workspace) shows the sizes of `.hive/sessions`, `.hive/archive`, `.hive/images` and each agent's worktree, and their total. The CLIs' own transcripts aren't counted. Main measures in the background (`storage.ts`): a directory at a time, links and junctions not followed, yielding to the event loop every few hundred entries; one measurement per project at a time, and the last result comes back at once until **Refresh**. Image and worktree folders are cached per folder by modified time (a folder that hasn't changed counts its files as before; its subfolders are still checked); backups and the archive are measured afresh.
- **Settings → Workspace → Storage**: the workspace's total and its eight biggest projects, the Assistant included, each opening its Storage page (the Assistant's opens in place).
- **Clean Up…** runs per project, only when asked; nothing is automatic. Options: images of archived sessions last active more than N days ago (on, 90); images of deleted sessions and of `run-<runId>` folders of launches that never got a session (never a running launch's); Hive's backups of archived sessions older than N days, **only where the CLI still has the transcript**; and, apart from that, with a warning, backups of archived sessions the CLI no longer has. Age is the session's last activity.
- A preview lists every file and its size and the total before anything is removed (`storage:cleanupPreview`). Applying it (`storage:cleanup`, with the listed paths) plans again and removes only listed items that still qualify (a session resumed or unarchived meanwhile is skipped and reported); a session's backups go only if every copy of it was listed. Each session is reserved while its files go (a resume of it is refused until then: "Clean Up is removing files of this session") and checked with both of its backups locked, again right before they go (still archived, not running or starting, its copies exactly the ones listed); an image folder is checked the same way just before it goes. Anything else is skipped. A backup goes only after what its session used has been read and saved on its record (`keptUsage`; a session whose only copy it was then moves it to `deletedUsage` as it is deleted), so its totals survive a failure partway; if that can't be read or saved, the backup stays and is reported. Everything goes to the Recycle Bin. Running sessions and sessions that aren't archived are never touched, nor `~/.claude` or `~/.codex`.
- Usage totals don't change: removing the backup of a session the CLI still has keeps its usage on the record (`keptUsage`), which counts if the CLI later drops its transcript; removing the last copy deletes the session as Delete does (§6.2: `deleted`, `deletedUsage`).

### 4.3 App data (`%APPDATA%/Hive/`)

- `config.json` — settings, recent workspaces, active projects per workspace, window state. Version 2 keeps each provider's settings in `settings.providers[<id>]` and plan usage per provider and limit. Before the first version-2 save, the 0.1 file is copied to `config.v1-backup.json`, and the 0.1 `settings.claude` block is still written, so 0.1 can read the file again. Version 3 (0.3) moves the Assistant's model and effort, when still at 0.2's saved defaults, to the agents' (§6.5).
- `agent-api.json` — Agent API token.
- `usage-cache.json` — each transcript's usage, so a restart doesn't read unchanged transcripts again (§9). Derived and disposable.
- **A window's page that crashes or hangs** (`main/rendererWatch.ts`, per window): agents run in main, so they are never affected. On `render-process-gone` (except a clean exit) Hive logs the reason and reloads the page; terminals reattach to their running sessions as after View → Reload, the window keeps its workspace, and a toast says "Hive's window stopped and was reloaded. Your agents kept running." with how many files' unsaved edits were lost (the window's last report; hot exit would keep them). A second crash within a minute doesn't reload again: a native dialog says "Hive's window stopped working. Your agents are still running…" with **Reload**, **Open Logs** (then asks again) and **Quit Hive**. On `unresponsive`, after 4 seconds a native dialog offers **Wait** / **Reload**; `responsive` closes it. Reload ends the hung page (`forcefullyCrashRenderer`) and loads it again, without the crash note.
- `logs/hive.log` — **Help → Copy Diagnostics…** puts its last 50 lines in a bug report, with Hive's version and update channel (stable/beta), installed or development build, Windows version, display scaling and locale; each coding agent (on/off, version and path, signed in, update available, anything its adapter adds (`diagnostics()`: Codex's Windows sandbox, default/non-admin/not set up), and its readiness issues); counts (windows, active and total projects, agents, running agents, agents in worktrees, whether the Assistant runs); and the settings that change behaviour (file locks, merge style, quitting, tray, backups, cache TTL, Agent API, Assistant control, notifications, theme), never free text. A dialog shows exactly what will be copied; **Copy** copies it. It is built and redacted in main (`diagnostics.ts`, `shared/redact.ts`). Hive marks the user's own text as it logs it (`userText()` in `logger.ts`: card titles, Assistant activity, session, project, agent and branch names, paths; of the arguments an agent is started with, everything but flags and the values of known flags such as `--model` and `--session-id`, whether separate or written as `--flag=value` (`argsForLog()`)), and the report replaces each marked span with `<text>` or `<path>`. Its start line says so (`your text marked`); lines from a run whose start line doesn't (an older version), or from before the first start line in view, keep only their time, level and scope. For older lines and anything unmarked: the home folder becomes `~`, workspace and worktree folders `<workspace>`, including the workspaces in the recent list; workspace, project, agent and branch names, and the project folders of recent workspaces, are taken out of the log lines (not the summary, which has none, so a project called "Hive" doesn't take Hive's name with it; each line's time, level and `[scope]` stay); any other absolute path becomes `<path>` unless it is under AppData, a dot folder in the home folder, Program Files or Windows; tokens, keys, `Authorization` and `token=`-style values, well-known key formats, JWTs, long hex or base64 runs and email addresses are masked.

## 5. Settings resolution

**Skills** — no switches: every Hive skill in `<Workspace>/.hive/skills` goes to every session of its audience (§7.1). The 0.1 lists (`workspace.json` `skills.enabled`, `project.json` `skills.disabled`) are dropped when the file is next saved.

**MCP**

```
effective(project) = globalEnabled − projectDisabled
```

- MCP servers must be deployed to `<Workspace>/.hive/` before any project can use them. Projects can only turn off what is globally on.
- An item disabled globally is off everywhere. The project's own "disabled" entry is kept, so its choice returns if the item is re-enabled globally.
- Changes (to skills and MCP) apply to **new sessions only**, including restarts. A live session keeps what it launched with; the UI shows "settings changed — restart to apply".
- If a project defines MCP servers in its own `.mcp.json` that are not in the workspace, Hive notifies the user that they stay disabled until copied to the workspace, and offers "Copy to workspace". (`--strict-mcp-config` enforces this.)

**Provider** — stored on each agent when it is added. The project's default provider, else the global one (Settings → Providers), is what **Add Agent** uses: its quick add adds an agent with that provider and its default settings in the project folder; **Add Agent…** (▾) chooses the provider, where it works and its settings.

**Model, effort, permission mode, chime** — per provider: the global value is on the provider's settings page (Settings → Claude Code, Settings → Codex), the project's in Project Settings under the provider's name, and the project value overrides unless it is `inherit`. An agent's own model, effort or permission mode (set when adding it, or in its settings) overrides the project's; unset, it follows the project. A mode that isn't allowed (e.g. Bypass after the option was turned off) falls back to the project's, then the global one.

**Agents** — *File locks* (global Settings → Agents & Worktrees, default **Block**; project override), *Copy into new worktrees* (global list, default `.env*`; project override), *Setup command* (project only, empty by default), *Default merge style* (global, default **Merge**; a Squash saved before 0.3 is moved to Merge once, config version 4).

**Number settings** (Settings and Project Settings) save on Enter or blur, once. A blank box saves nothing in Settings (the saved value comes back) and means Inherit in Project Settings; it is never read as 0. Text that isn't a number, or a number out of range, saves nothing and shows the range under the box. Where 0 turns the feature off (*Suggest compacting above*, *Warn when a transcript is over*, *Archive Done cards after*, *Pause after you type*), 0 is chosen with a **Never** / **No pause** checkbox beside the box (typing 0 does the same); unticking it restores the last other value, else the default (Settings) or Inherit (Project Settings). A failed save shows the saved value again.

**Permission mode**
- Global default: **Auto** (Claude Code's safety classifier approves low-risk actions and asks about risky ones; Manual asked too often to be a good default for supervising several agents).
- Project dropdown: Inherit, Manual, Accept edits, Plan, Auto, Don't ask — always available.
- **Bypass permissions** is only offered when Settings → Claude Code → "Enable the Bypass permissions option" is ticked (ticking asks for confirmation). Projects using it show a warning indicator.
- If the option is later unticked, projects set to bypass revert to Inherit and the user is told which ones changed.
- **In a running session** the mode can be switched without a restart. Hive knows the session's real mode from its launch flag, from Claude Code's footer as the terminal redraws (`⏵⏵ auto mode on`, `⏸ plan mode on`, …; read from the rendered screen, a headless terminal of one screen per session with no scrollback, since Claude Code may redraw only the characters that changed, as it does with `NO_COLOR` set, which Hive leaves as it is) and from `permission_mode` in hooks, so a Shift+Tab typed in the terminal shows in Hive at once. Choosing a mode (the mode badge in the project header, a pane header or the status bar, or **Switch Permission Mode…**, Ctrl+Alt+M) sends Shift+Tab until the footer shows it. Claude Code's cycle is Manual → Accept edits → Plan → Auto; Don't ask leaves it once left, and Bypass is only in it for a session launched in Bypass (it shows Claude Code's own warning the first time), so those two restart the session in the mode and resume the same conversation, after confirmation. Not while the agent is asking something (Shift+Tab could change the answer). A live switch affects that session only.
- **Codex presets**: Read only (`-s read-only -a on-request`), Ask for approval (`-s workspace-write -a on-request`), **Approve for me** (`--approve-for-me`: Codex's reviewer approves low-risk actions; the default, like Auto) and **Full access** (`-s danger-full-access -a never`). Full access is treated like Bypass: only offered when Settings → Codex → "Enable the Full access option" is ticked (with confirmation), badged as a warning, and reverted to Inherit when unticked. A running Codex session switches preset live: Hive clears the input (Ctrl+U), types `/permissions`, and picks the preset from Codex's menu; Plan mode is a separate toggle (Shift+Tab, shown as "· Plan" on the badge).
- **Changing the setting** (global, project or agent) never restarts anything and no longer marks sessions "restart to apply". New sessions use it; for running agents whose setting changed, a notification offers **Switch Now**, which switches them live (or reports which couldn't be).

## 6. Session lifecycle

§6.1 and §6.3 describe Claude Code; §6.4 is how Codex differs. Every launch has a **run ID**, so hooks reach the right agent before the session ID is known (hook URL `<hook server>?run=<runId>`).

### 6.1 Launch

On "New session" or "Resume":

1. Resolve effective skills and MCP servers (§5).
2. Rebuild `<Project>/.hive/launch/` from scratch (copy skills, write `mcp.json`, write `settings.json`, record hashes).
3. For a resume, if Claude Code's transcript is missing (e.g. cleaned up) but Hive holds a backup, restore it first.
4. Spawn in a pty, cwd = the agent's folder (the project folder, or its worktree):

```
claude --session-id <uuid> | --resume <uuid>
       --name "<session name>"
       --plugin-dir .hive/launch/plugin
       --mcp-config .hive/launch/mcp.json --strict-mcp-config
       --settings .hive/launch/settings.json
       [--model <m>] [--effort <e>] [--permission-mode <p>] [extra args]
```

Environment added to the pty: `HIVE_HOOK_TOKEN`, `HIVE_API_URL`, `HIVE_API_TOKEN` and `HIVE_API_TOKEN_FILE` (the agent's own Agent API token for this launch, never the workspace token), `HIVE_PROJECT`, `HIVE_PROJECT_PATH`, `HIVE_WORKSPACE`, `HIVE_AGENT` (the agent's name), `HIVE_PROVIDER`, `HIVE_RUN_ID` and, when known at launch, `HIVE_SESSION_ID`. Every provider's own session variables inherited from Hive's environment (e.g. `CLAUDECODE`, `CODEX_THREAD_ID`) are removed.

Each Claude Code agent launches from its own folder (`launch-<agent id>/`), because a launch replaces the folder while the project's other agents may still read theirs (skills are read when used).

Rebuilding `launch/` on every launch means a restarted agent has exactly the workspace's current skills (for its audience, §7.1) and MCP servers.

### 6.2 Operations

| Action | Behaviour |
|---|---|
| New session | New UUID. A live session is stopped first (with confirmation). In a project without agents, New Session (and Resume) first adds one with the quick add, then starts it. |
| Resume | `--resume <uuid>`, in an agent that works in the folder the session ran in (sessions record their agent, folder and branch). Shows the re-cache estimate (§9) first. A paused session can move between agents that share its folder (never across worktrees); the record then names the new agent, and any other agent whose *last session* it was forgets it. |

| Failed start | The CLI exits while the session is still **starting** (before its first hook, or for Codex before its prompt shows), and Hive didn't stop it: a missing or broken CLI, an argument or config it refuses. Not covered: errors the CLI shows without exiting (Claude Code's sign-in screen, an unknown model or expired sign-in on the first prompt). |
| Compact | Header button next to Stop, Session menu, command palette. Enabled only while the agent is idle (Ready/Finished) and the conversation has content. | Archive | Copies the current transcript to `.hive/archive/` (or moves the backup there if Claude Code no longer has it), removes the active backup and marks the session archived. Can be unarchived. Only Hive's sessions (adopt an external one first), and only when it isn't in use (as Delete). |
| In use (Archive, Delete) | Archive and Delete first **reserve** the session (as Clean Up does): until they finish, it can't start or resume and its transcript isn't read (the viewer, a search, an export wait). Then Hive checks nothing has it in use (`sessions.inUse`), and refuses (one at a time) or skips it (Archive All / Delete All, saying why): it is **running or starting** in any agent, project or window; Hive is **reading its transcript** (a read under way: `transcriptReads.ts`, counted around every parse, export and image); its transcript is **open in a Sessions view**, in any window (views register with `transcript:viewing`, and can't register on a reserved session; the tab asking closes its own view first and waits for main to know, opens it again afterwards if the session is still there (skipped, or archived one at a time), and says when it stays closed); **another program holds the CLI's transcript open** (found by opening it to read and closing it at once: the CLI's file is never changed or moved); or its CLI is **still writing** it: changed in the last 5 s and not since Hive saw that CLI exit (Hive notes each exit of its own sessions, so Archive and Start New archives one just stopped; a session started outside Hive, adopted or not, or a Codex guardian review still going, waits). Nothing is ever killed. **All or nothing**: an archive builds the new archive aside (the backup brought up to date from the CLI's transcript), then moves each copy, and any failure (a copy another program holds, the record not saved) moves every copy back; the record changes only after the files. A delete first moves each of Hive's copies aside and back, keeps a spare of each (a hard link, else a copy), then sends them to the Recycle Bin and removes the record; if one fails to go or the record can't be saved, the copies already gone are put back from their spares (a copy stays in the Recycle Bin). |
| Delete | Any session that isn't running (Hive's, archived or external), from the Sessions tab or the Assistant's conversations, after asking. Hive's backup and archive copies go to the Recycle Bin, the record leaves `sessions.json` and its id is kept in `deleted` so it never shows again (not even as external); **what it used is kept** (`deletedUsage`: its usage with the day buckets, no transcript), so the Overview's and the Assistant's totals still count it (`session:keptUsage`; lists, search and resume never see it); an agent whose last session it was forgets it. The CLI's own transcript is left alone: Hive doesn't change the CLIs' files, so the CLI's own resume list still has it. If it runs again (resumed inside the CLI), it is Hive's again (and its kept usage goes, counted from its transcript instead). Images pasted into it stay in `.hive/images`. |
| Adopt | Sessions for the project started outside Hive are listed and can be adopted into `sessions.json`. A sub-session stays one when adopted (its `sub` is kept): never resumed. |
| Add agent | Up to twelve per project, a page holding as many as the layout has panes (§6.2). **Add Agent** is a split button: the main part adds one at once (the default provider with its default settings, in the project folder, named "Agent n"); **▾ Add Agent…** opens the dialog: provider, name, where it works (project folder, new worktree with branch `hive/<name>` from a chosen base branch, or an existing unused worktree of the project), optional model/effort/permission overrides (and Use 200K context for Claude Code), and "Start a session now". A page whose layout wasn't chosen by hand shows all its agents (1 one at a time, 2 two columns, 3 three columns, 4 the 2×2 grid, 5–6 the 3×2 grid), and the new agent is focused (the seventh opens page 2). Adding the seventh shows a note that each agent is its own CLI process (roughly 150–400 MB of memory) and they share the plan's limits. |
| Merge (worktree agent) | Commits the worktree's uncommitted changes (with the message given), checks for conflicts with `git merge-tree` without touching anything, then merges into the branch checked out in the project folder: **squash** (one commit, default) or **merge** (`--no-ff`). Refused while the project folder has staged changes, and while the agent is in the middle of a task (starting, working, waiting for the user's answer, or waiting on background tasks it started: its uncommitted files would be committed half-done; `mergeBlocked()`): Merge… in the agent header and ⋯ menu, the Agents settings and the Changes tab are disabled then, with the reason in the tooltip (the unmerged count still shows), and an open Merge dialog says so and disables Merge. Optionally removes the worktree, branch and agent afterwards (off by default; agent must be stopped). | Remove agent | Any agent, once stopped. A worktree agent asks whether to keep the worktree and branch (reusable via "existing worktree") or delete both. Later agents move up (page 2 empties first); automatic layouts follow, chosen ones stay. |
| Reorder agents | A project's agents have one order, saved in `project.json` (the `agents` array; added ones go last): the strip, its pages and the panes follow it, every window agrees, and the Agent API lists agents in it. Held over another page's **button** for 600 ms, that page shows, so it can be dropped on one of its panes; dropped **on a page button** it moves to that page's last place. Escape or a drop elsewhere cancels (also when the dragged pane has left the screen with the page). ### 6.3 Status via HTTP hooks

`launch/settings.json` registers Claude Code **HTTP hooks** pointing at Hive's local hook server (`127.0.0.1`, random port per app run). The token is sent as `Authorization: Bearer $HIVE_HOOK_TOKEN` using `allowedEnvVars`. `SessionStart` only supports command hooks, so it is a command that pipes the hook JSON to the same server with Windows' `curl.exe`; its token is written into the git-excluded `launch/settings.json` (it changes every time Hive starts).

| Hook | Hive status / action |
|---|---|
| `SessionStart` | **ready** |
| `PreToolUse` (Edit, Write, MultiEdit, NotebookEdit) | File lock check (below); answered before the tool runs |
| `UserPromptSubmit`, `PostToolUse` | **working** |
| `Notification` (permission prompt) | **waiting** — notification if window hidden/unfocused |
| `Stop` | **finished** — chime if enabled; notification if hidden/unfocused. **background** instead when the agent has background tasks running that will start it again (below) |
| `PreCompact` | **working** ("Compacting the conversation…" when it was idle, e.g. `/compact` typed in the CLI); toast for automatic compaction |
| `PostCompact` | back to **ready** after a compaction that started idle (Hive's Compact or `/compact`); one mid-turn keeps working, and so does a turn begun since (a prompt after the compaction began ends it). Without the hook, Hive's Compact ends when the transcript shows a new compaction, the CLI says it refused or failed it, or if it hasn't begun 20 seconds after Hive submitted its `/compact` (typing a long focus doesn't count) or runs past 10 minutes, with the same rule. While Hive types the command, the agent is reserved: a second Compact or a prompt is refused, and if the agent stops meanwhile the rest isn't typed |
| `SessionEnd` | **stopped** |

Hooks have a short timeout; if Hive is unreachable, Claude Code continues normally. The same question twice, or a second `Stop`, notifies once. The rules are in `main/hookStatus.ts` (pure, unit-tested for both providers); `SessionManager.handleHookNow` carries out what they say.

**Another conversation in the same CLI** (Claude Code `/clear` or `/resume`, Codex `/new`): its first prompt's hook carries a different session id for the same launch. Hive then backs up the old conversation, records the new one (as the agent's session to resume) and follows it — usage, backups, the context meter. Only a prompt switches: helpers a CLI runs for itself (subagents) can report other ids.

Hooks are normalised by each adapter into one set of events (start, prompt, tool start/end, needs input, stop, interrupt, compact start/end, end), so the status rules above are shared by every provider.

**Background tasks.** An agent can leave work running when its turn ends: a test run, a server, a watch. Each adapter reads them from the transcript as it grows (`backgroundTasks()`), and Hive counts the ones started since the agent launched (`backgroundTasks` in its live state; shown as "· 2 background tasks running").
- **Claude Code**: a background Bash call's result has `backgroundTaskId` (also a command moved to the background after running too long), a Monitor's has `taskId` and an expiry. A task ends with a `<task-notification>` naming it (any status but a Monitor's events) or a `TaskStop`. Claude Code is told when a task ends and starts a new turn by itself, so the provider has the `backgroundWakes` capability: a turn that ends with tasks open leaves the agent **background** ("Waiting on 2 background tasks"), not finished. When the last one ends, the agent is **working** again (the notification's turn), then finished at its Stop. No "finished" notification or chime until then.
- **Codex**: a command still running when `exec_command` returns gives a `session_id` instead of an `exit_code`; Codex records its end as an `item_completed` CommandExecution with that `process_id`. In code mode (0.160) the command runs inside an `exec` script that prints what the model chooses, and Codex records no start (only each command's end, and no record of which `exec_command` calls a script ran), so a start needs evidence: an id the output shows (the result's whole-number `session_id`, or a script that reads `session_id`, printed only numbers, such as `text(r.session_id)`, and had none of its commands end within it), ended by its `process_id`; or else a script that runs its one `exec_command` once (a real call, not one in a string or a comment, as a statement of its own at the top level, with no loop, condition, function or `try` in the script) and completed with none of its commands ended, since Codex writes the end of every command that ends within a script before the script's output (counted under a stand-in id, ended by the CommandExecution of the same command text). Anything less clear (a loop that printed no ids, a condition, a failed or aborted script, an end that could be the script's own) counts nothing: a command missed rather than one counted that isn't running (`providers/codex/background.ts`, which keeps what it needs between reads of the rollout). Codex isn't told when one ends (checked with 0.159), so its agents stay **finished** and the count is only shown.
- **Time limit.** Hive can't tell a test run from something that never ends (a dev server), so a task stops counting after **Settings → Agents & Worktrees → Count background tasks for up to** (60 minutes; 10–480), and a Monitor at its own expiry if sooner. Hive logs it, and an agent left background then shows finished ("Stopped counting its background tasks after 60 minutes"), with the notification.
- A **background** agent counts as busy: `hive_wait_for_agents` waits through it (unless `ignoreBackground`), `hive_prompt_agent`, Hand Over, Compact and Merge refuse it, *Confirm before quitting* asks (its tasks would stop), and *Quit when agents finish* waits for it. The sidebar dot is a slow, faint pulse.
- **Watching** is the status of an agent whose turn has ended with a card watch running (§6.6, *Waiting on cards*): its `ready`/`finished` shows as `watching` (`SessionManager.emitState`), and when the watch ends it is `finished` again. It counts as busy like `background`: *Confirm before quitting* asks, for quitting and for closing a window or workspace or switching it (the dialog says what it waits for: stopping pauses its card loop until it is resumed, the watch kept); the Assistant's stop asks the user first; Merge is refused until it has finished or its watch is cancelled (merging commits unfinished work); `hive_prompt_agent` and Start Task refuse it. *Quit when agents finish* waits for it only while a card it watches is in Doing or Review with another agent (`watchKeepsQuitWaiting`, the same rule for the dialog's offer and the wait); once the watches have seen a watched card move or change hands (`onWatchedCardsMoved`), a pending quit checks again, so it goes ahead when no such card is left even though no wake comes. But `hive_wait_for_agents` doesn't wait for it (it reports `watching`, with the watch's label as `statusMessage`), and Compact is allowed from the header, the agent menu and the dialog (the watch is kept; a wake waits until the compaction has ended). No "finished" notification or chime while it watches. The sidebar dot is a hollow ring in the info colour.
- Hive looks at a running transcript every 5 seconds and reads it again when its size or modified time changes: Windows can report an old modified time for a file Codex keeps appending to.

**File locks.** Hooks are matched to sessions by `session_id`, so every agent reports its own status. For file edits, `PreToolUse` asks Hive first: the first agent to edit a file claims it (by its real path, so a junction or link to the same file is the same file); while the claim holds, another agent's edit of the same file gets, depending on the lock mode, `permissionDecision: "deny"` with a reason naming the holder (**Block**, default), `"ask"` (**Ask me**: Claude Code's permission prompt), or `additionalContext` warning it (**Warn**); **Off** skips the check. For CLIs whose hooks can't hand an edit to their own approval prompt (Codex rejects `"ask"` and then runs the tool; descriptor capability `lockAsk`), **Ask me** denies the edit, telling the agent to stop and wait, and Hive shows a notification with **Allow**; Allow lets that agent edit that file until its claims are released and tells it to go ahead: at once if the agent is idle, else when its turn ends (Allow is often clicked while the blocked agent is still replying; the edit is then allowed again for the turn the go-ahead starts, and several files allowed in one turn get one go-ahead). The go-ahead is typed like the Assistant's tasks: only while the user isn't writing in that terminal (**Pause after you type**), checked again until Enter, so it is never added to or sends their input; put off, it goes when the pause ends, or at the end of the turn the user's own prompt started (the file stays allowed for it). An edit of the file that goes ahead meanwhile (in the same turn, or after the holder finished) needs no go-ahead, and an interrupt drops it, even one that comes while the go-ahead is being typed (it stops before Enter). A claim is released when the holder's turn ends (`Stop`), when its session ends, or 15 minutes after its last edit. Claims, approvals and questions are numbered as they happen, and a turn's end releases only those from before it arrived, so a late `Stop` never clears what the next turn has claimed (an agent's hooks are handled in order, but `PreToolUse` is answered at once). Denials return at once, so agents can't deadlock; if Hive doesn't answer, the edit goes ahead. Only these tools are covered: shell commands, formatters and Claude Code's own config writes (`~/.claude.json`) are not — concurrency there is the developer's responsibility. Agents in different worktrees never collide (different paths). Claimed files are shown on the agent's tab and pane header (lock icon with a count; the list on hover).

**Status line** (Claude Code): `launch/settings.json` also sets Claude Code's `statusLine` to the same `curl.exe` command, posting to `/hook?statusline`. The hook server answers 204 with no body, so Claude Code shows no status line in the terminal. From the JSON Hive takes the session's effort (`effort.level`), model name and cost (`cost.total_cost_usd`) into the live state, and the plan limits (`rate_limits.five_hour` / `seven_day`: `used_percentage`, `resets_at`) into `config.json` (`planUsage`, account-wide, last report wins). Claude Code reports with every status-line update, many times a minute while agents work, so the latest report is kept in memory and written only when a shown value changes (a whole percentage or a reset time), at most once a minute, and on quit. Warnings at 80% and 95% are shown once per limit per reset period (`planWarnings`; a reset time within 30 minutes of the stored one counts as the same period). Hive never calls Anthropic's usage API or reads credentials itself.

### 6.4 Codex

Tested with Codex 0.159 and 0.160. Hive never edits Codex's own `config.toml`; everything is passed as `-c key=value` overrides (TOML values):

```
codex [resume <id>] --no-daemon          # options must follow "resume <id>"
      -c hooks.<Event>=[…] -c hooks.state={…trusted hashes…}
      -c tui.terminal_title=["activity","project-name"]   # keeps "Action Required" in the title (Status)
      [-m <model>] [-c model_reasoning_effort=<e>] <preset flags (§5)>
      -c developer_instructions="<the hive MCP server's instructions>"
      -c mcp_servers.<name>={…}          # each enabled workspace server
      -c mcp_servers.<other>.enabled=false   # the user's and the project's own servers
      [extra args]
```

- **Hooks**: SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, PermissionRequest, Stop, Interrupt, PreCompact, PostCompact, SessionEnd, each a command hook. Codex runs hook commands through PowerShell on Windows, so the command is `curl.exe -s -m 5 -X POST -H "Authorization: Bearer <token>" -H "Content-Type: application/json" --data-binary "@-" "<url>"`. Codex only runs hooks it trusts: Hive passes the trust records in one `hooks.state` table, keyed by `<session-flags config path>:<event label>:0:0` with `sha256:` of the hook's canonical JSON. For each new Codex version Hive checks its hashes against Codex's own (the app server's `hooks/list`) once, and uses Codex's if they differ.
- **Ready**: Codex fires SessionStart only with the first prompt, so Hive marks the agent ready when Codex's prompt appears in the terminal, and records the session (its ID and rollout path) at the first hook.
- **Status**: who is asked comes from Codex's terminal title, not its hooks. Codex sends PermissionRequest before anyone answers it, in every preset with the same payload: in **Approve for me** its auto-reviewer (a Guardian sub-session that sends no hooks) answers it, allowing it (PostToolUse follows) or denying it (nothing follows). It titles its terminal `[ ! ] Action Required | <project>` (blinking with `[ . ]`) exactly while a person must act: an approval prompt, or a question. So from Codex 0.160.0 (`titleAttention()`; Hive pins the title's items so a user's `[tui].terminal_title` can't hide it) the title saying so makes the agent **waiting** (a permission request or `request_user_input`, which stops Codex), or gives it a **pending question** (`request_user_input_async`, which returns at once: Codex works on, and the answer comes later as a prompt). The hooks only say what is asked: PermissionRequest is the status message ("Codex asks to run …"), or, in **Approve for me**, an action under automatic review (`LiveSessionState.review`) while the reviewer considers it: the status stays **Working…** with a small shield beside it in the agent's and the Assistant's headers (`ReviewMark`), whose tooltip names the reviewer and what is asked; the request is never the status, a label elsewhere or a notification, and the Agent API reports it as `reviewing`. It goes when the next tool starts or ends, a prompt comes, the turn ends or is interrupted, the session ends, or a person is asked after all (no review is shown over a wait). The command in a request is its first line, cut at 120 characters with an ellipsis. The title is one for everything asked, so Hive keeps what is open: each ask from its hook until it is resolved (its own tool call ends, the turn ends or is interrupted, or the title goes back). The title coming on is about what is open (the latest prompt is waited on, the latest question shows beside it), else about something the hooks didn't say (waiting, with no message). A permission request in Approve for me is never open: the reviewer decides it (one it can't decide fails; one it handed to you would still be told, unnamed), so a finished review can't be taken for a later title. While the title is already on, an ask is judged by what it is: a reviewed request stays the reviewer's (the agent works on, a question stays pending, no alert); anything else is put to you at once, as a new need. A wait ends when the tool call it is about ends (its PostToolUse names the same tool and command as the request); another call ending beside it doesn't, and with two prompts up the wait moves on to the other. The title going back ends the wait and the question. Older versions go by the hooks: PermissionRequest is **waiting** except in Approve for me (the preset's `reviewed`), a question waits or is pending, and the next prompt answers a pending one. Interrupt (Esc) means **ready** and releases the agent's file locks. File locks use PreToolUse with `apply_patch` (paths from the patch; in code mode too).
- **Live preset changes** go through Codex's `/permissions` menu: Hive clears the input, types `/permissions` and the preset's number (the arrow keys wrap around, so counting presses picked the wrong preset). The badge shows "Switching to X…" until Codex confirms, from its "Permission selection requested: X" line or the rollout's `thread_settings_applied`, within 12 seconds; otherwise it reverts and says so.
- **Models** come from Codex itself (`codex debug models`: the listed models, in Codex's order, with each one's reasoning levels and default) when the CLI is found, so new models appear without a Hive update (§10, models and capabilities); `model_reasoning_effort` in its config.toml is the default effort for every model when set.
- **Live details** (model, effort, context, plan limits, preset, Plan mode) come from the tail of the rollout file (`token_count` events and `thread_settings_applied`), read as it grows.
- **Sandbox**: on Windows Codex needs its sandbox set up once (`windows.sandbox` in its config); without it every command asks for approval. Agent Setup runs Codex read-only in a scratch folder and brings up Codex's own setup prompt (default or non-admin sandbox): with no sandbox yet, by choosing "Ask for approval" in `/permissions`; with the non-admin sandbox on (`unelevated`), by typing `/setup-default-sandbox`, which only exists then. The keys go in once Codex shows its prompt and its window title has stopped showing a spinner for a second (`CommandSpec.busyTitle`): Codex is briefly busy just after its prompt appears, and queues what is typed then ("tab to queue message") instead of acting on it. Agent Setup explains the two choices in Hive's terms (`ReadinessIssue.detail`), and with the non-admin sandbox shows an info item with **Upgrade** (the same task). Codex stays open after its setup, so the task ends itself once Codex's config names a new sandbox (`CommandSpec.done`); Agent Setup then shows that the task succeeded (the issue it was started for is gone) instead of the terminal.
- **Resume**: `codex resume <id>` restores a rollout only at its original path, so Hive keeps that path in `sessions.json` and restores a backup there when Codex's copy is gone.
- `.git` is read-only in Codex's workspace-write sandbox (committing asks for approval).

### 6.5 Hive Assistant

- **What it is.** Each open workspace has one Assistant, its overseer, shown in a panel on the right of the window (Ctrl+Alt+I, the command palette, or clicking the strip it folds into when hidden: a narrow bar down the right edge with a chevron, "Hive Assistant" written downwards and a status dot while it runs; each workspace remembers whether its panel is open and how wide it is, 430 px by default). It answers questions about any project, reports what the agents are doing, plans and reviews, and (as far as **Control** allows, below) runs the agents for the user: adds them, changes their settings, starts, stops and briefs them, and creates projects. It never edits project files itself.
- **How it runs.** It is a session like an agent's (terminal, hooks, status, usage, transcript backups, quit/close/switch handling, notifications), hosted by `<Workspace>/.hive/assistant`, a home Hive never lists as a project, with one agent (`assistant`). It **works in the workspace folder**, so it can read every project, and gets the hive MCP server scoped to the workspace (no project of its own) and the workspace's skills meant for it (`metadata.audience` `assistant` or `all`, §7.1: `coordinate-agents`, `split-work`, `handover`, `pick-up`, `workspace-note` as Hive ships them), not the project agents' skills or the workspace's other MCP servers. Reading a skill grants nothing: its tools and Control decide what it can do. Quit and close dialogs call it "Assistant".
- **What it is told.** Hive's session contract for the Assistant (`hiveInstructions(…, 'assistant')`, the hive MCP server's instructions: use the hive tools for Hive's things, and which skills cover its workflows), then at launch its role (`assistantInstructions`): the workspace and its projects at launch, what Control lets it do and the boundaries it keeps whatever else it reads (`controlRules`), that nothing wakes it but the user and its own tool calls, that clarity beats character, and its persona: Claude Code through `--append-system-prompt-file` (a file in its launch folder), Codex through `developer_instructions`. How to run agents and cards well (briefs, starting cards, waiting, handing over, stalled cards) is the `coordinate-agents` skill's, not its prompt's. The rules on what it may do come from Hive and replace anything a persona says; personas describe a character and a focus, and Hive's four carry no procedure or permissions. Its hive tools (below) are pre-approved where the provider allows it (Claude Code: `--allowedTools`); writing shared notes still asks.
- **Control** (Settings → Assistant → Control, for every workspace; default **Control agents and create projects**): **Look and advise** (it reads and suggests; you act), **Control agents** (also adds agents, changes their settings, starts and stops them, gives idle ones tasks, turns projects on), **Control agents and create projects**. It never removes agents, discards worktrees or deletes projects. Changing it marks a running Assistant for restart.
- **How it acts.** Through the Agent API with **its own token**: a new one each time it starts, in a per-workspace file under the profile (`assistant-api/`) that its hive MCP server reads, so its launch settings don't change. When it stops, its token stops working and any question it was asking is answered no. Its session doesn't get the Agent API's token, and its hive tools ignore one inherited from the CLI. Asking to stop a busy agent stops only the run it asked about, and only if Control still allows it when the user answers. The API applies Control (not Settings → Agent API) to its calls and confines them to its workspace; with the Agent API off, the server still runs for it alone, and its hive MCP server is always there. Its tools: `hive_list_providers`, `hive_agent_activity` (status, the task it was last given, its latest reply, this turn's tool calls, locked files, when the user last typed there), `hive_wait_for_agents`, and as Control allows `hive_activate_project`, `hive_add_agent`, `hive_update_agent`, `hive_start_agent`, `hive_stop_agent`, `hive_prompt_agent`, `hive_hand_over` (Hand Over to…: the first agent writes a handover, Hive waits until it exists, then starts the second on it; refused at once when project agents lack Hive's tools or the user just typed in either), `hive_create_project`. Project agents don't get these (AGENT_API.md lists them).
- **Its rules** (enforced by Hive, and in its instructions): a first task goes on the CLI's command line (`claude "<task>"`, `codex "<task>"`; through cmd.exe, below, it becomes one plain line); a task is typed into an agent only when it is idle (ready or finished), never while it works, starts or waits for the user, and never while the user may still be writing there: within **Pause after you type** (Settings → Assistant, default 15 seconds; **No pause** turns it off) of their last keystroke in its terminal, unless that keystroke was Enter and **Enter ends the pause** is on (the default). Hive records the user's keystrokes per terminal, ignoring the terminal's own replies (focus, cursor and device reports, colour queries such as Codex's at start, ended by BEL or ST); stopping a working, waiting or starting agent asks the user on a card at the top of the panel (or a notification with the panel hidden), and the call waits up to 10 minutes for the answer; a worktree only if the user asked or agreed; at most **30 changes per message** from the user (a new turn starts with each prompt it receives), then the API answers 429 and it must ask to go on. Every change and refusal is listed in the panel (**Done by the Assistant**: the last three, or all) and in hive.log.
- **The user's view never moves.** Its actions don't change the selected project, the page or the focus. Pages that weren't given a layout by hand follow their agents as usual. A new agent on the project on screen marks its page's button with a dot until that page is shown; on another project, that project opens on the new agent's page next time.
- **Trusting a folder.** When a CLI asks whether to trust a folder before it starts (Claude Code and Codex: "trust this folder"), the agent shows as **waiting** ("Asks whether to trust this folder") and notifies, instead of looking stuck in Starting, for any agent; the Assistant tells the user.
- **Settings.** **Settings → Assistant** holds the defaults: the provider (default: the default provider), the default persona, and per provider the model, effort, permission mode, 200K context (Claude Code) and extra arguments. The model and effort default to the agents' (empty: Settings → each provider's defaults; until 0.3 they were lighter, Sonnet with low effort, which made the Assistant careless, so 0.2's saved defaults move to the agents') and the mode defaults to the provider's `assistantMode`, the one where the CLI approves safe actions itself and only asks about risky ones, as agents default to: **Auto** for Claude Code, **Approve for me** for Codex (never a plan mode, which blocks MCP tools). That it only looks and advises comes from its instructions, not its mode. A provider can warn about a mode it may not run with a model (`modeCaveat` in its descriptor): Settings → Assistant, Assistant Settings and the agent dialogs say so under the mode when the model that would run doesn't take it. For Claude Code's Auto, whether a model takes it depends on the CLI's version and the account (#129), and is what Claude Code reports (`supportsAutoMode` in its initialize reply: absent for Haiku 4.5 with 2.1.289, §10); such a session runs in Manual instead (2.1.286 and 2.1.289), which the warning says. Without the reply's word, the shipped guess ("may not offer Auto with Haiku"). The real-CLI suite (`claude-real`) launches the Assistant with Haiku in Auto and checks that the mode Claude Code itself shows (`LiveSessionState.modeObserved`: from its footer, a hook or its transcript, never the mode asked for at launch, which `permissionMode` starts as) is the one it said, that Hive shows that mode, and that it warns exactly when Auto isn't offered; `automode` runs the same checks with the fake Claude Code acting out each answer (Haiku takes Auto, doesn't, or the CLI doesn't say) (#234). It is a warning, not a rule: Hive shows the mode the CLI really runs in. **Assistant Settings** in the panel (⋯, or clicking the footer's model) overrides any of them for the workspace; they are stored on the home's agent. Changing its provider or persona while it runs asks, stops the conversation and starts a new one.
- **Personas.** Files in `.hive/personas` with a header (`name`, `description`, `icon`) and the instructions. Hive ships four (Overseer, the default; Planner; Reviewer; Orchestrator), each with an unexpected character on top of a serious job. They are kept up to date in each workspace like the bundled skills (§7.1): added when the workspace has never had them, an untouched copy of an older version updated, an edited one kept (with **Update available** when it came from an older version, and **Revert to Default**), a deleted one left deleted (with **Restore**). The **Personas** section of the Assistant view (below) lists, creates, edits (with the unsaved-edits protection of the other editors), deletes and restores them, and makes one the workspace's (**Use in This Workspace**). A conversation keeps the persona it started with; its name records it ("Assistant · Planner · <date>").
- **Assistant view** (the robot in the activity bar, "Hive Assistant"): the sidebar has a **summary** of what the Assistant has used, with the Overview's periods (conversations, prompts, tokens, API-equivalent cost; not counted in any project's Overview), then the sections **Personas**, **Conversations** and **Images** (#243), each folding. **All Conversations** shows its conversations in the main area with the same tree as a project's Sessions tab (§ Sessions tab: by provider, with the conversations' sub-sessions; search, counts, Archive All / Delete All with the in-use checks, can't-resume markers, reading in full, export, rename, resume), in its own words and with Hive's conversations only; **Show** on the running one opens the panel. **All Images** shows the images pasted or dropped into its conversations (kept like agents' in its home's `.hive/images/<conversation>`) with the project Images tab's grid, viewer and actions, grouped by conversation (name, count, last time; newest first; archived conversations last, marked): a group's name opens that conversation in the tree, and its bin moves all its images to the Recycle Bin after asking (`images:trashGroup`: all or none, none if another program has one open; deleting images follows the Images tab's rules below). Main reads them through the session-host path (`assertSessionHost`), and watches the home for new ones. A persona opens in the editor. The panel's ⋯ has **All Conversations…** and **Manage Personas…**, which open this view; the commands **Show Assistant Conversations**, **Show Assistant Personas** and **Show Assistant Images** do too.
- **The panel.** Header: status, provider, the persona menu, Compact and Stop while it runs, and when it doesn't, **Resume** (|▷, its last conversation, when there is one it can resume with its provider) and New conversation, or Start when there is nothing to resume, as icon buttons (below 380 px of panel width they fold into ⋯, except Resume), ⋯ (New Conversation while it runs or Resume when it doesn't, Resume a Conversation…, All Conversations…, Assistant Settings…, Manage Personas…, Move Panel to the Left/Right, Hide), and hide. **Panel side** (`settings.assistant.panelSide`, `right` by default; one app-wide setting, not per workspace): Settings → Assistant → Panel side, the command `assistant.moveSide` (View menu and palette, its label saying where it goes: "Move Assistant Panel to the Left"), and ⋯. On the left the panel (or its folded strip, arrow pointing right) sits between the sidebar and the main area, with its border and resizer on its right edge (`PaneResizer edge="right"`, the same `assistant` width); the Progress panel stays on the right. The tip card and toasts only move aside for the panel when it is on the right (`.assistant-panel:not(.on-left)` in `CornerPlacement`). At the top, as tall as it needs up to a third (drag the line under it to set its share; double-click to go back): the workspace at a glance, with the agents that need you first (the attention inbox, §14), then each active project (or one with an agent running) and its agents, listed under its name with a fixed indent whatever the panel's width (#240; click one to go to it); the other inactive projects fold into one "N inactive projects" row that expands them, remembered per workspace. It scrolls under its title, which stays put with the counts. Then its terminal, and a footer like an agent pane's (model and effort, mode, context, cost). When it isn't running: **Start Assistant**, Resume, and its past conversations. Hiding the panel doesn't stop it; the strip's dot shows what it's doing.

### 6.6 Task board

- **What it is.** One board per workspace, in `<Workspace>/.hive/tasks` (one JSON file per card, so the workspace can commit it; §4.4). Cards have a number (#12, unique in the workspace and never reused, including past cards whose files were lost or damaged), a title, a Markdown description, a project (or none: about the workspace), an agent of that project (optional; its name is kept for when the agent is removed), labels (up to 12), a **blocked** reason, the cards it **depends on** and **related** cards, comments and a history of who changed what (**You**, **Assistant**, or the agent, "Agent 2 (hive)"). Card files edited by hand are read safely (anything missing or of the wrong type gets a default).
- **Columns, fixed** (#170): **On Hold**, **Todo**, **Doing**, **Review**, **Passed**, **Done** (`hold`, `todo`, `doing`, `review`, `passed`, `done`), so the Assistant, agents and the API all speak the same six; not configurable. **On Hold** is parked work nobody picks up: only the user and the Assistant put cards there (a project agent's move there, or a card it creates there, is refused, 403; it may take one out when the user asks it to work on it). **Passed** is work whose review passed, waiting to be merged: the reviewer moves the card there with its verdict. **Done means merged**: the builder moves its cards there after merging its branch (the merge-ready skill), or the user does. **Blocked** (a reason, or cards it depends on) stays a property of a card in any column: a blocked card doesn't move to On Hold by itself. Cards in On Hold and Passed are never stalled (only Doing cards are). Nothing moves on upgrade: cards already in Done stay there. Agent states aren't columns (they change by the second): a Doing card shows its agent's live status (working, waiting on background tasks, needs your input, finished, not running), and a Doing card whose agent has finished gets a green edge. **Blocked** is a red flag on a card in any column. **Archive** hides a card from the board but keeps it searchable (the **Archived** view), and **Bring Back** returns it to the end of its column. **Archived (n)** in the board's toolbar shows the archived cards as a data table (#249; `DataTable`, below): number, title, project (the whole board only), labels, agent (the last it had), **From** (the column it was archived from), **Archived** (its latest "Archived…" in its history, `archivedAt()`) and **Created**, the dates in the shared date format; newest archived first; filters: text for number, title and agent, a choice of project, label (a card with several shows for each) and From; pages with rows per page (`table-rows:archived-cards`). The board's search narrows the rows too (both apply). A row (click or Enter) opens the card, read-only as an archived card is. **Unarchive** on a row, or **Unarchive Selected** for the rows ticked (the header's box ticks every row the filters let through, on every page), brings each back to the end of the column it was archived from, as Bring Back does; nothing else changes an archived card. Cards in Done are **archived automatically** after **Settings → Board → Archive Done cards after** days (14, or **Never**; the same for every workspace), counted from when the card last went into Done or was brought back, not its last change; Hive checks when a workspace opens, every hour and when the setting changes, and the card's history says so (`archivedFor: 'done'`).
- **Column colours.** Each column has a colour on its top edge and heading, and a subtle tint of it on its cards (mixed with the theme's background, so it reads in light and dark): On Hold grey, Todo slate blue, Doing blue, Review purple, Passed teal, Done green. A card's tint follows its column (a colour saved before a column existed falls back to its default). The state edges (blocked red, stalled amber, finished green) stay solid over the tint, with their text. **Settings → Board → Colour columns** turns it off; **Column colours** has a picker per column (stored as `#rrggbb` in `board.colors`; anything else falls back to the default) with a reset for a changed one.
- **An agent's card.** An agent with cards given to it in **Doing** shows the first (in board order) as a chip with the board icon, in the Doing column's colour (plain with Colour columns off): only `#4` (and `+1` with more) in its agent strip tab, whose tooltip lists them; `#4 title`, shortened to fit, in its pane header (`#4` only when the pane is under 340 px) and on its row in the Overviews' running lists. Clicking it opens the card's dialog in place. The project's sidebar tooltip and the compact rail tile's list each agent with its card ("Agent 2: working · #5 Prompt snippets"); the row itself is unchanged. Todo, Review and Done cards aren't shown; it follows the board live. The Assistant has no cards. **Each session records its cards**: whenever an agent has cards in Doing (the board changed, or its session was recorded), main adds those not already there to the running session's record in `sessions.json` (`cards: [{ number, title }]`, in order, the title as it was then; only for a session Hive has recorded). The Sessions tab shows **Worked on #5 Prompt snippets, #7 …** under the transcript's toolbar; each card links to its dialog, and a deleted card shows its number and recorded title without a link.
- **Reviews.** An agent asked to review a card (check its work, often another agent's) marks it rather than taking it: `review: "start"` on `hive_update_task` / `PATCH /v1/tasks/{n}` (a card in Review, on its own, by an agent of the card's project through its own token; the user, the Assistant and scripts don't) sets `TaskCard.review` (the reviewer's id and name, and since when). The card stays in Review with the agent that did the work. `passed` or `failed`, with the verdict as the comment, ends it ("Review passed" / "Review failed" in the history); with `passed`, a `column: "passed"` in the same change moves it to Passed, which the review-agent-work and card-loop skills tell reviewers to do (#170; `"done"` still works, for a user's explicit say-so). A `failed` verdict with any other column than `review` is refused (400): a failed card stays in Review for its fixes. One reviewer at a time: another agent's start is refused, naming the reviewer; the same agent's start renews its mark (saved, without another history line); only the reviewer gives the verdict, and only while its review is going: once the card has moved on (out of Review for fixes, or the review ended with the reviewer's session), an old verdict is refused, so it can't settle newer work; a new review starts again. **Returning a failed card for review** (#214): a failed verdict leaves the card in Review, so a move to Review by the card's own agent (its hive tools, or the Agent API with its own token) or the user (the board's **Move to → Review (next round)**), on a card in Review whose latest verdict failed with nothing since that starts another round (a move, a review started, another agent, an earlier return), records "Returned for review, round N" (N: one more than the reviews failed since it last passed one). That is a move into Review for waits (`movedIntoSince`), so it wakes a reviewer waiting for the card's return, whose line says so (`#159 (Claudette's card) was returned for review (round 2)`), and it starts a new round (the failed verdict is no longer named). Any other move to the column a card is already in (by another agent, the Assistant, a script; a card not failed, or already returned) is no change. The review also stops (with a line in the history) when the card leaves Review or its project, when the reviewer's session ends (`session-exit`) and when the reviewer is removed (`endReviews`). The board shows "Reviewing: <name> · <how long>" on the card (eye icon; click shows the reviewer), in amber with the reason when the reviewer has gone or isn't running (`reviewStalled`); the reviewer's chip (strip tab, pane header, the Overviews' running list) shows the card with an eye in the Review column's colour when it has none in Doing, and tooltips say "reviewing #n". Its session records the card as reviewed (`cards[].review`), shown as **Reviewed #n** beside **Worked on** in the Sessions tab. Agents' session contract, the tool's description and the bundled review-agent-work skill (which also covers finding the exact state reviewed, findings with repro and impact, and reviewing again after fixes) say that reviewing isn't working on a card: only fixes they're asked to make move it to Doing. Cards and records without these fields read as before.
- **Waiting on cards** (#128). An agent that has to wait for another agent's work on a card (a builder for its review, a reviewer for the fixes) waits without spending tokens: `hive_wait_for_tasks` / `POST /v1/tasks/wait`, on up to 20 of the caller's cards (a project agent: its project's; others are unknown to it, 404). What counts as a change: a column move, a new comment, a review verdict, a new agent (`changes`, default all). `column` alone waits until a card is in that column (at once if it already is), and nothing else counts: a comment on a card still in Doing doesn't end a wait for it to reach Review. `column` with `changes` naming `column` waits until one *moves into* it, so a card still there waits until it leaves and comes back (the card's history is checked, so a quick out and back between checks still counts) or, in Review, is **returned for review**, or for another change listed (the builder's "a verdict, or into Passed"); `column` with `changes` that don't name it is refused. A watch keeps the agent's view of the board: a project agent's own project's cards (worked out from the agent, never from what is saved), the Assistant's whole board. A card moved to another project, archived or deleted counts as **gone** ("#12 is gone from your board (archived, deleted or moved to another project)") and nothing about its new state is told; a line that fired is checked again just before it is typed.
  - **`wake: true`** (an agent or the Assistant; not scripts) starts a **card watch** and answers at once: the agent ends its turn, and Hive types one line into its session when a watched card changes: `[Hive] #12 is in Review; latest comment by Codex (hive): "first line…". Your card watch has ended: carry on (…)`. **Changes landing together are told together** (#224): a watch fired by a change waits 1.5 s (`SETTLE_MS`) before its line is typed, and the line is made just before typing from every watched card's changes since the watch began (`wakeLines`): one card as below; several, each with where it is and its verdict, `[Hive] #217 is in Review: Codex (hive) passed it (latest comment …); #119 is in Review: Codex (hive) failed it (…). …`, comments cut first; when even that is too long, every card is still named, in a few words without names or comments (`#217 in Review, passed; #119 in Review, failed`, a gone card as `#12 gone`) or by number alone, and the line says details were left out and to read each card (#226). **No gap between watches:** a watch keeps, per card, where its view ended (`seen`: the last history entry and comment it counted), and counts comments, verdicts and moves into a column by the entries after it, never by time, so an entry sharing a millisecond with one already seen, even one alike in author and words, still counts, and the one seen is never counted again. Every history entry and comment gets an id when written (`id`, unique on the card; the Agent API's card views and latest comment leave it out); entries from before ids are found by time, a hash of who and what, and their place. History and comments only grow at the end and are capped at the start, so when the entry seen is no longer kept, everything kept came after it. Hive remembers, per agent and card, what its wakes told (in memory, the latest 100 cards an agent): the card's mark and `seen` as the line was made from it, or for a limit line the watch's own starting point. The agent's next watch starts each such card from there (`carriedOver`), moved on only past what the agent did itself since (by its board name), kind by kind, unless someone else made that kind of change too; column, agent and archived compare with the told state. So a verdict, comment, move, reassignment or archiving by others between a wake and the next watch fires it at once; the agent's own work in between doesn't. So it can't be misread (#143): when the change is a review verdict, the line names the reviewer (`#12 is in Review: Codex (hive) failed it; …`); on another agent's card (a dependency, or the builder's card a reviewer waits for) it says whose (`#12 (Claude's card) is in Review`), and in Passed that Passed isn't merged (`#12 (Claude's card) is in Passed: Codex (hive) passed it (Passed isn't merged); …`; #170: before it, Done said so). In Done, which means merged, it names the verdict that passed it and nothing more. The watcher's own card and a card without an agent get no owner. A verdict is named only for the current round: once the card has gone back to On Hold, Todo, Doing or Review, a new review has started, or it has gone to another agent, an earlier one isn't (a card moved to Passed or Done by hand names none). Names in the line are cut to 40 characters and the comment's first line gives way, so the card, its state and what to do always fit the line's 1000 bytes. A condition already met answers with the change instead of watching (and ends the agent's earlier watch). One watch per agent; a new one replaces it. The line is typed only when the agent is idle and the user isn't typing in its terminal (the same guard as the Assistant's prompts); otherwise Hive tries again on the agent's next status change and every 5 seconds. The watch stays while its line is typed (the agent still shows watching and takes no other work) and ends once it is in; cancelled or replaced meanwhile, the typing stops before Enter, and a cancelled watch never comes back. Typing in its terminal doesn't cancel the watch. A workspace's watches change one at a time, so a board change made while a watch is being set up is checked once it is in place (and the board is checked again right after every new watch).
  - **Wait limit.** `limitMinutes` (1–1440, default 120): with no change by then, Hive wakes the agent with `[Hive] No change on #12 in 2 h: your card watch has ended. Tell the user (hive_notify) and ask what to do.`
  - **Kept.** Watches are kept in `<Workspace>/.hive/watches.json` (with each card's state when the watch began, so a change while Hive or the agent was closed still counts: they are checked as soon as they are loaded), and a stopped agent with a watch is woken when it is resumed. They belong to their workspace: its folder is taken when they load, and once it closes or its window opens another workspace they are dropped from memory and nothing more is read or written for them (a registration under way then fails). Saves are a temp file renamed into place, the rename checked against the workspace's lifetime before every try. One that lands after the workspace closed fails, and is undone only while the file is still exactly that save: it is moved aside (renamed, never deleted), and the file as it was is put back only where nothing has taken its place (otherwise kept beside it as `watches.json.before-close-<time>-<id>`, or in its staging file if even that rename is refused); anything written since is left as it is. A copy is removed only once another is confirmed, so whatever fails, the earlier watches are left in some file. Each saved watch is checked in full when read; one that isn't valid (or is another workspace's agent's, or over the limit) is kept aside in the file as it was, under `invalid`, and never acted on, and one bad entry doesn't stop the others. At most 500 watches and a 1 MB file, for what Hive writes as for what it reads, with room for each watch to grow to its longest (fired, with its line cut to 1,000 bytes, and being typed; the cards as last seen aren't saved), so a watch Hive took can always fire, be typed and end. A new watch that wouldn't fit first moves the entries kept aside to a file of their own (`watches.json.kept-aside-<time>`, created new); if it still wouldn't fit it is refused (409; replacing an agent's watch is always allowed). A file read back too big for that moves its entries kept aside, then its last watches, to such a file, so nothing is lost. Only a missing file means no watches: one that can't be read is an error. A file too big or not JSON is renamed (`watches.json.too-big-<time>`, `.damaged-<time>`) before anything is saved; if it can't be renamed, that is an error and the file is left as it is. A watch or a cancel that can't be saved is reported as failed, and nothing changes. **At most once**: before Hive types a wake it saves that it is typing it (nothing is typed if that can't be saved); a watch read back marked so counts as delivered and is dropped, so a wake whose end couldn't be saved (or that Hive stopped in the middle of typing) is never typed again. A save that fails in the background is tried again by the 5-second tick.
  - **While watching** the agent shows **watching** (§6.3) and its pane header says what for ("Waiting for #12 → Review", eye icon; short of room only the label shortens, with the whole in its tooltip) with **Cancel**, also **Cancel Card Watch** in the agent's menu; the agent can cancel its own watch (`cancel: true`). It takes no other work meanwhile: `hive_prompt_agent` is 409 and Start… can't choose it. *Quit when agents finish* waits for it while a card it watches is in Doing or Review with another agent (the work it waits for is going on), and not otherwise. Every status reply says what it waits for: `statusMessage` is the watch's label, and agents have `watching { cards, column, changes, label, limitAt }` in project status, the project list, activity and `/v1/agents/wait` (the short rows: `watching`, the label).
  - **Without `wake`**, the call waits in place (event-driven) up to `timeoutSeconds` (default 300, at most 840, under the CLIs' tool timeouts) and replies with each change (the card, its column, who changed it last, its latest comment's author and first line) or no change, with a `since` token to pass to the next wait so nothing between them is missed. It reads the cards as the caller sees them (a card that leaves its view is gone), listens for board changes before its first check (so none falls between), checks again after a change that came during a check, and ends (409) if its workspace closes. At most two such waits per caller at once (429).
  - **The `card-loop` skill** (agents) runs a builder and a reviewer through a list of cards in turn with these watches: the builder sends a card to Review and watches for a verdict or a move into Passed; the reviewer watches for a card arriving in Review and, after failing it, for its return, and moves a card that passes to Passed with its verdict (#170; once the builder has merged its work, it moves its Passed cards to Done); the builder moves a failed card to Doing while it fixes it, then back to Review (a move to Review without leaving it returns it too, #214). Each starts its watch *before* the step that lets the other act, so a fast reply isn't missed. It counts rounds, a round being one build and its review (round 1 is the first build and review), and asks the user when the last round's review fails (5 rounds by default), and tells the user when a wait limit passes. A finding that comes back is marked recurring in the failed verdict and is another round, not a reason to stop early; one the builder disputes is a design question and stops the loop to ask (#163).
- **Who may do what.** The user does everything from Hive. Agents (through their hive tools or the Agent API) and the Assistant create cards, change them, give them to agents, comment, block them and move them between the columns, Done included; putting a card On Hold is the user's and the Assistant's (a project agent is refused, 403). **A project agent works on its own project's cards only**: known by its own Agent API token (never by what a request says), it lists, reads, comments on, moves, creates and orders only its project's cards; another project's card, or one with no project, is to it as if it didn't exist (404, the same as a missing number), a card it creates is its project's and can't move to another, a linked or blocking card from another project shows only as its number (listed in `elsewhere`) and stays when it edits the list, and its top, bottom and reorders work among its project's cards in the column without moving other projects' cards. Since a card started on an agent is that agent's prompt, it also can't read another project's agents' activity or session list, or type into them (403), and its event stream (`/v1/events`) has only its own project's session events; their status stays open to it. The Assistant, the user's board and scripts with the workspace token see the whole board. An agent runs as the user and could read the workspace token from disk, so this keeps agents in their lane rather than containing a hostile one. **An agent that moves a card into Doing takes it**: through its hive tools, moving a card into Doing from another column without naming an agent gives the card to it (if it is an agent of the card's project), also when another agent had it (out of Doing, nobody was working on it; the history says "Given to …"), and so is a card it creates in Doing; naming an agent (or none, with empty) wins, a card already in Doing keeps its agent, and the Assistant, the user and other Agent API callers give it to nobody. **Review is the default for finished work**: the agents' session contract and the work-on-card skill (which a card's prompt points to) tell agents to move a card to Review when its work is done, also one that was in Passed or Done before (more work on a finished card is Done → Doing → Review); a reviewer moves a card that passes to Passed; Done means merged, so an agent moves a card there once its work is merged, or when the user asks; and On Hold is the user's, so agents don't move cards in or out of it unasked. Those are conventions, not permission checks (Hive doesn't read prompts to decide), apart from parking a card On Hold. **Another agent's card in Doing is its work in progress**: a project agent can't move a card that is in Doing with a different agent to Review, Passed or Done (`409`, saying newer work is in progress, the card unchanged), checked under the card's lock against the card as it is before the rest of the change, so giving it to itself in the same change doesn't get round it. This covers a reviewer whose review ended because the card came back for more work: its verdict is refused, and so is a plain move. Its own agent may, and so may the user, the Assistant and scripts with the workspace token; a card in Doing with no agent, and other changes to the card (comments, labels, moving it back to Todo), aren't restricted. Every move is in the card's history with who made it ("Claudette (hive): Moved to Done"), and any move is undone the same way, from the board or the tools, with no approval step. What stays the user's: creating a card straight in Done, putting Done in order, archiving, deleting and bringing archived cards back. Archived cards change only once the user brings them back. **Changing a card's project** (the user, the Assistant, scripts; never a project agent) always takes it from its agent, recorded in its history ("Moved to beta", "Taken from Agent 1 of alpha") so it can be put back; an agent named in the same change is refused (give it to one of the new project's agents afterwards; the card dialog does that as a second change). Every change to a card, including each card of a reorder, is checked against the card as it is when its change is made (under the card's lock): a card moved to another project while a project agent's change waited is unknown to it then, and is left as it is. **The latest comment**: `GET /v1/tasks/{n}/comments/latest` (`hive_read_task` with `latestComment`) gives only the newest comment, so an agent asked to check it doesn't read the whole card. **Stalled cards**: a Doing card that nobody is working on (no agent, its agent removed, or its agent not running; an agent that finished its turn is waiting for the user, not stalled) gets an amber edge and "Stalled: <why>", the board's sidebar lists them under **Stalled**, and the Agent API's card has `stalled` (the reason). The Assistant's `coordinate-agents` skill tells it to report stalled cards when it looks at the board and suggest who could take each; its rules say it reassigns or restarts one only when the user agrees. **Removing an agent** (Remove Agent…, Discard) with open cards (not done or archived) asks: **Move them back** (nobody has them; Doing ones go to Todo) or **Leave them** (they show the agent as removed, Doing ones as stalled); Cancel keeps the agent. Removing an agent after a merge with clean-up leaves its cards as they are. **Archiving and deleting** (to the Recycle Bin; other cards' references to it are dropped) are the user's. A reference (blocked by, link) to a card that is gone, left by a card linked to one at the moment it was deleted, is left out whenever cards are read and leaves the file when that card is next saved; numbers are never reused, so it can't come to mean another card. Nothing moves by itself: an agent finishing doesn't move its card; it moves to Review when someone moves it, which the card's prompt asks the agent to do.
- **Order is priority.** A column's order (top first) is its priority; `hive_list_tasks` and `GET /v1/tasks` return cards in board order. The user drags cards within a column. While a card is dragged, holding it near the top or bottom of a column's cards (or over its heading) scrolls that column, and near the board's sides scrolls the board, faster nearer the edge (`edgeScroll.ts`, in pixels a second, every frame so it goes on with the pointer still); the drop marker is worked out again from what scrolling brings under the pointer. It stops on drop, drag end or cancel, and when the pointer leaves the board. Agents and the Assistant put cards in order too, on any project's cards: `hive_update_task` / `PATCH /v1/tasks/{n}` take `position` (`top` or `bottom`) or `before` (a card that has to be in the column the card ends up in; anything else is refused with 400, as is giving both), with or without a column change; `hive_reorder_tasks` / `POST /v1/tasks/reorder` `{ column, cards }` puts the listed cards at the top of the column in that order in one call (the rest keep their order below them), and refuses the whole list (changing nothing) if a card isn't already in that column or is listed twice: it never moves cards between columns. **The order of Done is the user's**: placing a card in Done or putting Done in order is refused (403) for agents and the Assistant, before the Assistant would ask about a move to Done. A placement by an agent or the Assistant that moves the card adds a line to its history ("Moved to the top of Todo", "Moved before #12 in Todo", "Moved to Review, before #12", "Placed 3rd in Todo" for a list; a card left where it was gets none); the user's drags are saved without one. For the Assistant (Control agents) each call is one change in *Done by the Assistant* ("Put #4, #2 at the top of Todo") and counts once towards its limit per message. The agents' session contract and the work-on-card skill say a column's order is its priority, and to put the cards in order on the board when asked to prioritise rather than only list an order.
- **Lean tool replies.** The hive tools answer in as few characters as do the job, since agents pay for every reply on each later turn: `hive_list_tasks` gives a line per card (number, title, project, agent and what it is doing, labels, blocked, depends on, stalled, reviewer, comment count; at most 200 lines a reply, saying how many more and the `offset` that carries on), `hive_read_task` the card without its history (`history: true` for it; `comments: n` for only its newest n comments, with `commentsOmitted`), and `hive_create_task`, `hive_update_task` and `hive_reorder_tasks` confirm what changed and where the card is now ("#12 Fix the redirect: Moved to Review; Commented. Now in Review (1st of 4), web."). `details: true` lists whole cards. Other tools follow the same rule: projects a line each, shared notes as a list of paths and read as text, agents and projects confirmed in a line. The Agent API keeps its full replies unless asked for the short ones (AGENT_API.md).
- **Move to Doing asks.** When the user moves a card into Doing from another column (dragging it, the card menu's **Move to → Doing**, or the card dialog's **Column** set to Doing and Save), the **Move to Doing** dialog asks: **Nobody yet** (column doing, agent cleared: also takes it from an agent it had), **Assign an agent** (a list of every agent of the card's project with its status, busy ones included; only the assignment changes, nothing is sent or started) or **Assign and start** (Start's choices, below: busy agents (working, starting, waiting for input, waiting on background tasks) can't be chosen, stopped ones can; Start checks again when confirmed, and an agent that gets busy while the dialog is open can no longer be chosen). The default is the card's agent, assigned (Nobody yet when it has none). **Cancel** changes nothing: a dropped card stays where it was, and the card dialog stays open with its edits unsaved. Confirming saves the card dialog's other edits first, then sets column and agent (the drop position is kept). Reordering within Doing, a new card, a card with no project in the workspace (it moves as it is), **Save and Start…**, agents' and the Assistant's tool calls don't show the dialog. The Assistant's `hive_update_task` description and its `coordinate-agents` skill say to ask the user which of the three they mean when asked only to move a card to Doing, and not when they've said ("have Claude start this" starts it; "assign it to Claude without starting" assigns only). Agents moving a card they were given into Doing take it as before.
- **Start** gives a card to an agent of its project with the card as its prompt, and moves it to Doing. A card is started once at a time (a second Start is refused while the first runs). The card is taken (given to the agent, moved to Doing) before the agent is started, checked again under its lock (still in that project, not archived, and in the column and with the agent the Start read: a card moved or reassigned since the Start began is refused and left as decided), so the prompt is the card as it then is; the agent is checked again just before the prompt goes in and while it is typed (before clearing the input, before each piece and before Enter: busy, or for the Assistant the user just typed there, and the rest isn't typed, what Hive typed is cleared unless the user typed since, and the card goes back), and an agent is given one card at a time (a Start of another card for it is refused while one is being given, and for 5 seconds after a prompt is typed into it, until its status says it's working); if the agent can't be started, an agent added for it is removed again and the card goes back where it was, unless it was changed meanwhile (moved to Done or Review, another project or agent), which stays. The user chooses each time: an **existing agent** (stopped: a new conversation on the card; idle: the card as its next message; busy ones can't be chosen), **a new agent** in the project folder, or **a new agent in its own worktree** (git projects; merged back as usual). **A card in Review or Done can be started again** for more work (the menu's and card dialog's Start… are on for it): it goes to Doing, the prompt says "It was in Review/Done and is back in Doing for more work", and the agent moves it to Review when done. The Assistant's `hive_start_task` takes a `note` (what to do now, up to 4000 characters), put in the prompt before the card; its instructions say to use it rather than `hive_prompt_agent` for more work on a card (such as review feedback), so the card is in Doing under its lock before the agent gets it. The prompt is the card's own words: its title, the note, its description and the cards it depends on, and for a card back from Review or Done its latest comment (the feedback it came back with, up to 4,000 characters). With Hive's tools it adds "Use the work-on-card skill." and how many comments the card has to read with `hive_read_task`: how to carry a card through (Doing first, progress worth a comment, blocked, Review with a summary, Done only when the user asks) is that skill's, and the boundaries are also in the agents' session contract (§7.3), so a session without the skill keeps them. Only the Assistant (Control agents and up) starts cards through the API (`hive_start_task`); project agents can't start other agents. An agent started from the board has no terminal on screen until it is shown, like one the Assistant adds; the notification has **Show**.
- **The card dialog keeps edits**: **Start…** on a card with unsaved changes reads **Save and Start…**, saves first and opens the start dialog only once the save succeeded (a failure shows in the dialog and starts nothing), so the agent gets the card as shown. Closing a card with unsaved field changes or a comment draft (Escape, ×, outside, Cancel) asks **Keep Editing / Discard**; an unchanged card closes at once. **Save** also posts a comment being written.
- **Dialogs move** (#87 for the card dialog, every dialog since #133). Each dialog is dragged by its header (`Modal`, movable unless `movable={false}`; pointer capture; its buttons and fields aren't handles) within the window: its header stays wholly in it, below the title bar (where the native window buttons would cover its ×), and is moved back in when the window shrinks or is restored. Escape while dragging puts it back; releasing or a cancelled pointer leaves it where it is, open. It opens centred each time (no remembered place), can be moved while busy, and its fields, menus and pickers work as before wherever it is. A question over a dialog moves on its own, and Escape goes to the top one only (it takes the key for itself, so the dialog under it neither closes nor asks again). Only the two **image viewers** (Images tab, Sessions tab) stay put: they are sized to their image and have their own controls.
- **Where it shows.** The **Task Board** in the activity bar (Ctrl+Shift+J): the sidebar filters by project (All projects, each project, Workspace) with open-card counts and lists the cards waiting for review; the main area has search (#12, words, labels), **Archived**, **New Card** and the six columns. **Folding** (#170): each column collapses to a narrow strip (the arrow in its header; the strip shows its name, rotated, and its card count, and clicking it, or Enter on it, expands it); the expanded columns share the board's width equally (flex, the change animated briefly unless the system asks for reduced motion), and the board scrolls sideways only when their least widths (160 px each, 34 px a strip) don't fit. A card dropped on a strip goes to the top of that column. Each card folds to one line with its own arrow: its number, its title cut short, its agent's status dot and its blocked or stalled marker; folded, it still opens on a click and drags. A column's **⋯** (also right-click on its header) has **Collapse All Cards** and **Expand All Cards** for the cards it shows. Which columns are collapsed and which cards folded is a view preference kept per workspace in Hive's settings (`ui.boardFold`, by the workspace's path in lower case; never in the cards' files), shared by the Task Board and the projects' Tasks tabs and restored after a reload or restart. A window sends each fold as a change (`ui:changeBoardFold`, `applyBoardFold()`), which main applies to what is saved now for that window's workspace only, keeping the newest 50 workspaces and 5,000 folded cards each; so two windows never write over each other's folds with what they read earlier, and a window reads them again when it opens a workspace. A card keeps its fold when it moves column; a new card starts expanded; the folds of cards no longer on the board are dropped when it is saved. The Assistant's and agents' tools are unaffected. Cards drag between and within columns; click opens a card, right-click has Open, Start…, Move to, Archive and Delete. The activity bar's badge counts cards in Review. Each project has a **Tasks** tab with its own cards. **New Card…** (Ctrl+Alt+T) adds one for the selected project. The card dialog edits every field (description with Write/Preview), adds comments (Ctrl+Enter), shows the history, and has Delete, Archive, Start…. Save sends only the fields changed in the dialog, so an agent's change made while it was open (moving the card to Review, say) stays; if both changed the same field, the user's value wins and a notification says so. Deleting a card waits for a change already under way, and a change waiting for it then finds the card gone rather than writing it back. The board in a window is only ever the latest read of that window's workspace.
- **Guidance**: the Assistant's `coordinate-agents` skill describes the board as the shared list of work: plan multi-step work as cards with a full description, start them with `hive_start_task` (with a note for more work on a card), report stalled cards, ask which kind of move to Doing the user means. Agents' `work-on-card` skill says to move a card they were given to Doing before they start (also one back from Review, Passed or Done with more work; one On Hold only when the user asks), keep it up to date, move it to Review with a summary when done (also one that was in Passed or Done), leave Passed to its reviewer and Done until the work is merged, and add cards for follow-up work rather than doing it unasked; `merge-ready` says to move a merged branch's cards from Passed to Done; their session contract repeats those boundaries in a line. `hive_update_task`'s description for the Assistant says moving a card to Doing starts nothing, and to ask which the user means. Tools: `hive_list_tasks`, `hive_read_task` (every agent and the Assistant), `hive_create_task`, `hive_update_task`, `hive_reorder_tasks` (every agent; the Assistant at Control agents), `hive_start_task` (the Assistant only).

### 6.7 Removing projects

**Project → Remove Project…** (also the project's right-click menu and the project header's ⋯) offers three ways, each described in the dialog with what it will touch: running agents (stopped first, conversations kept), the folder, the project's handovers (files named for it, §7.3), its board cards (and archived ones) and its worktrees with any work not merged. The CLIs' own transcripts (`~/.claude`, `~/.codex`) are never touched.

| | **Hide** | **Remove from Hive** | **Delete** |
|---|---|---|---|
| Folder | Stays in the workspace, left out by Hive | Stays on disk; can be moved, renamed or put in another workspace | Recycle Bin |
| Handovers | Left where they are | Copied into `<Project>/.hive/removed/handovers`, then to the Recycle Bin | Recycle Bin |
| Cards | Archived (`project-hidden`) | Archived (`project-removed`), and a copy in `.hive/removed/cards.json` | Deleted (Recycle Bin) |
| Worktrees | Left as they are | **Refused** while any has commits not merged into the project's branch or uncommitted files; otherwise removed with their branches (and their agents) | Recycle Bin (the repository goes with the folder) |
| Afterwards | Listed in **Settings → Workspace**, **Restore** | Listed there while the folder is in the workspace, **Restore** | Forgotten |

- Hidden and removed projects are kept in `workspace.json` (`hiddenProjects`), by folder name; Hive leaves them out of the project list, the Agent API and new cards, and turns them off. A project whose folder has left the workspace shows **Forget** instead of Restore.
- **Restore** brings the project back with the cards archived when it left (cards the user had archived stay archived). For a removed project, the packed handovers go back into the shared notes (never over an existing file) and its cards come back: the archived originals in the workspace it was removed from, else copies with new numbers (references between them follow; references to cards that didn't come along are dropped). The pack is then deleted.
- **A folder holding a pack** (`.hive/removed/manifest.json`) that appears in any workspace, or was never unpacked, shows a banner in its project view: **Restore** (as above) or **Discard** (deletes the pack).
- **Delete** asks for the project's name to be typed. The folder goes to the Recycle Bin first, with its file watchers paused: if Windows can't move it (a program has it open), nothing else has been touched, the watchers resume and Hive says so. After that, a worktree or handover that can't follow is reported, not undone. Unsaved edits to its files in Hive are dropped. A deleted project restored from the Recycle Bin is a new project to Hive.
- **Safety.** Nothing is decided from what the dialog saw. One removal runs per project; its agents are stopped (starts in progress cancelled) and **no agent of the project can start** until it ends (the Assistant, a card, a hand-over are refused); then its worktrees, handovers and cards are looked at again, so a file an agent wrote while stopping still blocks Remove. A worktree **git can't check** (a failing `git status` or `rev-list`) counts as holding work. Hive only removes or deletes a worktree that git lists as one of the project's, that doesn't contain the project or the workspace and isn't another project: `project.json` can be edited by hand, so a path it gives is never deleted on its word alone (Delete leaves such a folder and says so; Remove refuses). The handovers moved or deleted are the ones whose header names the project exactly (so `foo_bar` never takes `foo-bar`'s, even after `foo-bar` has left the workspace); one without a header only when no other project could own it. Restoring never overwrites a different note that took a packed handover's name: the packed one comes back as `<name>-restored.md`, and the pack is deleted only once everything is back.

## 7. Skills and MCP

### 7.1 Skill levels

Skills have no on/off switches: every skill an agent can see is always available. Hive lists them by where they come from.

| Level (label) | Location | Loaded by | In Hive |
|---|---|---|---|
| **Hive** | `<Workspace>/.hive/skills/`, copied into `<Project>/.hive/launch-<agent>/plugin/skills/` (Claude Code) or `<agent folder>/.agents/skills/hive-<name>` (Codex) | Its audience (`metadata.audience`): project agents (every agent, every provider; the default), the Assistant, or both | Skills view: add, add from file, edit, delete; bundled ones restore/revert |
| **Local (User Managed)** | `<Project>/.claude/skills/` (Claude Code), `<Project>/.agents/skills/` (Codex), project root only | That provider's agents in the project | Project Skills tab: add, add from file, edit, delete |
| **User** (`machine`) | `~/.claude/skills/`, `~/.codex/skills/` | That provider's agents everywhere | Project Skills tab: view only |
| **Plugin** | Installed Claude Code plugins | Claude Code agents | Project Skills tab: view only |

- **Deleting from lists** (skills, MCP servers, shared notes, personas, sessions): a bin on the item's row that shows on hover, and another in the top bar of the open item. Rename uses a tag icon everywhere (sessions, notes, files).
- **Skills view** (activity bar): the workspace's Hive skills only, under a warning, "Warning: Editing these skills may change agent behaviour in Hive" (`HiveSkillsWarning`), shown again above the editor while a Hive skill is edited there (not in preview, nor in a project's tab, where Hive skills are view only). **Project → Skills**: what the project's agents get: Hive skills first, in a group that starts open (its count beside it; a note under them counts those for the Assistant alone, which aren't listed, and links to the Skills view) (view, and **Edit in workspace**, which opens the Skills view with the skill in edit mode; if it no longer exists, the view says so), then one turned-on provider's skills, picked from a dropdown (each with its count), in a group that starts folded: Local, User, Plugins (#118; Hive open and the provider folded by Darren's decision of 5 Oct). The dropdown starts on the project's default provider; the last choice, and whether each group was left open, are remembered per project (`config.json` `ui.skillsProvider` and `ui.skillsFold`, by project path; the newest 200 projects). **Copy to workspace** on local, user and plugin skills; its tooltip and notification say who gets the copy, from its own audience.
- **Audience in the UI**: a Hive skill's page shows its audience as a badge (**Project agents**, **Assistant**, **Agents + Assistant**; a tooltip says what it means and how to change it), also for a deleted bundled skill. A row shows it only when it isn't the default. The Skills view's footer and empty page, the Hive tooltip and the delete confirmation say the same: deleting says who stops getting it, that a running Claude Code session keeps its own copy until it restarts, and that running Codex sessions share their folder's copy, which goes when another Codex session in that folder starts.
- **Adding** (both places): **+** creates `<name>/SKILL.md` from a starter; **Add from file** takes a `.md` (becomes `SKILL.md`, with the frontmatter `name` set and a frontmatter added if missing) or a `.zip` (unpacked as the skill folder: `SKILL.md` at its top or inside one top folder; at most 500 files and 50 MB; unsafe paths refused). Names: letters, numbers, `-`, `_`, max 64. A local skill can be added for both providers at once (tick box, shown when both are on). **Deleting** moves the folder to the Recycle Bin; only Hive and local skills can be deleted, never Hive's marked Codex copies.
- **Who gets a Hive skill** is its `SKILL.md`'s `metadata.audience` (the Agent Skills format's place for a tool's own keys, so the CLIs read the file as usual): `agents` (the default, also for a skill without it) for project agents, `assistant` for the Hive Assistant, `all` for both. It is not a switch: it says which kind of session a skill is written for, so a user's skills don't reach the Assistant and the Assistant's don't reach agents. Reading a skill grants no tools or permissions. The header is read as YAML (js-yaml, core schema; from the first 64 KB of the file), so comments, flow mappings (`metadata: { audience: assistant }`), quotes and block scalars mean what YAML says, and only `name`, `description` and `metadata.audience` of the right types are used. **A Hive skill whose header can't be read** (not closed, not valid YAML, including a key given twice, not a mapping) **or whose audience is anything else** (a misspelling, a list, or written but empty: `audience:`, `null`, `~`; only an audience left out is the default) **is given to nobody until it is fixed**, never to a guessed recipient: the Skills view marks it **Not given** with the reason, the API's listings and status carry `problem` (`audience: "none"` in the status), tool listings say "given to nobody: …", and each launch lists it in its problems.
- **Bundled skills** ship in the installation (`resources/skills`): for agents `work-on-card` (carry a card from Doing to Review), `review-agent-work` (review another's work, with the board's review marks), `merge-ready` and `use-hive-api` (scripts against the Agent API); for the Assistant `coordinate-agents` (plan as cards, brief and start agents, follow them, stalled cards); for both `handover`, `pick-up`, `split-work` (plans only) and `workspace-note`. **They're kept up to date in each workspace** (`bundled.ts`, each time it opens; the bundled personas the same way): a bundled skill the workspace was never given is added; an untouched copy of an older version (its content, line endings ignored, matches a version Hive shipped before this one; a link (symlink or junction) in it is never followed and counts as a change, since Hive ships none: `src/main/bundledHistory.json`, which `npm run bundled-history` appends to and a unit test keeps current) is replaced whole (a copy beside it renamed into place, so nothing reads it half-copied; a copy whose files are open stays until next time). **An automatic update or add never overwrites the user**: the swap (`swapIn`, also used for personas) is told what the copy was when the update was decided (its content hash, or nothing there for an add) and checks it again once the new version is copied (holding Hive's own editors' file locks), on the old copy once it has been moved aside, and once more before the old copy is removed (a write through a file left open); a copy edited, deleted or replaced meanwhile is put back as the user has it, the update is abandoned until the next scan (which sees its real state), and the manifest isn't changed. When both the old copy and the new one were edited, the old goes back in place and the new is kept beside it as a conflict copy; what a putting-back sets aside is removed only if it is still exactly the new version, and if a rename for it is refused, nothing is deleted (what can't go back is kept as a conflict copy). What a crash in a swap left behind (an old copy, a rollback's backup) is removed only when it is a version Hive shipped; anything else is kept beside the item as `<name>-conflict-<time>` (listed like any skill or persona), after the user's original is put back in an empty place. Another program writing through a file it held open in the instant between the last check and the removal is the one case this can't see; on Windows an open file usually stops the swap altogether. Restore and Revert, which the user asks for, replace whatever is there (sending it to the Recycle Bin first); an edited copy is kept, and offers **Revert to default** (with **Update available** only when it was made from a version this Hive knows to be older than its own: not from a newer Hive's, where Revert would go back); a deleted one stays deleted, listed greyed with **Restore**. `.hive/bundled.json` records which were given and the version each copy came from. A workspace from before it has none: a bundled skill missing there was deleted by the user (a new bundled skill is added), and a persona folder that doesn't exist means it never had them. A copy of a version this Hive doesn't know (a newer Hive's, sharing the workspace) is left alone. Revert and Restore send the workspace copy to the Recycle Bin.

For Codex, Hive skills are copied into `<agent folder>/.agents/skills/hive-<name>` on each launch (removing Hive copies of skills it no longer gets), since Codex reads skills only from there; the Assistant's go into the workspace folder, where it works. Those copies carry a `.hive-copy` marker and are never listed as local skills; a changed skill is swapped in whole, and what a crash during a swap left behind (Hive's dot-folders named for it) is tidied at the next launch, under the same lock. Each launch records what it delivered of each skill (`launched` in `GET /v1/projects/{name}`): the revision of the copy the CLI reads, and `problems` for a skill not delivered as asked (a folder of the user's has its name; its old copy was in use, so it kept that one; its folder in the workspace is gone or couldn't be read). A kept old copy leaves the agent needing a restart; a user's folder doesn't, since a restart can't change it. **A skill is copied within the hashing limits as it is read** (`copySkillTree`: entries listed a batch at a time, depth, bytes actually read; the entry limit counts the skill's own entries, with Hive's `.hive-copy` marker allowed on top, one a folder, so a skill at the limit is still within it once its copy is marked), since its source can change while it is copied, and the copy is hashed before it is published: what is recorded as delivered (and in a Codex copy's marker) is that copy's revision, not the source's from before. A source grown past the limits, or with a file gone or unreadable, mid-copy publishes nothing: Codex keeps its old copy (reported with its revision and why), a Claude Code launch leaves the skill out (revision null, and why); nothing is left half-copied. One skill's failure is its own: the launch delivers the others, and the failed one's record is Hive's copy from an earlier launch (its revision, the problem saying it kept it) or nothing, never a folder of the user's. A source that couldn't be read may work at the next launch; one over the hashing limits, or with a link that can't be made, is a lasting problem. If the skills folder itself can't be set up, each record is what is already there, the same way, and a failure to keep the copies out of git changes no record.

A link in a skill (symlink, or junction for a folder) is copied as a link to the same place, never as what it points to, and counts as content by where it points (`contentHash`, also for the markers and when telling the user's same-name folder from a copy of Hive's); a link Windows won't let Hive make (a link to a file needs a privilege) is a lasting delivery problem, naming the links: a Claude Code agent gets the rest of the skill without them; a Codex copy is swapped all or nothing, so it keeps its old copy whole (or, the first time, has none).

The workspace folder is a store only; no agent loads from it directly. Copies are used (not links): a Claude Code agent's are its own (`launch-<agent>`), so a running one keeps the version it started with. Codex agents sharing a folder share its copies, so when one launches with a changed skill, the others read the new version the next time they use it (Codex reads a skill's files when it uses them). Edits reach a session at its next launch either way.

### 7.2 MCP servers

One file per server: `<Workspace>/.hive/mcp/<name>.json`, in Claude Code's format plus an optional `description`:

```json
{ "command": "npx", "args": ["-y", "@modelcontextprotocol/server-github"],
  "env": { "GITHUB_TOKEN": "${GITHUB_TOKEN}" }, "description": "GitHub issues and PRs" }
```

Enabled servers are merged into `launch/mcp.json` for Claude Code, and passed to Codex as `-c mcp_servers.<name>={…}` (with `default_tools_approval_mode = "approve"`). The user's own servers and a project's own (`.mcp.json` for Claude Code, `.codex/config.toml` for Codex) are not loaded, by the same rule as §5. Secrets are passed as environment references only; a definition whose values can't be passed safely to Codex is skipped with a log warning. Server code in `<Workspace>/.hive/mcp/<name>/` is referenced in place, not duplicated. Hive warns when a definition looks like it contains a literal secret.

### 7.3 Built-in Hive MCP server

If "Provide Hive tools to sessions" is on (default), every session, of every provider, also gets a `hive` MCP server (bundled script run via Hive's own executable) exposing the Agent API as tools: list projects, project status, read/write shared notes, read the latest handover, create handovers, notify the user, session usage. Its MCP instructions (sent on `initialize`) are Hive's **session contract** (`hiveInstructions` in `shared/hiveGuidance.ts`), kept to what must hold whatever else is loaded: which project and workspace, that handovers, shared notes, other projects and the board are Hive's (use the tools, not the file system), the board's scope, which skill covers which workflow (`work-on-card` for a card given to it, `review-agent-work` to review one), and the board's boundaries in a line (Doing first, Review with a summary when done, reviewing isn't working on a card, Done only when the user asks, follow-up work as new cards, column order is priority), so a session without the skills keeps them. Procedures live in the skills, arguments and side effects in the tools' descriptions, and enforcement in the Agent API. If the project has a handover, the instructions name the latest one. `GUIDANCE_REVISION` (a hash of this text, the control rules and a card's prompt) is in `GET /v1/status`, Help → Copy Diagnostics, and each running agent's `launched` in `GET /v1/projects/{name}` with its skills' revisions, so an older build's or launch's guidance can be told apart. Skill revisions are kept per open workspace (and once for Hive's shipped copies) and hashed again only when a skill's files change (their sizes, times and file ids, checked on each call without reading them), so status polls don't re-read every skill; callers asking at once share one scan, a closed workspace's revisions are dropped and hashing for it stops, and a skill over the hashing limits (64 MB read, 2000 entries, 12 folders deep) has no revision and says why. Too big by its files' sizes is found without reading them and kept like a revision while nothing changes, so polling an unchanged too-big skill reads no content (over the entry or depth limit, each check is a walk stopped at the limit); a file that grows while it is read is still stopped by the cap on bytes read. Listing skills reads only the first 64 KB of each `SKILL.md` (its header), again only once it changes, and at most 1000 entries of a skills folder. A launch checks each skill against the limits before copying it: one over them isn't delivered (Claude Code) or keeps the copy it had (Codex, which reports that copy's revision), with the reason in `launched.problems`. A handover belongs to a project when its file name is `<date>-<project slug>-<title slug>.md` (as `hive_create_handover` writes it). When project names overlap (`hive`, `hive-website`), a file that could belong to either is decided by its `- **Project:** <name>` header line. Codex doesn't show MCP server instructions to the model, so Hive passes the same text to Codex as `developer_instructions`.

## 8. Git

- Project: `.hive/` is added to `.git/info/exclude` (idempotent) when the project is a git repo; re-checked on activation.
- Workspace: `.hive/` is **not** excluded; it is meant to be committed.
- The Changes tab shows `git status` and a Monaco diff (HEAD vs working tree) per file.
- **Hive's git commands never write the index as a side effect** (#212): they run beside the user's and agents' own git commands, and `git status` (and `git diff` against the working tree) otherwise refresh the index, taking `index.lock` for a moment, so a `git add` or `commit` at that moment failed with "index.lock: File exists". Every git command Hive runs (`git()`, `GIT_PREFIX` in `src/main/git.ts`) passes `--no-optional-locks` and `-c diff.autoRefreshIndex=false`; locks a command needs (commit, merge, reset, worktree add) are still taken. Status compares content in memory, so a file touched but unchanged still isn't listed; a worktree branch's changes since it left base (`diff --name-status <merge-base>`, which without a refresh lists stat-only files as modified) drop such a file only when git says exactly that it isn't changed: its working copy matches the index (status) and the index matches the merge base (`diff --cached`, mode included). A working copy that differs from an index that differs from base is kept (shown even if it was changed back by hand), never hidden.
- **Ignored entries in the Files tab** (#222): `git check-ignore` exits 0 or 1; any other exit (128, "index file open failed" while another git command rewrites the index on Windows) is a failure, not "nothing ignored". A busy index is tried again (4 tries, 50 ms apart); outside a repository nothing is ignored. If git still can't say, the folder keeps its last known ignored entries (a memory of the 500 folders listed last) and is listed again 500 ms later (`files-changed`; at most 3 times in a row while it keeps failing). The failure is logged once per project.

## 9. Usage, compaction and memory

Each provider's adapter reads its own transcripts into one usage shape. Codex: rollout files under `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-…-<id>.jsonl` (`token_count` events for tokens, context window and plan limits; `session_index.jsonl` for titles). Claude Code: `~/.claude/projects/<encoded-path>/<session-id>.jsonl`, where the encoded path replaces every non-alphanumeric character of the project path with `-` (matched case-insensitively). Claude Code's transcripts don't carry the context window; for a running session it comes from the status line (`context_window.context_window_size`) and is added to the session's usage.

**Model choice** (global default, per project, per agent and for the Assistant): the models Claude Code reports (§10, models and capabilities), else the fallback list in Settings → Claude Code (as shipped: Latest aliases, pinned versions and older versions, hidden until requested); and a custom model ID. There is no 1M-context choice: current models (Fable, Opus 4.7+, Sonnet 5+) have the 1M window without asking, and Opus 4.6 and Sonnet 4.6 reach it only through a `[1m]` model ID, typed as a custom model (the placeholder says so). Saved `[1m]` choices from 0.2 still work and show as custom models. Availability for the account is only known when a session starts.

**Use 200K context (instead of 1M)** (providers with `capabilities.contextLimit`: Claude Code): global (Settings → Claude Code, off by default), per project (Inherit / On / Off), per agent (Add Agent and Agent Settings: the project's / On / Off, stored as `use200kContext` on the agent and cleared when its provider changes) and for the Assistant (Settings → Assistant and Assistant Settings). Resolved like the model: the agent's, else the project's, else the global setting. A session launched with it gets `CLAUDE_CODE_DISABLE_1M_CONTEXT=1`, and a `[1m]` suffix is dropped from its model, since Claude Code rejects such a model as unrecognised when 1M is off (2.1.287). A change applies on the next start or restart (it's part of the launch signature, so running agents show Restart session).

**Metrics per session**
- Input, output, cache-write, cache-read tokens (assistant `message.usage`, de-duplicated by request id).
- Current context size: the last assistant entry's `input + cache_read + cache_creation`.
- Compactions from `system/compact_boundary` entries: trigger, `preTokens`, `postTokens`.
- Cache TTL detected from `cache_creation.ephemeral_1h_input_tokens` vs `ephemeral_5m_input_tokens` (overridable in settings).
- Model, Claude Code version, session title (`ai-title` / `custom-title`), last activity.
- API-equivalent cost from `cost-state` entries (`totalCostUSD`), shown on the Overview as "API-equivalent cost". Claude Code writes them only at some turns' ends (hours can pass without one), so the requests after the last one get Hive's estimate on top, and the cost shows as partly estimated ("≈"). For providers that don't report cost (Codex), Hive **estimates** it from a price table (per million tokens: input, cached input, cache write, output), shown with "≈". Hive ships the published API prices as editable defaults (checked 30 Sep 2026, GPT-6.1 Sol 5 Oct 2026; Claude's cache writes are 1.25× input and cache reads 0.1× unless listed; never fetched or scraped) and each provider's settings page has the table, labelled with the date they were checked: the user can change any price, add models, remove them (a removed shipped price is no longer used) and **Reset to defaults**. Only the user's changes are stored (`prices`, `pricesRemoved`), so Hive's later prices still reach models they never edited. A session whose model has no price has an **unknown** cost, never $0: the agent's footer shows **$?**, the Overview's running agents **Unknown**, and its cost totals (the summary, each provider's, the Workspace Overview's and the Assistant's, by agent and by day) and session details **Unknown** when no session in them has a price, or the known subtotal with **+ ?** ("≈ $1.20 + ?") when some haven't; the agent's footer and the running agents say (on hover) that Hive has no price for the model and to add one in Settings → <provider> → API prices. It is the API-equivalent value, not what a subscription charges.

**Keeping up with the CLIs**: a transcript of over 200 KB in which Hive finds no requests at all is taken as a format change it doesn't understand, and the user is told once per provider version. Sample transcripts per supported CLI version are unit-test fixtures (`tests/fixtures`).

**Overview tab**: first the project's cards at a glance (`TaskStrip` in `Board.tsx`, shared with the Workspace Overview, counts from `taskOverview()` in `shared/tasks.ts` for the project's cards only): On Hold, Todo, Doing, Waiting for review, Passed, Done, Stalled and Blocked (blocked not counting Done), from the store's board, so they follow every card change without a reload; each number opens the project's Tasks tab, and a project without cards shows "No cards for this project" with **Open Tasks** (the Workspace Overview's strip hides when the board is empty, and its numbers open the whole board). Then a period (Today, 7 days, 30 days, All time; All time by default) and a project summary across every provider (tokens, API-equivalent cost, sessions, prompts). Periods are **local calendar days** (Today since midnight; 7 and 30 days include today) and count only what happened in them: each session's usage is kept **by day** (`SessionUsage.days`, `shared/usageDays.ts`): requests, tokens, prompts and compactions on the day they happened; Codex's running totals by what they grew by each day. A day's cost is its share of the reported cost (each Claude Code cost report's increase is split between the days of the requests it covered, in proportion to Hive's estimate for them, so the days add up to the reported total) plus Hive's estimate for requests after the last report; for providers that don't report cost, Hive's estimate. A session counts in a period's sessions when it had activity in it. For 7 and 30 days a chart shows tokens per day (cost and prompts on hover). The day charts (both Overviews' and Performance's) share their look: each day or hour is a tile with a soft background (`.daily-col`, `--daily-slot`), 3 px apart, so a day without tokens still reads as its own column; Performance adds its hatching (not recorded) and fade (partly recorded) on top. Usage is read incrementally: each transcript keeps its parser and offset, and only lines added since are read (a long session's transcript can be over 100 MB). Then the agents running now (context against the model's window, cost), then one section per provider used (its totals and its plan limits: Claude Code's 5-hour and weekly, Codex's primary and secondary windows), a table by agent, and one agent's session details (its running session, else its most recent; the focused agent's until another is picked in the agent picker shown with more than one agent; compaction history as a data table, below). Its **compaction history** is a `DataTable` (`components/DataTable.tsx`, rules in `shared/tableView.ts`; #124): When (newest first by default; a text filter on the formatted date), Trigger (a choice), Before, After, Freed (sortable, biggest first); ten rows a page. A row (click, or Enter when focused) opens the Sessions tab on that session at that compaction's divider, its summary open (`openInSessionsTab(path, id, n)` → `transcript:compactions` gives the nth compaction's item id), when its transcript or Hive's backup is there; otherwise rows aren't clickable. The footer's context (`showInOverview`) scrolls to it (`#compaction-history`), else to the session details.
- **Data tables** (`DataTable`): one component for tables that grow, with the look of Hive's other tables (`.table` in `.table-wrap`, Performance's too): a header click sorts (ascending, or descending first for dates and numbers; then the other way; then the default order; `aria-sort`, a chevron, the header a button), quick filters in a row under the headers (text contains, any case; a choice of the rows' values), and paging under it (rows per page 10/20/50/100, remembered per table in `ui.panes` as `table-rows:<id>`; "21–40 of 133"; first, previous, "Page n of m", next, last), hidden when one page of the fewest rows holds them all (so a bigger size can always be made smaller again). Rows can be selectable (`selection`, #249): a checkbox before each row, and one in the header for every row the filters let through, on every page. A choice filter can match rows with several values (`values`: a card's labels). Filters and sorting apply before paging; a filter or rows per page change goes back to page 1, and a page past the end shows the last. Only the page is rendered. No rows: a message instead of the table; no matches: a row saying so, with Clear filters. It scrolls sideways inside its pane at narrow widths. It (and the session lists) update per **Settings → Sessions → Overview updates**: **Live** (default: as sessions change, at most every 15 seconds, only while shown), **Every minute**, or **Only on Refresh**; the Overview has a Refresh button. A session list reads each project and session file once.

**Workspace Overview** (activity bar, Ctrl+Shift+O): the same summary for the window's workspace. A period (Today, 7 days, 30 days, All time; **7 days** by default, kept while Hive runs), then a strip with the board's cards per column, stalled and blocked (each opens the board); the summary (tokens, API-equivalent cost, sessions, prompts) across every project **and the Assistant**; for 7 and 30 days a chart of tokens per day **stacked by project** (the six that used the most in the period, in name order so each keeps its colour while the set stays the same, the rest as "Other (n)"; a legend, and each day's numbers by project on hover; colours from a validated categorical order stepped for each theme); every running agent (the project's name and the agent's, click opens it; the Assistant's opens its panel); a sortable table **by project** (sessions, tokens, cost, share of the tokens, last active; the Assistant is its own row; click opens that project's Overview, or the Assistant view); and a section per provider with its totals and plan limits. Hidden and removed projects aren't counted (a note says how many). The sidebar lists each project with its cost for the period. It uses the project Overview's counting (`shared/usageTotals.ts`) and its update setting, and only while shown; main sends only what totals need (`workspace:usage`: each project's and the Assistant's Hive sessions, with deleted sessions' kept usage, no sessions started outside Hive and no transcript or backup checks), with usage from the usage cache (a transcript is read only where it grew). Budgets, alerts, export and comparing periods are not in it.

**Re-cache estimate on resume**: if time since last activity exceeds the TTL, "Resume will re-cache ≈ N tokens" (N = current context size); otherwise "cache likely warm (≈ M min left)". Always labelled as an estimate. Resuming a session whose cache has expired with more than 20k tokens asks first: **Archive and Start Fresh** (archives it and starts a new session in the same agent) or **Resume**.

**Transcript backups**: while a session is live Hive brings its copy in `<Project>/.hive/sessions/` up to date at most once a minute while it changes, at the end of every turn (`Stop`) and when the session exits, so sessions survive Claude Code's own cleanup. Transcripts only grow, so while the copy is still the start of the transcript (same first and last 4 KB at its length) only the new bytes are appended; otherwise (the first copy, a rewritten transcript) the whole file is copied to a temp file and renamed into place (`syncCopy` in `fsutil.ts`, one at a time per copy). A failed backup is retried at the next look. Archiving moves the backup to `.hive/archive` and brings it up to date the same way.

**Memory tab**: grouped by provider. Claude Code: `CLAUDE.md`, `CLAUDE.local.md`, `.claude/CLAUDE.md`, the user `CLAUDE.md` and its auto-memory folder for the project. Codex: `AGENTS.md` and the user `AGENTS.md`. When a project's agents use more than one provider and they don't read the same instructions, **Share one AGENTS.md…** makes AGENTS.md the shared file: CLAUDE.md gets an `@AGENTS.md` import line (anything else in it stays, for Claude Code only); with no AGENTS.md yet, CLAUDE.md's content moves into it first, so nothing is lost. Providers declare the import line in their descriptor (`instructionsImport`); those that read AGENTS.md themselves need none.

**Usage cache**: each transcript's usage is worked out incrementally and kept in memory, and also in `usage-cache.json` in the profile (§4.3): per transcript path, its session, provider, size, modified time and the parser's result **before costs**. Costs (the provider's report, Hive's estimate, each day's share) are worked out from it with the current prices whenever it's shown, so price changes need nothing more. After a restart, a transcript with the same size and modified time is taken from the file without being read; one that changed while Hive was closed (a session continued outside Hive) is read again in full, since the parser's state isn't saved. The file is derived and disposable: written a few seconds after a change and at quit, ignored when damaged or written by another Hive version (each version starts afresh, as parsers change), and **Settings → Sessions → Clear the usage cache** deletes it. **Usage cache size** (5,000 transcripts; 100–50,000) bounds it, least recently used first; the parsers themselves (each holding a session's request history) stay limited to 200.

**Busy actions** (a shared pattern: `useBusy()`, `BusyButton` and `Modal`'s `busy`/`error`; `confirm({ run })`; `runOnce()` for buttons without a dialog): while an action runs its button shows a spinner and an "…ing" label, the dialog's other controls are disabled, Escape, × and clicks outside don't close it, and repeat clicks do nothing; a failure keeps the dialog open with the error (the button offers **Try Again** where it helps). Used by Start, Remove Project (its label says what it does: Hiding…, Removing from Hive…, Moving to the Recycle Bin…; no stages reported), the card's Save, Delete, Archive and Comment, Compact, Agent Settings, Stop All Agents, Delete note and Delete MCP server; Resume All and Remove Agent show a spinner on their button or tab. Questions (confirm, choose, prompt) render above every other dialog, and Escape closes only the topmost dialog.
**Dialogs dim the window buttons.** A backdrop (`.overlay`: a dialog, nested or not, or the command palette) dims the whole page, but Windows paints the native minimise, maximise/restore and close buttons over it (`titleBarOverlay`). So the page tells main how many backdrops are up (`useBackdrop()` keeps them per window, in order; `window:setBackdrops`), and main dims the buttons' background and symbols the same way: black at the backdrop's 45% once for each, as the page's layers stack (`shared/titleBar.ts`; a question over a card is two), back to the theme's colours when the last one goes. The same stack decides which backdrop Escape is for: the top one only, so Escape with the palette over a card closes the palette. Main keeps each window's theme colours and dimmed state (`main/titleBar.ts`), so a theme change while a dialog is up stays dimmed in the new theme's colours, each window is on its own, and a page that reloads starts undimmed. The buttons keep working, and Windows still highlights them on hover. The overlay exists on Windows and Linux only; elsewhere there is nothing to dim.

**Footer usage belongs to its conversation**: the usage an agent's footer shows (context, cost) is held with the project and session it was read for (`src/shared/liveUsage.ts`); after a switch it shows `– ctx` until the new conversation's own usage is read, never the previous one's, and a refresh that fails keeps the same conversation's numbers, faded, with a note in the tooltip.

**Transcript size**: a running agent's live state carries its transcript's size (`transcriptBytes`, from the 5-second look). The pane footer shows it next to the context count ("6.1 MB"), orange from **Settings → Sessions → Warn when a transcript is over** (20 MB; per-project override; **Never** turns it off; a 50 MB saved by 0.3.x or earlier, the old default, is moved to 20 MB once, config version 5). A long transcript slows the CLI and Hive (each turn, resume and transcript view reads more), and compacting doesn't shrink it, since the file keeps the whole history. Crossing the limit notifies once per conversation (a toast with **Hand Over to…**, and a desktop notification under the usual settings, no chime). Clicking the size opens **Hand Over to…** for the agent, with the agent itself chosen when its transcript is over the limit. The Assistant sees `transcriptMB` and `transcriptWarnMB` in `hive_agent_activity`. For the Assistant itself the advice is a new conversation, and the click does nothing.

All parsing lives in the adapter, tolerates unknown fields, and degrades to "unavailable".

### 9.1 Performance metrics

Hive counts what its own parts cost, locally, per workspace (`metrics.ts`; the contract and units are in `shared/metrics.ts`), so a change to its guidance or API can be judged by what it does to real use. **On by default** (Settings → Sessions → **Record performance metrics**); turned off, nothing new is recorded and what was recorded stays until **Reset performance metrics**. Kept **30 days**: hourly buckets for 7 days, folded into daily ones after, in `.hive/metrics/metrics.json` (git-ignored, this machine's; at most 2 MB, the oldest buckets going first), saved 30 seconds after a change, when the workspace closes and when Hive quits. Retention is applied whenever the data is loaded or read, however long Hive was idle, and what expires is removed from the file too (a read that changes nothing writes nothing); a store holds at most 201 buckets whichever way the clock moves, and buckets dated more than a day ahead (a clock that was ahead) are dropped. A workspace's metrics file has one writer at a time across openings: a workspace reopened (by any window, its path in any case) while its last save is still going continues with that same store, so a Reset or new records can't be overwritten by the older save. The 2 MB cap is in UTF-8 bytes, even if only one bucket is left, so Hive never writes a file it would refuse. The saved file is untrusted input: a file over 2 MB isn't read (the read itself stops at the cap), and every bucket, series, counter and label in it is checked as it is loaded (what isn't valid is skipped).

- **What is measured, in exact units**: UTF-8 bytes; characters as UTF-16 code units (JavaScript string length); milliseconds on a monotonic clock (the wall clock only picks the bucket, so a clock set back lands in an earlier hour). **No token estimates**: provider token usage is only ever what the provider reported.
- **Agent API**: requests by route template (never the path asked for), method, caller role (agent, Assistant, script) and outcome (ok, client error, denied, server error, cancelled: a client that went away before the reply); count, a latency histogram, request body bytes as received (a partial or refused body as far as it came) and response body bytes as serialized (an aborted reply may not all have been sent; headers and transport not included). Requests refused before Hive knew whose they were, event streams (connections, events, bytes, time open) and requests in flight are process-wide, not any workspace's. The health check and the bridge's own reports aren't counted.
- **hive tools (MCP)**: the bridge reports each call's final text, the one the model got (characters and UTF-8 bytes), its time, outcome and mode (compact, or detail when the call asked for it), and once a session start the tool list as its CLI got it (bytes of the JSON). Reported with the session's own token (an agent's or the Assistant's), checked and bounded (at most 50 calls a report; a malformed one is refused, not stored), and never counted again as API traffic. Reports never hold the bridge up: one at a time, each with its own 3-second deadline, at most 500 calls waiting; a report that fails or times out drops what is still waiting, so a bridge whose CLI has gone exits within one deadline.
- **Guidance**: each launch's Hive-supplied parts, exact sizes, by provider and role, each part apart (`launchParts()` in `guidance.ts`): **core** (the session contract, once, whichever way the provider gets it), **custom** (what Hive adds for the project: the latest handover's pointer), the Assistant's **role** (who it is, the workspace, Control's rules) and its **persona** (text that isn't as expected is counted whole, never split by guesswork), the skills that reached the session, measured on the copies its CLI reads, not their sources (how many, their catalog entries' bytes, their bytes on disk; a model reads a skill's body only when it uses it, which isn't observable), how many skills asked for didn't reach it (too big, a link that can't be made, a failed copy, a broken header), and how many it got whose copy couldn't be measured (`skillsUnmeasured`: gone, unreadable, or a header that isn't a valid skill header; left out of the sizes, unknown rather than zero).
- **Skill service**: scans (timed), shared scans, hits, misses, invalidations, skills too big to check, and the files, bytes, header bytes and directory entries it read: the workspace's, not any project's.
- **Provider usage**: what the providers reported for sessions active in the range (as the Overview has it), summed per provider and whose sessions they were (project agents' or the Assistant's; scripts have none, and the report says so): each session's total, labelled as such, how many are running now, requests, compactions, and context as a snapshot (each session's last request: how many reported one, average, largest, the largest window), never summed. Its cells are one or two deliberate lines (#241, `CellLines` in `components/DataTable.tsx`): Sessions the count over "n running · n unknown", Context the average over "max of window", Cost "≈ $…" over "+ n unknown"; a table's numbers never wrap (`.table td.num`), and a table too wide for its section scrolls in its `.table-wrap`. A session with none reported is unknown, not zero: left out of the totals and counted as unknown cost too (a row whose sessions are all unknown shows unknown, not $0). The workspace's own work and the Assistant filter keep the Assistant's sessions only; a project scope never has them. Session history that can't be read (a project's or the Assistant's) is counted, never named (`providersUnreadable` of `providersHosts`): the totals are partial, or unknown if none could be read, and the page says so even when there is nothing else to show; the next read that works reports in full again.
- **Coverage**: when Hive observed the workspace (open in Hive, recording on, since the last reset), kept with the metrics as up to 500 `[start, end]` stretches, extended by each record and query and every 5 minutes while the workspace is open (an unref'd tick; saved with the next save, never a write of its own), so it is right to within about 5 minutes; a longer gap starts a new stretch. Known boundaries are never joined over, however short the gap: recording turned off ends the stretch at that moment (the setting's change, or a touch that finds it off), the last window holding the workspace closing ends it (another window reopening it while it saves starts a new one), and a store loaded from disk starts a new one at its first use. History evicted to keep the file under its cap or the bucket count (not by age) is unavailable, not idle: the store keeps `evictedThrough` (saved), observation before it is removed, and every report whose range reaches it says so (`coverage.evictedThrough`, the storage's own fact, no loss count). Expired with the buckets, cleared by Reset. A report has `coverage` (the range, the time observed in it, since when, how many stretches) and each trend point `observedMs`, so an unobserved slot reads as no data, not zero; rates are per hour observed.
- **Scope and attribution**: work is recorded in the workspace it started in (a workspace that is closing admits nothing new: its lifetime stays ended until it has fully closed): a request, launch, scan or read that is still going when its workspace closes (or its window opens another) is dropped, never recorded in the next one, and a metrics read that the workspace switches under is refused. An agent's work is its project's; the Assistant's, scripts' and the shared skill service's are the workspace's own, never spread over projects. A workspace query has each project's part and the workspace's own, which add up to its totals without counting anything twice; a project query has that project's part only (matched case-insensitively, as the API matches project names), and its `dropped` counts only that project's dropped measurements. Who lost measurements is itself bounded (as many owners as projects); past that a loss is untracked: a workspace report has that total (`droppedUntracked`), and a project report only says some losses couldn't be attributed (`lossesUnattributed`), with no count from other projects or the workspace, never a known zero. A project's own known losses are summed bucket by bucket. Project names are plain keys: a project called `constructor` or `__proto__` is like any other, and a name longer than 128 characters is kept under a bounded label of its own (its start, `|` and a hash of the whole name), matched the same way. `|` can't be in a project's name, so such a label never equals another project's name. A measurement that is only dropped (a cap was full) is still saved as a loss. An agent may read its own project's.
- **Bounds**: every label comes from a fixed set: the Agent API's route templates, the hive MCP server's own tools (a list a test keeps equal to the server's), the provider ids; anything else is "(other)". Per hourly bucket at most 100 projects and 2000 series, what doesn't fit dropped and counted (`dropped`). Nothing stores a prompt, a body, a token, a URL or a path. Recording a request costs about 0.3 µs; a bucket at its series cap is about 430 KB; the collector has no timers while idle.
- **Performance view** (activity bar, after Workspace Overview; `views/Performance.tsx`, selection and totals in `shared/metricsView.ts`): the workspace's metrics, with a scope filter (sidebar or **Scope**: the whole workspace, the workspace's own work, or one project, queried as that project's scope), and a **Performance** tab in each project (after Overview) fixed to its project (no workspace or other-project data reaches it: its query is the project scope). Ranges **24 hours, 7 days, 30 days**; filters by role (agents, Assistant, scripts; the tab has agents only) and provider (launches and provider usage; the rest isn't per provider), kept per view and project while Hive runs. Every filter goes to Hive with the query (`queryFor()`: `role`, `provider`, `own` for the workspace's own work), which narrows the parts, the trend and the provider usage alike, so the cards, tables, chart and an export always agree; what a filter can't narrow is said (`filters.notFiltered`: API requests and tool calls aren't per provider; the skill service, Hive-wide numbers and dropped measurements aren't per role or provider). Cards (requests per hour observed, failure and cancelled shares apart, p50/p95 from the histogram, bytes sent and received, tool characters and bytes, guidance per launch), a trend (`trend` in the query: every hour of a range up to 2 days, else every day, at most 200 points, empty slots zero) of requests with failures, tables by tool (by characters), route (failed and cancelled apart), guidance (provider and role: per launch core, project, role, persona, skills, catalog, bytes on disk, not delivered or unmeasured) and provider usage (by provider and whose: sessions and running, tokens, reasoning shown as part of output, requests, context average and largest of the window, compactions, cost with ≈ when estimated and unknown sessions counted). Unobserved trend slots are hatched, partly observed ones shaded. The workspace scope adds the skill service and Hive-wide streams. Coverage (range, retention, how long Hive was recording in it and the gaps, dropped measurements, losses not attributed: shown for any project scope, from either entry) and what isn't measured are always shown, and a banner when recording is off. Refreshes every minute while shown and the window is visible, one request at a time, and a late reply for another scope or range is never shown; it reads through IPC (`metrics:query`), so looking at it records nothing. **Export** (`metrics:export`) saves the page's own query (scope, range, filters) as JSON (`schema: "hive-metrics/1"`, Hive's version, units, export time, range, filters, coverage, and the report with its trend) through a save dialog; Shift+click sanitizes it (project names become `project-N`, the same name the same number; no workspace path).
- **Compare** (#117; the Performance page's Now/Compare switch, `views/PerformanceCompare.tsx`, rules in `shared/benchmark.ts`, storage in `main/benchmarks.ts`): a baseline against a run, each a kept artifact of the page's scope. Sources: **Keep current view** (the page's own query as an export summary), **Import…** of a Performance export (`hive-metrics/1`, kept as its summary) or a scenario benchmark (`hive-benchmark/1`, written by `npm run scenarios`). Files are untrusted input, imported or kept alike (the same normalisers, a fresh bounded object, never the one read): read with a cap (at most 2 MB in UTF-8 bytes, however the file changes meanwhile), known measures only, bounded scenarios (100), samples (20), checks (60), skill revisions (60) and text; a series that isn't what it should be counts as none. Scopes: the whole workspace, **its own work** (the view with "Workspace's own work" chosen: its own list, never the whole workspace's) and each project (its tab, or the view with it chosen). A scenario benchmark is the whole workspace's only. A project's export must hold only that project's data (one also holding other projects' or the workspace's is refused, never summed); a workspace export's project part only after the page asks (sanitized ones, own-work ones and ones without that project are refused, and why); an own-work export must hold no project's. Up to 20 kept per workspace in `.hive/metrics/benchmarks` (an index and one file each); each scope remembers its baseline and run (selections of scopes with nothing kept are dropped). Every operation is bound to the workspace it started in: its folder and lifetime are taken before any await (a dialog, a read, the queue), and one whose workspace closed or switched meanwhile is refused, never written into the next; a project-part answer is bound to that workspace, scope and lifetime, used once, within 10 minutes. The index is the only authority and records every change in progress: an entry being added (`adding`) or removed (`removing`), with its change's id. Keeping is (1) the index records the new entry as adding and the evicted ones (the oldest unpinned, when full; refused if all are pinned) as removing, (2) the file is written, (3) the new entry becomes kept; then each evicted file is removed and its entry dropped only once the file is gone. Remove is the same: recorded as removing (off the list), the file removed, then the entry dropped; a removal whose file can't be removed stays recorded, is retried on every read (also after a restart), is said, and never comes back to the list. The index holds at most 40 entries in all (kept, being added, being removed): the reader's bound, which every index Hive writes is checked against first, and a keep that would pass it (removals piling up while their files stay in use) is refused, saying why, until they finish. Renames are retried while Windows holds a file for a moment, the workspace checked before every attempt, so a retry after it closed or switched commits, moves or sets aside nothing. Every write is staged and renamed into place only after the workspace is checked again, so a workspace that closes or switches during a write commits nothing. Every read first validates the whole index, then reconciles it with the folder, deleting only what that validated index proves: an add whose change never finished is rolled back (its file goes, what it evicted is kept again), and recorded removals are retried. A file the index doesn't account for (unreadable, or valid but unlisted) is never deleted: it is moved once to `quarantine/`, named by when it came there (time, then a sequence for the same moment), and the newest 100 so named are kept (the oldest by that time go, whatever their ids; other files there are left alone) and said, and an entry whose file is gone is dropped. A damaged index (not JSON, not an index, over 512 KB, an entry invalid or repeated, too many entries) is never acted on: it is set aside as `index.damaged-<time>.json` (the newest 10 kept) and rebuilt by adopting every valid kept file with what the old index still said about it (pin, when kept); invalid files and valid ones past the limit go to quarantine, so the rebuilt index accounts for every file and is stable afterwards; the page says it was recovered. An index that can't be read for another reason (permissions, I/O) is an error and nothing is written. A kept file whose scope doesn't match its index entry is refused. Comparable only when they measured the same thing: the same kind and scope; for benchmarks the same fixtures version, provider, fake or model, and for model trials the same model, effort and mode (CLI versions differ: a note); for exports the same filters and some recorded time on both. Otherwise **Not comparable**, with why, numbers shown. Benchmarks compare scenario by scenario on usable samples: completed, correctness known (a sample whose checks all skipped is unknown, never passed) and not stale (left-out ones said). Each measure has mean, min, max and n, the change and whether it is within the spread; a measure some sample didn't measure is **unknown** (no zero-filled totals: context and guidance exist only when every part is known) and isn't compared. Correctness first, check by check, the check list being authoritative (its counts are used; summary counts that disagree with it, a check listed twice, an entry that isn't a check, or more checks than can be read leave the sample's correctness unknown, and any failed check in it fails the sample): a check that passed or ran less often, or failed more often (one the baseline never had included), in the run is a regression (a fake's declared skips are skipped on both sides, so they aren't), shown with its counts and the run's failed checks; a regression is *smaller but failing* (less context) or *worse*. Otherwise more failed calls, tool errors, API failures or cancellations, more calls or retries, or more than 1% more context is *worse*; less context is *better*, else *same*; a scenario with a partial measurement (recording off or unknown, measurements dropped or missing) or an unknown failure measure is *incomplete*, not judged on size. Comparable also needs both runs' sources unchanged while they ran. Provider usage only between model trials (a fake's is simulated: said), only when every usable sample on both sides reported that field (unknown stays unknown, a resumed session's is the conversation's), cost only when both have one (≈ said when Hive estimated it), reasoning its own row. The skill revisions each session was given are compared, and a difference (an edited skill) said. The page shows each side's provenance; while comparing it hides the live range and filters, which only shape **Keep current view**. Exports compare per hour recorded (guidance per launch as is), noting partial data and that real use isn't a controlled workload. A total that any damaged piece of the export adds to (a series that is missing, isn't a list, is too long to read, or has an invalid number) is unknown, said, and not compared; never zero. A late answer for another pair or scope is never shown.
- **Scenario benchmarks** (`tests/scenarios`, developer tooling): each run writes `benchmark.json` with every scenario's samples: each check (passed, failed, skipped), failed checks, incomplete with a path-free reason, stale guidance, resumed, the guidance and skill revisions the session was given, the measurement's coverage (recording, dropped, what made it partial), and measures: Hive's metrics before the launch and after the turn, the harness's own requests left out (context in parts with bytes and characters, tool replies, calls and repeated calls, failures, API traffic, delivered and undelivered skills, skill service work, time, and the session's provider usage as reported: a field it didn't report is left out). Fixtures v5 adds controlled pairs: **list-compact** / **list-detail** (the same cards, the compact list against the explicit detail form, the same required correctness) and **skill-unchanged** / **skill-changed** (a skill edited inside the measured window, `beforeLaunch`). Both fake providers act the scenarios out (`fake`, `fake-codex`); model trials are opt-in and record their model, setup and authorization. Model trials keep to `--budget` (a finite amount above 0): a trial that reports no cost makes the spend unknown, so no further trial starts unless `--allow-unknown-cost` is given, and the spend is the reported subtotal plus the unpriced trials, unknown in all (never $0). `--repeat N` (default 1), `--save-baseline NAME` (the new one read first and swapped in atomically; the older one archived under a name of its own, never overwritten, also when saved twice in a second; 5 kept), each run in a results folder of its own, the newest 30 kept.
- **Not measured**, and said in every report (`notMeasured`): provider tokens per tool or guidance part, provider network traffic (Hive isn't a proxy), context a CLI adds itself, whether a model read a skill, and HTTP headers.

## 10. Provider framework

A provider is two pieces:

- **Descriptor** (`src/shared/providers.ts`, static data both processes use): id, product and company names, icon, permission modes (with danger flags and labels), effort levels, model groups, capabilities (fixed session IDs, live mode switch by cycle or menu, Plan toggle, prompt-cache TTL, reports cost, compact focus, 200K context limit, image paste), terminal keys the CLI reserves, instructions file and import line, setup notes.
- **Adapter** (`src/main/providers/<id>/`, `ProviderAdapter`): locate the CLI and check readiness (login, sandbox), setup tasks, launch (`prepareLaunch`, `buildCommand`), hook normalisation and file-lock replies, live details (status line or transcript tail), mode-switch keys, transcripts (path, restore, list, usage, conversation parser, images, export), memory sources, allowed files and skill folders, the project's own MCP servers.

**Models and capabilities from the CLIs** (#125). The CLI is the source of truth wherever it can say; where it can't, the lists are manual (never scraped or fetched) and every one is editable in Settings, so nobody waits for a Hive release.
- **Where they come from.** An adapter's `listModels` asks the installed CLI for its models and what each can do, at start and on every refresh (Check now, a changed CLI path), with a timeout, never blocking start. Claude Code: the Agent SDK's `initialize` control request (`claude -p --input-format stream-json --output-format stream-json --verbose --no-session-persistence --strict-mcp-config` in a folder of Hive's own, in the sessions' environment), which sends no prompt and uses no tokens; the CLI is closed as soon as it answers. Only `models` (and `unavailable_models`) is read: `account` and the reply's other personal fields are never read, logged or stored. Each model gives its value, resolved id, name, `supportedEffortLevels` and `supportsAutoMode`; the pickers (and the Agent API's model list) show an alias with the model it stands for, "Opus (Opus 5.5)" (#248), a pinned version as the CLI names it; the `default` entry isn't offered (it is "Claude Code default") and its resolved model is the CLI's default model. Codex: `codex debug models` (hidden models left out; `supported_reasoning_levels`, `default_reasoning_level`). The replies are the CLIs' protocols, not documented commands, so they are read defensively: unknown fields ignored, a missing or odd field falls back for that field, a reply without models is a failure (logged without personal data). Per-model flags are trusted only when the reply uses them at all: then a Claude model without effort levels has none (Haiku), and one without `supportsAutoMode` no Auto. Contract tests run against recorded replies in `tests/fixtures` (personal fields removed), which the fake CLIs answer with too.
- **Cache.** The last good catalog per provider is kept in config.json (`modelCatalogs`), keyed by the CLI version, so pickers fill at once on start while the fresh read runs ("as it last said; asking again"); a different version's is not used. Only the latest refresh's answer is kept.
- **Pickers.** Models: the CLI's (unavailable ones shown, not offered), else the fallback. Effort pickers (global, project, agent, Assistant) offer the levels of the model that would run (`models.ts` `modelCaps`); without the CLI's word, the effort fallback. A saved effort the model doesn't take stays chosen and is shown as such ("Extra high (not offered with Opus 4.6)", with a warning), never changed behind the user's back. A model without effort (Haiku) says so.
- **Default effort.** The footer and the pickers' Inherit option show the model's own default when nothing is set or reported: "Medium (default)". It is the CLI's config (Codex's `model_reasoning_effort`), else its catalog (Codex's `default_reasoning_level`), else the effort a session started without one reported for that model (Claude Code's status line; `observedDefaultEffort`, the newest 50 models per provider). Unknown: nothing shown, as before.
- **Fallbacks in Settings → each provider:** **Models (fallback)**, used only when the CLI can't be asked (not installed, too old, an unexpected reply), with where the models come from now ("From Claude Code 2.1.289", "Fallback (Claude Code couldn't be asked)"); **Effort levels (fallback)**, used when the CLI doesn't report a model's own (its names also name the CLI's levels, in the pickers and the agent's footer alike); and the prices (§9). Each can be edited (add, remove, rename; models marked Older) and has **Reset to defaults**. The lists are folded while the CLI's answer is in use and they are Hive's own. Defaults stay in code (the descriptor's `modelGroups` and `effortLevels`, `SHIPPED_PRICES`); only an edited list is stored (`modelFallback`, `effortFallback`), so improved shipped defaults reach users who never edited them.

The registry (`src/main/providers/index.ts`) lists the adapters; the rest of Hive (sessions, Overview, settings pages, status bar, Agent Setup, Sessions tab) works from descriptors and adapters without naming a provider. Adding a provider means a descriptor, an adapter, an icon and a price table. Skills and MCP are stored in a Hive-neutral form; adapters translate them at launch.

## 11. Provider installation and updates

The same rules apply to every provider's CLI; the details below are Claude Code's. Codex: installed with OpenAI's installer (`irm https://chatgpt.com/codex/install.ps1 | iex`) into `%LOCALAPPDATA%\Programs\OpenAI\Codex`, signed in with a ChatGPT plan or an API key, plus the one-time sandbox setup (§6.4). **Agent Setup** (Help menu) has a tab per provider with its install, sign-in, sandbox and update steps, and the readiness banner links to it for enabled providers that need something.

- Not bundled (proprietary; redistribution would need Anthropic's permission).
- **The standalone CLI is required** (Claude Code and Codex alike). Copies bundled with editor extensions (VS Code, Cursor, Windsurf) are never used, even if set manually: they move on every extension update and can't be updated with `claude update`. If only an extension is present, the setup dialog explains that the CLI is still needed.
- Discovery: settings path → `PATH` → `~/.local/bin/claude.exe` → npm global.
- **`.cmd` launchers** (npm's `codex.cmd`, say) aren't run through cmd.exe when Hive can tell what they run: a Node CLI's launcher that does nothing else, matched whole (npm's cmd-shim template, with its `node.exe` beside it or `node` on PATH, or the bare one-line `@node "%~dp0cli.js" %*`), is started as that node and script directly; one that sets anything, adds its own arguments or Node flags, or runs another interpreter is not, since a direct start would leave that out (`shimTarget` in `providers/common.ts`), so its command line can be as long as an .exe's (32,767 characters) and the first task and session name are passed as they are. cmd.exe takes at most 8,191 characters, less than the Hive Assistant's Codex launch (its hooks, instructions and hive server, about 9.5K). Any other `.cmd`/`.bat` still goes through cmd.exe, with its first task and name flattened to one plain line, and a launch too long for it is refused before it starts, saying to point Settings at the CLI's `.exe`.
- Not found → first-run dialog offers a one-click install using Anthropic's official installer, run in a visible terminal.
- On launch (if enabled): read `claude --version`, compare with the latest published version, offer **Update** (`claude update`) in a visible terminal. Never updates while sessions are live.
- Auth is handled by each CLI itself. Hive never touches credentials, and never edits a CLI's own config files.

### 11.1 Hive's own updates

- **electron-updater** against GitHub Releases of `Suremise/hive-desktop` (`publish:` in `electron-builder.yml`). It reads `latest.yml`, downloads the NSIS installer (differentially when a `.blockmap` is available) and checks its SHA-512 before installing. ## 12. Agent API

Local HTTP API on `127.0.0.1:<port>` (default 47821), bearer-token auth. The workspace token is in `%APPDATA%/Hive/agent-api.json` (Settings → Agent API) for scripts; each agent launch gets a token of its own instead (`agent-api/<hash>.json` in the profile, passed as `HIVE_API_TOKEN`, ended when the agent stops), from which the API knows the calling agent and its project, and the Assistant has its own per launch. Errors use 400 (bad input), 401, 403 (not allowed, e.g. an agent asking for another project's cards), 404, 409 (conflicts with the current state) and 500 (unexpected). Endpoints under `/v1` for app status (with the API's version, who the caller is to Hive and the guidance and skill revisions), workspace, projects, sessions, usage, shared notes, the task board, skills (a lean listing; one Hive skill's files, paths checked whole and inside its folder), MCP, notifications, progress (long runs for the Progress panel, §13), a server-sent events stream and `/v1/docs/agent-api` (the running version's own reference). A project agent lists only its own project's skills; a project's listing leaves out the Hive skills for the Assistant alone, as its Skills tab does. An agent's activity is clipped (prompt and reply to 300 and 500 characters, the last 3 tool calls; with detail 2,000, 3,000 and 10) and says what it cut (`clipped`, `toolCalls`). Full reference: `docs/AGENT_API.md`.

Step lines `##hive-progress step=N total=M name=…` (N the step starting, from 1) are taken out of the output and reported (`step` N−1 finished, `stepName`); the run starts at the first step line with a total, or after 2 s; a run started without one sends the first total printed later once (`PATCH`, #145), and later totals are ignored. Silent and harmless outside Hive, unreachable, refused, or `HIVE_PROGRESS=0`. **Agents use it unasked** for commands and background tasks likely to take over 30 s: the session contract (`progressRule` in `shared/hiveGuidance.ts`) says so while **Settings → General → Agents show long commands in the Progress panel** (`general.progressCommands`, on by default) and the Progress panel are both on, and otherwise to use it only when the user asks; the setting is greyed out while the panel is off (#167). The hive MCP server gets the choice as `HIVE_PROGRESS_COMMANDS`, Codex the same text in its developer instructions; it applies to sessions started afterwards. The command gets `HIVE_PROGRESS_WRAPPED=1`: a reporter inside it (another `hive-progress`, Hive's own runners) then reports no run of its own (`progressTarget` is null) and Hive's runners print step lines for the wrapper's run instead, so a wrapped `npm test` is one row (its total, printed once Vitest has found the files, comes late if that takes over 2 s). Hive's own runners report through `tests/progressReport.mts`: `npm run e2e` a step per suite with per-suite estimates (`%LOCALAPPDATA%/hive-test/progress-timings.json`; `--no-progress`), `npm test` a Vitest reporter added to Vitest's own reporters, a step per file; output unchanged; the e2e runner and the scenario harness give the suites, their test Hives and the wrappers they start only an allowlisted environment (`tests/e2e/runContext.cjs`), so no session or wrapper variable (`HIVE_*`, `HIVE_PROGRESS_WRAPPED`) reaches them (#202, #203).

## 14. Tray, notifications and sound

- Close and minimise go to the tray (each configurable). Quit via tray or File → Exit.
- **Quitting** stops all sessions (they stay resumable). Setting *Confirm before quitting*: **When an agent is working** (default; working, waiting on a prompt, or waiting on background tasks), **Whenever sessions are running**, or **Never** (the earlier on/off setting migrates to working/never). The confirmation is an in-app dialog (the window is shown first) listing each session with its status, marking the ones that would be interrupted, with *Don't ask again* (about sessions), *Cancel*, *Quit when agents finish* (only when an agent is working) and *Quit now*. Files with unsaved edits in the Files tab are listed at the top and always make Hive ask, whatever the setting, with the choice to save or discard them (the buttons read *Save and quit…* when saving). No native message boxes.
- **Quit when agents finish**: Hive hides, the tray tooltip and menu show the pending quit (*Quit Now*, *Cancel Pending Quit*), a banner shows it if the window is opened, and Hive quits as soon as no agent is working or waiting on background tasks.
- Quitting without a dialog (or after waiting) shows a notification that the stopped sessions can be resumed. Shutdown waits up to 3 s for each session's final transcript backup.
- **Sleep** (`main/power.ts`, `shared/keepAwake.ts`): while any agent in any window (the Assistant too) is **working** or **waiting on background tasks**, Hive holds `powerSaveBlocker.start('prevent-app-suspension')` (the screen may still turn off and lock) and releases it as soon as none is. **Settings → General → Keep the PC awake while agents work**: *When plugged in* (default; not on battery, `powerMonitor.isOnBatteryPower()`, re-checked on `on-ac` / `on-battery`), *Always, on battery too*, or *Never*. While it's held the status bar shows **Keeping the PC awake: n agents working** (click: Settings → General).
- **Windows shutting down** (shutdown, restart or sign-out): Windows' callbacks (a window's `query-session-end`, then `session-end`; `powerMonitor` `shutdown` elsewhere) don't wait for anything asynchronous, so Hive backs up every running session's transcript before the callback returns: the transcript's bytes only (appended to the backup, or copied whole), no reading of usage or cost. It has 2 s at `query-session-end` and 1 s at `session-end` (which catches up with what was written since), well inside the ~5 s after which Windows offers to end an app, and never cancels the shutdown. It copies 1 MB at a time and starts nothing once its time is up; a step under way can't be cut short, so it can run over by about one disk write. Out of time, a whole copy is dropped (the backup stays as it was) and an append stops where it got to (a shorter backup that is still the transcript's start); sessions after it aren't tried. Every window gets these notices: one save covers them all. A shutdown another app cancels leaves nothing to undo. Best effort: a session whose transcript Hive hasn't found yet keeps its last ordinary backup, and the log counts what was saved, incomplete, not tried or failed. An ordinary backup under way at the time doesn't undo it: appends write each byte at its own offset, and a whole copy is put in place only if the backup hasn't changed since it began, checked and renamed in one synchronous step (retries too), so no rename is left pending across the shutdown copy.
- **Waking up** (`powerMonitor` `resume`): each running session's transcript is read again (usage, background tasks and their time limit, plan usage from it) and its state reported; the workspaces refresh. Logged.

The menu lists them under **Need you (n)**, then **To review (n)**, across every window, oldest first, up to 10 each (then *and n more*); an item opens its agent in the window showing its workspace (`agent.show`). Below them, active projects with their status.
- **Notices** for waiting/finished: an **in-app banner** while any Hive window is focused, a native Windows notification otherwise (`shared/bursts.ts` `noticeRoute()`, unit-tested). Rule: notifications off, or that kind off → nothing; no Hive window focused (visible, not minimised) → Windows notification; a Hive window focused → per **While Hive is focused** (`whileFocused`): *Show in Hive* (default; a banner in the focused window), *Show nothing*, or *Windows notification*. Banners only for what **Show banners for** (`bannerScope`) covers: *All workspaces* (default), *This workspace* (the focused window's), *This project* (the one it shows: the page reports it, `window:showing`); a notice left out shows nothing (no banner, no Windows notification) but still counts in its window's inbox and taskbar. A notice about no project (plan usage) passes every scope. Banners (`components/NoticeBanners.tsx`, sent with `emitTo` as a `notice` event): **Banner position** (`bannerPosition`, six places, top centre by default; several stack, the newest nearest the edge, at most four); a finished banner (or another notice) closes after **`bannerSeconds`** (6), kept while hovered or holding the keyboard focus; a waiting one stays until clicked, dismissed (×) or answered (`main/notices.ts` tells every window `notice-resolved` once the agent no longer asks or its session ends), unless **`waitingBannerStays`** is off. For the keyboard, a banner about a project has its text as a button ("Show the project: <title>"; the banner keeps its live `status`/`alert` role) and × as a second one. Clicking a banner (`notice:open`) brings up the window showing its project and the project, as a Windows notification's click does. Agent notices are already in the attention inbox (waiting, and finished-unseen), so banners need no history of their own. Plan usage keeps its toast (the bell's history) and adds a Windows notification only when routed there; the "Hive has closed" quit notice stays a Windows notification (its windows are closing). `onlyWhenUnfocused` is gone: config version 6 moves every profile to *Show in Hive* once. **Bursts** (`shared/bursts.ts`): finishes are collected and told together once none has come for 3 s (at most 10 s after the first): one alone reads as before ("hive · Claude finished" and its last message); several in one project "3 agents finished in hive" naming them ("Claude, Codex, Agent 3"); across projects "3 agents finished" with "hive (2), web (1)". When the group is shown, each finish is checked again (`noticeRoute()`, the same check as when it came): one turned off meanwhile, or left out by the banner scope, is left out, and nothing is shown if none is left; the rest go as one banner in the focused window, or one Windows notification, as things are then. Clicking it shows the (first remaining) project. **Waiting for input** is never grouped or delayed: it is told at once, on its own, with its chime, once per need: when the agent starts waiting, or a pending question appears while it isn't (*<agent> has a question for you*). A wait that turns out to be a question already told, or the same prompt reported again, isn't told twice. The rules are in `main/hookStatus.ts` (pure, unit-tested per provider), which learns who is asked from the CLI's hooks or, for Codex, its title (§6.4); each change of whether an agent needs you is logged at debug level with its cause (a hook's name or the title), never what was asked. Warnings (`notice`) are unchanged.
- Chime synthesised in-app (several styles, volume), global on/off with per-project override. A window plays at most one chime every 2 seconds, so agents finishing together chime once.

## 15. Resolved decisions

1. `<Workspace>/.hive/` is committed.
2. Archived transcripts are preserved until the user deletes the session. Non-archived sessions are backed up too.
3. Skills/MCP must be deployed to the workspace before a project can use them. Project-only MCP servers are disabled until copied.
4. Permission mode: global default Auto (Manual until 0.1.0 development), per-project and per-agent override, bypass behind an opt-in setting.
5. Machine and Local skills are always on and read-only in Hive.
6. The standalone Claude Code CLI is mandatory; editor-extension copies are not supported.
7. Pasted and dropped images are saved in the project's `.hive/images` (by session) and passed to the agent as paths, so each image is kept and tied to the point in the transcript where it was sent.
8. Deleting from the Files and Images tabs moves items to the Recycle Bin; Hive never deletes project files permanently. Images are never removed automatically.
9. Transcripts are read-only in Hive: the Sessions tab shows and exports them but never edits them. Claude Code owns the file and only ever appends to it.
10. Up to twelve agents per project (a page holding as many as the layout has panes), each in the project folder or its own Hive-managed git worktree (Hive creates, merges and removes worktrees itself rather than using Claude Code's `--worktree`, because the worktree must outlive sessions).
11. Agents sharing a folder are protected by Hive-enforced per-file locks (Block by default). Concurrent changes to shared config and memory are a documented risk, not prevented.
12. Worktrees live next to the workspace (`<Workspace>.worktrees/<Project>/<agent>`). New worktrees get `.env*` copied by default and an optional per-project setup command. Merging defaults to a merge commit (`--no-ff`), and the worktree, branch and agent are kept unless **Remove** is ticked, so one agent can merge task after task; a squash that keeps the worktree moves the branch to the merged branch afterwards (ticked by default).
13. Hive is open source under the **MIT License** (`LICENSE`, © 2026 Darren Marshall). Everything it ships is under permissive licences (mostly MIT and ISC; DOMPurify MPL-2.0 or Apache-2.0; codicons CC-BY-4.0; sax BlueOak-1.0.0; argparse Python-2.0); `THIRD_PARTY_NOTICES.md` lists them with full texts and is regenerated by `scripts/licenses.mjs` on every build. Electron's and Chromium's licences ship in the install folder (electron-builder adds `LICENSE.electron.txt` and `LICENSES.chromium.html`).
14. Hive updates itself from GitHub Releases with electron-updater: checked and downloaded automatically by default, installed only when Hive quits or with Restart and Update (or only manually, by setting), never while it runs.
15. The permission mode of a running session is switched live (Shift+Tab driven by Hive, confirmed from the footer), not by restarting; settings changes are offered to running agents, never forced.
16. Every command's shortcut is configurable globally, and project and session commands per project.
17. Providers: Claude Code and Codex, chosen per agent, so a project can mix them; each CLI's own terminal UI is shown (Hive doesn't draw conversations). The framework is built for more providers.
18. Workspace skills and MCP servers are shared by every provider; user-level MCP servers load for none, and a project's own servers follow the same rule for each CLI.
19. Fresh installs start with every provider disabled; upgrades from 0.1 keep Claude Code enabled. No enabled provider is a valid state.
20. Codex defaults to Approve for me; Full access is opt-in like Bypass. Hive drives Codex's `/permissions` menu for live changes.
21. Cost for providers that don't report it is estimated from a shipped, user-editable price table and always marked as an estimate.
22. Conversations never move between providers; **Hand Over to…** moves work through a handover. Projects that mix providers can share one `AGENTS.md`, imported by `CLAUDE.md`.
23. Agents are all equal and a project starts with none; the provider is stored on each agent. Upgrading from 0.1 clears existing agents (their sessions stay).
24. Hive keeps a last good copy of its own JSON files and never silently replaces a damaged one.
