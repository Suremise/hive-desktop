# Hive Architecture

This document explains how Hive is put together, for anyone changing the code. Product decisions live in [SPEC.md](SPEC.md).

## Processes

```
┌──────────────────────────── Electron main process ───────────────────────────┐
│ index.ts        app lifecycle, window, quit flow, settings side-effects      │
│ workspace.ts    open workspace, .hive folders, project list, git exclude     │
│ sessions.ts     launch/stop sessions, status from hooks, backups, usage      │
│ providers/      ProviderAdapter registry; claude/ and codex/ adapters        │
│ providerService.ts  each provider's install info, setup tasks                │
│ ptyHost.ts      node-pty processes, output buffers                           │
│ servers.ts      hook server (random port) + Agent API (configured port)      │
│ skills.ts mcp.ts notes.ts git.ts files.ts   feature services                 │
│ ipc.ts          typed IPC handlers        tray.ts   system tray              │
│ updater.ts      Hive's own updates (electron-updater, GitHub Releases)       │
└──────────────┬───────────────────────────────────────────────▲──────────────┘
               │ IPC (preload bridge: window.hive)              │ HTTP hooks
┌──────────────▼───────────────┐                  ┌────────────┴─────────────┐
│ Renderer (React + zustand)   │                  │ claude / codex CLIs      │
│ xterm.js terminals, Monaco   │◄── pty output ───│ one per running session  │
└──────────────────────────────┘                  │  └─ hive MCP server ─────┼──► Agent API
                                                  └──────────────────────────┘
```

- The **renderer** never touches the filesystem or processes. Every request goes through `window.hive.invoke(channel, …)`; channels and their types are declared once in `src/shared/api.ts` (`HiveRequests`) and implemented in `src/main/ipc.ts`, so both sides are type-checked against the same contract.
- **Events** flow the other way through `emit()` in `src/main/events.ts` (`HiveEvent` in `src/shared/types.ts`). The Agent API's SSE stream subscribes to the same events.
- **Several windows** (`windows.ts`): each `BrowserWindow` has its own `WorkspaceService` (`createWorkspaceService()` in `workspace.ts`). The `workspace` everyone imports is a stand-in: a method given a project or worktree path goes to the workspace owning it (`workspaceFor()`), anything else to the workspace of the current work, set with `inWorkspace()` (AsyncLocalStorage) by `registerIpc` (the calling window's), the Agent API (the request's: `X-Hive-Workspace`, `?workspace=`, or the only one open) and `sessions.effective()`; without one, the last focused window's (logged once, as it means a call site forgot to say). Background work that knows its project uses `workspaceOf(projectPath)`. `emit()` asks the router in `windows.ts` where an event goes: a project's to the window showing it, a workspace's to its window (or the calling one), app-wide ones to all; `emitTo(win, …)` targets one. Terminal output goes by the pty key (`session:<project>#<agent>` to its window, task terminals to all). Quitting and closing a window (`index.ts`) ask in the window concerned (`HiveWindow.question`); each window reports its own unsaved files.
- **File system access** in main goes through Electron's `original-fs` (`original-fs/promises`), never `fs`: Electron's `fs` opens an `.asar` it stats or reads as an archive and keeps it open until Hive quits, so a project's build output (`dist/win-unpacked/resources/app.asar`) couldn't be replaced (#246). oxlint's `no-restricted-imports` holds `src/main` to it, except `hive-mcp.js` and `hive-progress.js` (plain Node); unit tests alias it to `fs` (`vitest.config.ts`), so `vi.mock('fs')` still reaches main's modules. Dependencies use Electron's `fs`, so chokidar (which stats everything it lists) watches only `.hive`; the workspace root has a plain `fs.watch` whose `rename` events refresh the project list. Electron's own readers that take a path are asar-aware too (`nativeImage.createFromPath`, `net.fetch` of a `file:` URL), so `hive-img:` streams the file through `original-fs` (#261), `images:copy` decodes the bytes it read (`createFromBuffer`), and a path inside an `.asar` archive is refused by `guardFile` (every file IPC route) and `hive-img:` (`insideArchive()` in `fsutil.ts`: a folder of the path named `*.asar` that `original-fs` finds is a file; a real folder named `art.asar` is just a folder, #261). `tests/e2e/asarfiles.cjs` checks a project's `.asar` files can be deleted while Hive runs.
- **Files tab** operations live in `files.ts`; every path is resolved against the project and refused if it escapes it. Deletes use `shell.trashItem`. While a Files or Images tab is open, a reference-counted recursive `fs.watch` sends `files-changed` events with the changed folders (not forwarded to the Agent API).
- **Unsaved edits** (drafts) live in a module-level map in `FileView.tsx`, keyed by absolute path, with the root and relative path for saving. The Files tab calls `moveDrafts()` after renames and moves and `discardDrafts()` after deletes; `saveAllDrafts()` saves them all, refusing conflicts. Every change of the set is reported to main (`files:setUnsaved`), which makes `requestQuit()` ask and sends the list with `quit-request`; the quit dialog saves or discards before answering. `actions.saveUnsavedFirst()` guards Reload Window and workspace switches. The other editors (`DocEditor` for notes, skills, instruction and memory files; the MCP view) keep theirs in `editorDrafts.ts`, each with its own save function; `unsavedFiles()`, `saveAllDrafts()` and `discardDrafts()` include them. Their saves pass the text as loaded (`file:write`/`mcp:save` `expected`), and main's `writeTextUnlessChanged()` answers CONFLICT if the file has changed since.
- **Writes that repeat**: plan usage from the status line is kept in memory and saved only when a shown value changes, at most once a minute (`planUsage.ts`); transcript backups run at most once a minute during a turn, plus at `Stop` and exit (`BACKUP_INTERVAL_MS` in `sessions.ts`), and append only what the transcript gained (`syncCopy` in `fsutil.ts`).
- **File editor**: `components/FileView.tsx` holds the previewer registry (`PREVIEWERS`: match by file name, whether it needs the text, whether it is editable, default view). `files:read`/`files:write` in `files.ts` do the I/O; writes pass the modified time they started from and fail with `CONFLICT` if the file changed. `CodeEditor` ignores values it emitted itself, so React lagging behind fast typing can't overwrite newer keystrokes.
- **Images** are shown through the privileged `hive-img:` protocol (`hive-img://img/<encoded path>`), which only serves image and PDF files inside the workspace; the CSP allows it in `img-src` and `frame-src`. `webPreferences.plugins` is on for Chromium's PDF viewer.
- **Hive's own files**: `writeJsonAtomic`/`writeTextAtomic` (`fsutil.ts`) write a uniquely named temp file and rename it (retrying briefly while Windows holds the target). Changes that read a file and write it back go through `withFileLock`: use `workspace.mutateProjectConfig()` / `updateAgent()` for `project.json` and `workspace.mutateSessions()` / `upsertSession()` for `sessions.json`, never read-then-`updateProjectConfig` with a value computed outside the lock (one provider's project settings: `project:updateProvider`, which merges under the lock). The files Hive keeps are read with `readKeptJson()` and written with `writeKeptJson()`, which also writes `<file>.bak`; an unreadable file is set aside (`<file>.corrupt-<time>`), the `.bak` restored and `onCorruptFile` (a notification, set up in `index.ts`; startup reports wait for the window) told.
- **IPC** is accepted only from a Hive window's top-level frame (`registerIpc`), provider ids are checked (`knownProvider`), and `index.ts` refuses every permission request except the clipboard's. A build's CSP drops the dev server's `ws:`/`localhost` (`hive-production-csp` in `electron.vite.config.ts`).
- **File IPC** (`file:read`, `file:write`, open/reveal): paths must be in the workspace or its worktrees (checked by their real location too: `insideReal()` in `fsutil.ts`, also used by `hive-img:` and shared notes), or be one of the provider files Hive shows (each adapter's `fileAllowed()`: Claude Code's user `CLAUDE.md` and auto memory, Codex's user `AGENTS.md`, read-only `SKILL.md`).
- **Session IDs** are validated with `assertSessionId()` (`shared/defaults.ts`) wherever they reach a path: `sessions.start/usage/archive/rename/adopt`, `backupPath`, each adapter's `transcriptPath`, the transcript viewer.
- **Pty output** goes over its own `pty:data` channel for throughput. The main process keeps the last 512 KB per pty so a reloaded window can replay it.

## Providers

A provider is a **descriptor** (`src/shared/providers.ts`, plus `shared/claude.ts` and `shared/codex.ts`; static data used by both processes: names, icon, permission modes, efforts, models, capabilities, reserved terminal keys, instructions file) and an **adapter** (`src/main/providers/<id>/adapter.ts`, `ProviderAdapter` in `providers/types.ts`). `providers/index.ts` is the registry (`allProviders()`, `providerAdapter(id)`). Shared helpers resolve settings: `providerSettings`, `projectProviderConfig`, `agentProvider` (agent → project default → global default), `agentLaunchSettings` (model, effort and an allowed mode), `isProviderEnabled`. The UI reads descriptors and never switches on a provider id; capabilities (`liveModeSwitch: 'cycle' | 'menu'`, `planModeToggle`, `reportsCost`, `promptCacheTtl`, `compactFocus`, `imagePaste`…) turn features on and off.

**Models and capabilities** (#125): each adapter's `listModels(executable, env)` asks the CLI (Claude Code: the `initialize` control request, `providers/claude/models.ts`; Codex: `codex debug models`, `providers/codex/models.ts`), parsed defensively into `CatalogModel`s (value, name, resolved id, effort levels, default effort, Auto). `providerService.refreshOne()` keeps the answer in `AgentInstallInfo.catalog` and caches the last good one per CLI version in config.json (`modelCatalogs`); `configuredDefaultEffort()` and `observeDefaultEffort()` (fed by `sessions.applyDetails()` for sessions launched without an effort) give each model's default effort. `shared/models.ts` is the one place that resolves them for the pickers, the footer and the Agent API: `modelGroups()` (the catalog, else the fallback: the user's `modelFallback` or the descriptor's groups), `modelCaps()` (a model's effort levels and default, and `supportsAuto` for `modeCaveat`), `fallbackEfforts()`, `effortText()`. `config.setProviderFallback()` stores only an edited list; `null` resets it.

Adding a provider: a descriptor added to `PROVIDERS`, an adapter added to the registry, an icon in `renderer/src/assets/providers/`, prices in `shared/prices.ts`, a `migrate…` step if settings change shape, and tests. Nothing else should need to change; if it does, move that knowledge into the descriptor or adapter.

- **Settings**: `AppSettings.providers[id]` (`ProviderSettings`) and `defaultProvider`; `ProjectConfig.providers[id]` and `defaultProvider`. `migrateConfig()`/`migrateProjectConfig()` in `shared/defaults.ts` read 0.1 files; `withLegacySettings()`/`withLegacyProjectFields()` keep writing the 0.1 fields, and `config.ts` backs the 0.1 file up once.
- **Runs**: each launch gets a `runId` (`LiveSessionState.runId`, `sessions.runs`). Hook and status-line URLs carry `?run=<runId>`, so `findLaunch()` finds the agent even before a provider reports its session id (Codex does so with the first prompt; `recordSession()` then writes the record, including `transcriptPath`).
- **Hooks**: `adapter.normalizeHook()` turns each CLI's JSON into a `NormalizedHook` (session id, transcript path, mode, and an event of kind start / prompt / toolStart / toolEnd / needsInput / stop / signIn / interrupt / compactStart / compactEnd / end; signIn is a turn its CLI refused for the sign-in, which Codex says only in its rollout, `LiveDetails.signIn`); `handleHook()` only sees those, and asks `hookStep()` (`main/hookStatus.ts`, pure and unit-tested per provider) what each one does to the status and which actions to take (notify, release locks, record the turn, compaction). A compaction Hive asked for is a `Compaction` (`main/compaction.ts`), reserved while its `/compact` is typed: its time limits (from the submission) and the transcript and terminal signs that end it when no `PostCompact` comes; however it ends, `compactionOver()` decides the status. An exit before the session started is a failed start or a plain stop by `failedStart()` (`shared/startFailure.ts`). `adapter.lockReply()` shapes the file-lock answer.
- **Live details**: Claude Code posts its status line (`handleStatusLine`: model, effort, cost, context window — `usage()` adds the window to a running Claude session's usage); Codex's model, effort, context window, plan limits, preset and Plan mode come from the rollout tail (`readDetails()` → `adapter.transcriptDetails()`, from `detailsOffset`). Both end in `applyDetails()` and `reportPlanUsage(provider, usage)`.
- **Background tasks**: `readBackground()` reads what the transcript gained (from `tasksOffset`) through `adapter.backgroundTasks()` (`providers/claude/background.ts`, `providers/codex/background.ts`) into the launch's `tasks` map, ignoring lines from before the launch. `settleBackground()` drops expired tasks and those past `agents.backgroundTaskMinutes`, sets `backgroundTasks` in the live state and, for providers with `capabilities.backgroundWakes`, moves the agent between `background`, `working` (a task ended, so the CLI starts a turn) and `finished`. A Stop reads the transcript first (`refreshBackground()`) and leaves `background` instead of `finished` while tasks are open (`idleStatus()`), without the finished notification.
- **Mode switching**: `liveModeSwitch: 'cycle'` sends Shift+Tab until the footer (`adapter.footerMode`) shows the target (Claude Code); `'menu'` types the adapter's `modeMenuKeys()` (Codex: Ctrl+U, `/permissions`, arrows, Enter). `setPlanMode()` sends `planToggleKey`.
- **Readiness and setup**: `adapter.readiness()` returns `ReadinessIssue`s (not installed, signed out, sandbox) with a task; `providerService.runProviderTask()` runs install/login/update/setup in a visible terminal, typing `CommandSpec.keys` once `readyPattern` shows (Codex's sandbox setup, through `/permissions`). `KeyGate` (`taskKeys.ts`) decides when: it matches `readyPattern` against the screen the output draws (a `TerminalScreen`, so a word changed in place or output split anywhere is read right) and follows `busyTitle` in the window title; the keys wait until it has been ready and not busy for a second, and each key until it has been idle for half a second.
- **Cost**: `shared/prices.ts` (`SHIPPED_PRICES`, `modelPrice()`, `estimateCost()`) prices sessions without a reported cost; user prices (`ProviderSettings.prices`) win, and shipped ones the user removed (`pricesRemoved`) aren't used. `usageFor()` fills `costUsd`/`costEstimated`, and price changes clear the usage cache.

### Codex

`providers/codex/adapter.ts` launches `codex [resume <id>] --no-daemon` with `-c` overrides only (it never writes Codex's config): hooks and their trust records (`hookOverrides()`, `hookHash()`: sha256 of the sorted-key JSON of the hook identity, checked once per Codex version against the app server's `hooks/list`), model and effort, the preset flags (`CODEX_MODE_FLAGS`), `developer_instructions` (the hive MCP server's instructions, `shared/hiveGuidance.ts`), `mcp_servers.<name>` tables (`codexMcpServer()`) and `.enabled=false` for the user's and the project's own servers. Skills are copied to `<cwd>/.agents/skills/hive-*` (`syncSkills()`), excluded from git; each copy has a `.hive-copy` marker with the source hash, so only Hive's copies are replaced or removed and unchanged ones aren't copied again; a changed one is swapped in whole (`replaceDir()` in `fsutil.ts`). Live preset switches type `/permissions` and the preset's number (`modeMenuKeys`); `sessions.setPermissionMode()` shows `modeSwitching` until `modeFromOutput()` reads Codex's confirmation or the rollout's settings say so. `listModels()` reads `codex debug models` for the model pickers (`AgentInstallInfo.catalog`, see models and capabilities above). SessionStart only arrives with the first prompt, so `readyOutput` (the composer's placeholder) marks the agent ready. `providers/codex/rollout.ts` parses rollouts: usage (`parseRollout`), live details (`rolloutDetails`, `rolloutPlanUsage`), the Sessions tab conversation (`CodexConversationParser`, including code-mode `exec` calls to `tools.apply_patch`), and `patchPaths()` for file locks.

## Hand Over to…

`sessions.handOver(project, from, to, { handover })` optionally types a handover request into the source (`sendPrompt()`: Ctrl+U, text, Enter) and waits until `sessions.latestHandover()` (set in `index.ts` from the shared notes) shows a newer handover for the project, failing if the agent finishes, asks or stops without one; starts the target if it isn't running and waits for **ready**; types the pick-up prompt; then writes `handedOverFrom` on the target's session record once its id is known. The renderer's `HandOverDialog` (`AgentDialogs.tsx`) and `POST /v1/projects/{name}/handover` call it.

## Launching a session

`sessions.start()` (Claude Code shown; Codex differs as above):

1. Resolves effective settings (`effective()`, run in the project's workspace): every Hive skill in the workspace, the workspace-enabled MCP servers minus the project's opt-outs, plus model, effort, permission mode and args. Bypass is downgraded unless the global opt-in is on.
2. Restores the transcript from `.hive/sessions` if resuming and Claude Code no longer has it.
3. `adapter.prepareLaunch()` — for Claude Code, rebuilds `Project/.hive/launch/` from scratch:
   - `plugin/` — a session-only Claude Code plugin containing copies of the Hive skills (`--plugin-dir`)
   - `mcp.json` — enabled servers plus the built-in `hive` server (`--mcp-config … --strict-mcp-config`)
   - `settings.json` — HTTP hooks pointing at Hive's hook server (`--settings`); `SessionStart`, which can't be an HTTP hook, is a `curl.exe` command posting to the same server
4. Spawns `claude` in a pty with `--session-id` (new) or `--resume` (existing), so Hive always knows the session ID and therefore the transcript path.
5. Records a **launch signature** (hash of the effective settings). `liveInfo()` compares it with the current settings to show "restart to apply".

## Status

Claude Code calls the hook server (URL `?run=<runId>`) for `SessionStart`, `UserPromptSubmit`, `PostToolUse`, `Notification`, `Stop`, `StopFailure` (a turn ended on an API error; an expired sign-in is `authentication_failed`), `PreCompact` and `SessionEnd`. The hook token is passed to the pty as `HIVE_HOOK_TOKEN` and referenced from `settings.json` through `allowedEnvVars`, so it is never written to disk. `handleHook()` maps the normalised events to `SessionStatus`, triggers the chime and desktop notifications, and marks events unseen when the window isn't in focus.

**Seen and the attention inbox.** Every move to finished or waiting sets `unseen` in main, and `emitState()` stamps `statusSince` whenever the status changes. Main doesn't know what is on screen: the renderer does (`agentsOnScreen()` in `store.ts`: the selected project's panes on its Session tab, the Assistant's open panel, only while the window is focused). It marks those agents seen on every store change (`markOnScreenSeen()` in `renderer/inbox.ts`, `session:markSeen` with their ids), and applies a finish that is already on screen as seen so it never flickers. `shared/inbox.ts` turns projects, live states and worktree branch statuses (`branchWatch.ts`, with `worktrees.branchStatus()`'s diff summary) into the inbox: the status bar's popover, the Projects badge and sidebar counts in the renderer, and the tray menu in main (which overlays `sessions.liveStates()` on each window's cached workspace info).

## Usage

Each adapter's `parseUsage()` reads its transcripts into `SessionUsage` (Codex: `codex/rollout.ts`). `providers/claude/usage.ts` parses Claude Code's JSONL transcripts (`~/.claude/projects/<encoded path>/<session>.jsonl`):

- usage is summed once per API request (Claude Code writes one entry per content block with repeated usage);
- context size is the last request's `input + cache_read + cache_creation`, or `postTokens` after a compaction;
- compactions come from `system/compact_boundary` entries;
- the cache TTL is detected from `ephemeral_1h_input_tokens`.

Results are cached by file mtime and size (parsers for at most 200 transcripts, results for `sessions.usageCacheSize`, least recently used first) and saved to `usage-cache.json` in the profile (`loadUsageCache()`/`flushUsageCache()`: the result before costs, `raw`, which `priced()` turns into costs with the current prices; a restart takes unchanged transcripts from it without reading them); reads of one transcript take turns and read 4 MB at a time. While a session runs, a 5-second poll checks the transcript's modified time and size (Codex's appends can leave the reported modified time unchanged on Windows), copies it to `.hive/sessions` at most once a minute during a turn, and emits `usage-changed`; for providers without a reported cost, the estimate (a full parse) is worked out at most every 30 seconds and at turn ends. `sessions.list()` reads `sessions.json` and `project.json` once for the whole list (`ListContext`); the Codex adapter reuses its rollout listing for 10 seconds and remembers missing rollouts for a minute. In the renderer, `useSessions()` (Overview, Sessions tab) reloads per `settings.sessions.overviewRefresh`: live at most every 15 seconds, every minute, or on Refresh. Period totals (`periodFrom`, `sumUsage`, `dailyTotals`, and `stackedDaily` for the chart by project) are in `shared/usageTotals.ts`, shared by the project Overview, the Assistant's summary and the **Workspace Overview** (`views/WorkspaceOverview.tsx`), which loads `workspace:usage`: `sessions.usageItems()` per project and for the Assistant, lighter than `list()` (Hive's records and kept usage only, no external sessions, no transcript or backup checks), into `workspaceUsage` in the store, with the same refresh rules while it is shown. A large transcript with no requests at all raises a one-time "may not understand this version" notice (`checkUnderstood`).


## Performance metrics

`main/metrics.ts` (contract and units in `shared/metrics.ts`; SPEC §9.1) keeps one `Store` per open workspace (a WeakMap on the `WorkspaceService`, made on first use and saved and forgotten when its `lifetime` aborts). Stores are also kept by file (`byFile`, canonical path): a workspace reopened while its last store is still saving gets that store under the new lifetime, so writes to one file stay in one order; a store is forgotten after its final save if nobody took it over. Every collection point takes a `MetricsHandle` (`metricsHandle(w)`: that store and that lifetime) before it awaits anything and records through it, so work that outlives its workspace is dropped instead of landing in the window's next one; `metricsReport` checks the lifetime after each await of its usage read and refuses a read the workspace switched under. `roll()` runs on load, on each new hour and before each query (retention however long Hive was idle; buckets more than a day ahead dropped; at most `METRICS_LIMITS.buckets`) and reports whether it changed anything, which is then saved. Projects and series live in prototype-free dictionaries (`dict()`), drops are counted by owner (`droppedBy`) so a project report has only its own, the write cap is in UTF-8 bytes, and `load()` reads through `readCappedSync` (at most the cap plus one byte). `load()` checks the file's size before reading it and rebuilds each bucket through `readBucket`/`readPart` (finite non-negative counters, histogram length, known labels, the bucket caps). A record is a few map updates into the current hour's `Bucket`: `projects[name]` and `workspace` parts (`api`, `mcp`, `guidance`, `catalog` series) and the shared `skills` series; `roll()` folds hours older than a week into days and drops days past 30; `save()` is debounced (30 s, unref'd), chained so saves never overlap, size-capped (oldest buckets first) and writes `.hive/metrics/metrics.json` plus its `.gitignore`. Labels come from fixed sets (`knownRoute()` registers each Agent API template in `route()`; tool names and provider ids by pattern; anything else is "(other)"); per-bucket caps on projects and series count what they drop. Recorders never throw. Where each measurement is taken:
- `servers.ts` `handleApi`: an `ApiRequest` per response (`apiRequests` WeakMap) filled in as it is handled (role and project from the caller, the handle from `requestWorkspace` before the body is read, route template, request bytes per chunk as `readBody` receives them, response bytes as `send` serializes them), recorded on the response's `close` with its outcome (`outcomeOf`: unfinished is cancelled). Unauthenticated requests, event streams (`broadcast` and the `/v1/events` handler) and requests in flight go to the process-wide `appMetrics`. `/v1/health` and `/v1/metrics/mcp` are skipped.
- `hive-mcp.ts`: each `tools/call` reply's final text (chars, UTF-8 bytes, monotonic time, outcome, mode) and the first `tools/list`, batched (at most 50 a post, every 2 s, at once when the CLI closes input and no call is running) to `POST /v1/metrics/mcp` with the session's own token; the route checks and bounds each entry (`recordMcp`, `recordCatalog`) and attributes it by the token.
- `sessions.ts` launch: `recordLaunch` with the session contract (`ctx.guidance`, counted once whichever way the provider gets it), the Assistant's instructions, the delivered skills measured on their copies (`deliveredSkillSizes`: each adapter's `skillCopyPath`, the copy's header through `headerOf` and its `treeSignature` byte total) and the skills asked for that weren't delivered.
- `revisions.ts` / `guidance.ts`: hits, misses, invalidations, too-big outcomes and what each hash read (`HashOptions.count`, scoped instead of the global `readStats`), header bytes (`headerOf`), and each `skillRevisions` scan's time and shared callers (`coalesced(scan, onShare)`).
- `metricsUsage.ts`: `metricsReport()` adds the providers' own reported usage (`sessions.usageItems`, sessions active in the range: tokens, requests, compactions, cost) to `queryMetrics()`, for `GET /v1/metrics` and IPC `metrics:query`; `metricsExport()` wraps a report for IPC `metrics:export` (schema, version, units, optional sanitizing).
- The Performance view and tab (`views/Performance.tsx`) share one `PerformancePage`: the scope is in every query (a project's tab asks for its project only), `useScopedLoad` keys results by workspace, scope and range, refreshes are coalesced, and filtering and totals are the pure `shared/metricsView.ts` (`select`, `totals`, `byRoute`, `byTool`). The page's filters go to main with the query (`queryFor()`); `queryMetrics` narrows each bucket's parts with `filtered()` before summing them and before `trendOf()` (so the parts, trend and an export agree), reports `filters.notFiltered`, and reads coverage from the store's `observed` stretches (`touch()` on each record and query and on an unref'd 5-minute tick over the stores some workspace holds (`holders`); `seal()` ends a stretch when recording is turned off (`config.onSettingsChanged`, or a touch that finds it off) or the last holder closes, and a loaded store starts sealed; `evicted()` moves `evictedThrough` and trims observation when `roll()`'s bucket cap or `write()`'s byte cap removes a bucket; saved with the buckets, expired by `roll()`, cleared by `reset()`). `providerUsage()` reads the hosts the scope and filters keep (projects as `agent`, the Assistant's home as `assistant`), counts running sessions from `sessions.projectStates()`, takes context as a snapshot, and counts hosts whose `usageItems()` failed (`providersUnreadable`). `launchParts()` in `guidance.ts` splits a launch's text into core, custom, role and persona for `recordLaunch`.

Compare (#117): `shared/benchmark.ts` reads artifacts as untrusted input (`parseArtifact`: scenario benchmarks, Performance exports reduced to `summaryOf()` totals, a workspace export's project part only when asked), and compares them (`compareArtifacts`: comparability with reasons, per-scenario `Stat`s and statuses, correctness before size). `main/benchmarks.ts` keeps them in `.hive/metrics/benchmarks` (`index.json` plus one file each) behind the `benchmarks:*` IPC. Each handler takes a `BenchContext` (the folder, the workspace's lifetime and path) synchronously before any await, and every step checks it (`live()`): work whose workspace closed or switched is refused. Changes are serialised per folder (a settled chain is forgotten). Every write goes through `commit()`: staged beside the file, the context checked, then renamed. Index entries carry `state` (`adding`, `removing`) and `txn` for changes in progress: `keep()` records the add and the evictions, writes the file, commits the add, then removes evicted files (`removeFile`, ENOENT counting as gone) and drops each entry only once its file is gone; `removeBenchmark()` does the same for one entry. `readIndex()` validates the whole index (damage goes to `recover()`, never acted on), then `reconcile()` rolls back unfinished adds, retries recorded removals, moves files the index doesn't account for to `quarantine/` (`quarantine()`: named `<time>-<seq>-<id>.json`, pruned by time to the newest 100) and drops entries whose file is gone. `recover()` sets the damaged index aside (bounded), adopts every valid file with its old pin and time, and quarantines invalid and overflow files so its result is stable. `writeIndex()` refuses an index the reader wouldn't accept (`acceptable()`: at most `MAX_ENTRIES` in all, 20 kept, ids unique), and `keep()` checks that bound before recording a change. Every rename (commit, quarantine, set-aside) goes through `guardedRename()`: fsutil's `renameRetrying()` with a guard run before each attempt (`live()`) and `benchIo.renameOnce` as the single rename, so tests drive the real retry loop. Notices from recovery and clean-up are returned once by `benchmarks:list`. Reads are capped (`readCapped`); writes and removals go through `benchIo` (tests inject failures and pauses there). A file waiting for the project-part answer is held by a token bound to its context and scope, never a renderer-supplied path. Every call carries the page's `CompareScope` (the whole workspace, its own work, a project) and reads only that scope's; `shared/benchmark.ts` `readKept`/`readEntry` re-read kept files through the same normalisers as imports. `views/PerformanceCompare.tsx` loads the list and each pair with `useScopedLoad` keyed by workspace, scope and pair. The scenario harness (`tests/scenarios/harness.cjs`) reads `/v1/metrics` before the launch and after the turn and writes `measuresOf()` the difference; `benchmark.cjs` writes the artifact, prunes results and rotates baselines; the fakes' scenario steps call the real hive MCP server through `tests/e2e/fake-bridge.cjs`.

Measured (`tests/metrics.test.ts`, `MEASURE=1`; e2e replysize): recording costs about 0.3 µs a request; an hour's bucket filled to its 2000-series cap with Hive's real tool names is about 430 KB on disk and as JSON in memory (so under extreme cardinality the 2 MB file keeps a few such hours; ordinary use is far smaller); 300 sequential API requests took 14.45 ms each recording and 14.73 ms not (noise); idle, an open workspace's store only notes every 5 minutes that it is still observed (no write of its own). Budgets: under 50 µs a record (tested), the file at most 2 MB, a bucket at most 2000 series and 100 projects.


## Status line and plan usage

Hive's generated `launch/settings.json` sets Claude Code's `statusLine` to a `curl.exe` command that posts the status JSON to `/hook?statusline` on the hook server, which replies 204 (an empty status line). `sessions.handleStatusLine` copies effort, model name and cost into the live state; `planUsage.ts` parses `rate_limits`, stores the report in `config.json`, emits `plan-usage`, and raises the 80%/95% warnings once per reset period.

## Transcript viewer

The Sessions tab reads the conversation itself through `transcripts.ts` (IPC `transcript:*`), with the parser of the session's provider (`adapter.conversationParser()`). `providers/claude/conversation.ts` has Claude Code's `ConversationParser`, which turns JSONL entries into display items: user messages, replies, thinking, tool calls (matched to their `tool_result` by id), slash and `!` commands with output, notices, and compactions (the `isCompactSummary` message becomes the divider's summary; the next request's usage gives its real size). Sidechain entries, meta messages and attachments are skipped.

Transcripts are append-only, so the parser is incremental: `feed()` takes the bytes after its offset and stops at the last newline, leaving a line Claude Code is still writing for next time. `transcripts.ts` keeps a parser per session (LRU of six), reads only the new bytes when the file grows, and starts again if the file is replaced (for example by Hive's backup). `transcript:read(project, id, { knownSize, from })` returns the items from `from` on (by default the latest `TRANSCRIPT_WINDOW`, 200) with the total, or null when the size hasn't changed; the viewer loads earlier windows as you scroll up (keeping its distance from the bottom), and polls every 2 seconds for a running session only with Follow on (`settings.sessions.followTranscripts`). Tool input and output are shortened to 4,000 characters for display; `transcript:tool` returns the full call. Images are not sent with the items: the parser records each image's line range, and `transcript:image` reads that line and returns a data URL. Search (`searchItems`) and Markdown export (`transcriptMarkdown`), in `providers/conversation.ts`, work on the full items in main for every provider.

The tab's list is a tree (`shared/sessionTree.ts`: provider → agent → session → sub-sessions, from `session:list`). Sub-sessions (Codex guardian reviews and other sessions a CLI starts for another) are found by each adapter's `listSessions()` from the transcript's first line, cached by mtime (`rolloutSubSession()`, `transcriptSubSession()`), as `SessionListItem.sub`. Why a session can't be resumed is `shared/sessionResume.ts`. Archive and delete, one at a time or a branch at once (`session:bulk`), reserve the session (no start, resume or transcript read meanwhile), go through `sessions.inUse()` (running anywhere, a read in progress or a view open in another window: `transcriptReads.ts`; the CLI's transcript held open by another program, checked read-only; or written in the last few seconds by a CLI Hive didn't see exit) and change each session all or nothing: an archive is built aside and its moves undone on any failure (`Moves`); a delete keeps a spare (hard link) of each copy it sends to the Recycle Bin and puts them back if a later step fails.

## Agents in a project

A project has up to four agents, all equal (`ProjectConfig.agents` as added; `projectAgents()` in `shared/defaults.ts`), and a new one has none. Ids are random (`a-<hex>`, `projectAgents.addAgent`) so session records of a removed agent never attach to a new one, and the provider is stored at once. `migrateProjectConfig()` clears 0.1's agents and layout (project.json version 2). Calls that name no agent use the project's only one (`sessions.soleAgent()`; the Agent API answers 400/409 otherwise), and the renderer's `focusedAgentId()` is null without agents: `actions.quickAddAgent()` adds one (the default provider, if on and installed; else the Add Agent dialog), which New Session and Resume use. Adding sets `sessionLayout` from the count (`layoutForAgents`). `SessionManager` keys live sessions by project + agent id; terminals are `session:<project>#<id>` (`agentPtyKey`). Hooks and the status line carry the launch's `runId` (and `session_id`), so they find their agent without any other routing; a prompt hook with another session id for the same run moves the agent to that conversation (`switchSession`). `resumeRecord()` offers an agent its own sessions, then sessions no current agent owns. `ProjectInfo.agents` carries each agent's definition and live state; `ProjectInfo.live` is the first running agent's session. The renderer keeps the focused agent and pane assignment per project in the store (`focusedAgent`, `paneAgents`, `paneAssignment`, `showAgent`) and derives the single project dot with `mostUrgent`.

- **Launch**: each Claude Code agent has its own launch folder (`launch-<id>/`) because `prepareLaunch` replaces the folder. The pty's cwd is the agent's worktree when it has one. A worktree's setup command runs first in the same pty key (`quietExit`, so the renderer doesn't see an exit), then Claude Code continues in that terminal with the setup output carried over (`continueBuffer`).
- **Transcripts**: Claude Code files transcripts by folder, so a worktree agent's live in another `~/.claude/projects` folder. Session records keep `agentId`, `cwd` and `branch` (and, for Codex, `transcriptPath`), and `sessions.providerTranscript()` looks in the record's folder, the project folder and every agent's worktree. Backups and images stay in the project's `.hive`.
- **File locks**: `sessions.preToolUse()` answers the `PreToolUse` hook (Claude Code: matcher `Edit|Write|MultiEdit|NotebookEdit`; Codex: `apply_patch`, every path in the patch) synchronously in the hook server. Locks are a map from absolute path to the holding session, released on `Stop`, `SessionEnd`, exit or after 15 minutes; held files are published as `LiveSessionState.lockedFiles`.
- **Worktrees**: `main/worktrees.ts` wraps git (`worktree add/list/remove`, branch status, `merge-tree` conflict check, squash or `--no-ff` merge with `reset --merge` on failure, copying ignored files by pattern). `main/projectAgents.ts` adds, updates, removes and merges agents. `main/branchWatch.ts` keeps each worktree agent's unmerged work (commits ahead, uncommitted files) up to date from session-status, window-focus and workspace events and sends changes as `branch-status` events; the renderer keeps them in `branchStatus` (by `projectKey`) for Merge… and the agent tab. `workspace.assertRoot()` accepts a project or a registered agent worktree, so the Files and Changes IPC can work in worktrees; `git:status`/`git:diff` take a base branch and compare with the merge base.
- **Merge slot** (#350): `main/mergeSlots.ts` is the logic, unit-tested with a fake clock: a slot per project path and branch (one object each, kept registered while anything uses it: unused ones are dropped only when a new one is made past a cap), its holder (an agent's launch, by `runId`, or the user's merge, `asUser`; each hold has an id, which the user's Release must name) and its line, synchronous between awaits so a check and its change can't be split. Claims wait in the call (`claim`, woken by any change to the slot, bounded under fetch's 300 s), keep their place between calls, and a turn given between calls lapses after 2 minutes. `sweep()` ends what has run out (a launch gone, a hold past its time unless its Progress run is still reporting), and `settled()` re-arms the slot's one timer, wakes the waiters, sets each agent's status note and tells the window. `main/mergeSlotHost.ts` wires it: `sessions.onLaunchEnded` releases holds, `progress.openRunOf` keeps them, `merge-slots-changed` updates the renderer (`components/MergeSlots.tsx`: Overview, Progress panel, Merge dialog), and a record per workspace in app data (`merge-slots/`) lets `recoverMergeSlots()` report a hold Hive closed under when the workspace opens. `projectAgents.merge()` runs the Merge dialog's merge through the gate the host sets at startup (`setUserMergeSlot`, `asUser`), so `projectAgents` doesn't depend on the slot service.
- **Moved workspaces** (#146): `main/workspaceMove.ts` records where the workspace and its projects were last opened (`lastPath`), checks on open (from `onOpened`, in the background) and sets `WorkspaceInfo.moved` for the banner (`components/MoveRepair.tsx`); `movePlan()` works out the worktrees, session folders, per-path data (the adapter's `copyPathData`, `copyMissing()` in `fsutil.ts`) and Open Recent to repair, and `repairMove()` does it (one at a time per window, refused while agents run). Path rewriting is in `shared/movePaths.ts`. Moves whose data copy failed are kept in project.json (`pendingCopies`) until it works. `main/agentWorktree.ts` makes a missing agent worktree again (on its branch, or new from its base), for Repair and for Start, never pruning another missing worktree's link.
- **Rendering**: `components/AgentPanes.tsx` has the agent strip, `TerminalLayer` (every agent terminal of every project stays mounted and is positioned into its pane) and the pane frames drawn over it. `TerminalView` holds a WebGL renderer only while visible, within a window-wide budget (`WEBGL_BUDGET`, 8): a terminal that becomes visible takes the context of the longest-hidden one if the budget is used up, and hidden ones release theirs after 30 seconds anyway. Chromium's own limit is about 16 contexts per window, beyond which it silently drops the oldest.

## Hive Assistant

The Assistant (`shared/assistant.ts`, `main/personas.ts`, `components/Assistant.tsx`, `components/Personas.tsx`) reuses the whole session machinery by being a **session host like a project**: its home, `<workspace>/.hive/assistant`, has a `.hive` folder like a project's, with a `project.json` holding one agent (`assistant`). Hive never lists it as a project (`listProjectPaths` skips dot-folders), and because it is inside the workspace folder, `workspaceFor()`, window routing (`session:<home>#assistant`), close/switch/quit and the workspace's refresh all find it without anything new.

- **Where it differs**: `workspace.assertSessionHost()` (session calls and `agents:update`) accepts the home besides projects, and `workspace.isAssistantHome()` marks the few differences. `WorkspaceService.projectConfig()` overlays **Settings → Assistant** on the home's config (`assistantProjectConfig()`: its provider as the "project" default, per-provider model/effort/mode/arguments as the "project's" settings, an unset mode → the descriptor's `assistantMode`, one agent always). So `agentLaunchSettings()`, the footer and the settings dialogs work unchanged, and the workspace's own choices (Assistant Settings) are that agent's overrides, plus `persona`. In `sessions.ts` the Assistant works in the workspace folder (`cwd`), gets the workspace's skills for the Assistant (`hiveSkills(false, 'assistant')`, by `metadata.audience`) and only the hive MCP server (`HIVE_PROJECT` empty), is named "Assistant · <persona> · <date>", and its launch carries `instructions` (`assistantInstructions()` in `personas.ts`: its role and `controlRules()` from `shared/hiveGuidance.ts`, then the persona) and `trustedHiveTools` (`assistantTools(control)` from `shared/assistantTools.ts`). Session records keep `cwd` whenever it isn't the host folder, and `liveInfo()` passes the workspace folder to `resumeRecord()`.
- **Adapters**: `LaunchContext.instructions` → Claude Code `--append-system-prompt-file <launch>/instructions.md`, Codex `developer_instructions` after Hive's guidance. `trustedHiveTools` → Claude Code `--allowedTools mcp__hive__…`. Claude Code's Plan mode refuses MCP tools, which is why the Assistant's Claude Code mode is Manual.
- **Workspace info**: `WorkspaceInfo.assistant` is the home's `ProjectInfo` (named "Assistant"). The renderer finds it with `findProject()` alongside projects (actions, Compact, the mode menu, events), `applyLiveState()` updates it, and `actions.reveal()` shows its panel instead of a project.
- **Personas** are Markdown files with a small header (`parsePersona()`); `resources/personas` ships four. `WorkspaceService.onOpened` copies them into a workspace without a `personas` folder; `personas:list/create/delete/restore` manage them, the watcher emits `personas-changed`, and they are edited with `DocEditor` (drafts protected).
- **Control** (`main/assistantControl.ts`): per workspace, the Assistant's API token (rotated by `sessions.onAssistantLaunch` before each launch, written to `assistant-api/<hash>.json` in the profile, which `hiveMcp()` passes as `HIVE_API_TOKEN_FILE` with `HIVE_ROLE=assistant` and `HIVE_ASSISTANT_CONTROL`), its list of actions, the per-turn count (reset by `sessions.onAssistantPrompt` on its prompt hook) and the questions waiting on the user (`ask()`/`answer()`, events `assistant-questions`). `servers.ts` tells callers apart (`callerStore`, an AsyncLocalStorage): the Assistant's calls are confined to its workspace and its changes go through `assistantChange()` (control level, the 30-change limit, recording). The API server always listens; with the Agent API off only an Assistant token gets in. `hive-mcp.ts` offers the Assistant's tools by `HIVE_ROLE`/`HIVE_ASSISTANT_CONTROL` (`shared/assistantTools.ts`, no imports, so it can be a chunk). A first task reaches the CLI as `LaunchContext.initialPrompt` (the adapters' last argument, `promptArg()`); `sessions.noteUserInput()` (from `pty:write`) and `userTypedAt()` keep the Assistant from typing over the user. An agent the Assistant adds emits `agent-added`, which the renderer turns into a page dot (`newAgents`) or the project's focus, never a view change.
- **Trust questions**: an adapter's `startupQuestion` (Claude Code and Codex: "trust this folder") seen in the output while starting makes the agent `waiting` (`askedAtStart`) until its ready output, start hook or first prompt.
- **Panel state**: `assistantOpen` is saved per workspace as the pane entry `assistant-open:<path>` (`ui:setPane`), its width as `assistant` and the overview's share as `assistantTop`.

## Task board

`main/tasks.ts` keeps the workspace's cards in `.hive/tasks/<number>.json` with `board.json` holding the next number (`nextNumber()` also goes past every card file there, readable or not, so a lost `board.json` never reuses one). Cards are read through `clean()`, so hand-edited files can't break the board. Every change takes a `TaskActor` (`user` from IPC, `assistant` or an agent's name from the Agent API) for the card's history, and each card file is changed under its own `withFileLock`. The rules are in the service, not the callers: anyone moves a card between columns, Done included (each move is in its history with the actor), but only the user creates a card in Done or puts Done in order, a project agent can't put one On Hold (`checkHold`), a failed verdict can't move a card on, archived cards change only for the user, and `TaskPermissionError` becomes `403` in `servers.ts`. Order within a column is a float (`orderIn()` puts a card halfway between its new neighbours). `main/taskStart.ts` starts a card, one start per card at a time: it takes the card first (`updateTask` with a `check` run under the card's lock: still startable, same project), then starts an existing idle or stopped agent (`sessions.sendPrompt` or `sessions.start`) or a new one (`addAgent`) with `taskPrompt()` from `shared/tasks.ts`; if that fails the card goes back and a new agent is removed. `deleteTask` takes the card's lock too, so a change waiting for it finds it gone.

Changes emit `tasks-changed` (routed by workspace path); the workspace watcher emits it too for files changed outside Hive. The renderer keeps the whole board in the store (`tasks`, `loadTasks()`, debounced on events) and derives every view from it: `components/Board.tsx` has the board (the six columns of `TASK_COLUMNS`, drag and drop, collapsed columns and folded cards kept per workspace in `ui.boardFold`: `saveFold()` sends a change, `ui:changeBoardFold` applies it in main with `applyBoardFold()` to the window's own workspace's entry, the archived list), the Board view and its sidebar panel, the project Tasks tab and the card and Start dialogs. Agents reach it through the hive MCP tools (`hive_list_tasks`, `hive_read_task`, `hive_create_task`, `hive_update_task`, `hive_reorder_tasks`; `hive_start_task` for the Assistant only). Each agent launch has its own Agent API token (`main/agentTokens.ts`: made by `sessions.start` before the launch, in the pty's `HIVE_API_TOKEN` and the hive tools' `HIVE_API_TOKEN_FILE`, ended on exit by `runId`); `servers.ts` turns it into an `agent` caller, and `taskActor()` gives the board a `TaskActor` with `scope`, its project. The scope is enforced in `tasks.ts` (`scopeOf`, `inScope`, `readTask`, `listTasks({ scope })`, `cardRefs` keeping refs outside the scope, `placement` and `reorderTasks` among the scope's cards); `refsOutside()` gives the API's `elsewhere`.

**Card watches** (#128): `shared/watch.ts` is the pure part, unit-tested: a card's `CardMark` (column, latest comment and verdict times, agent, archived), `changesBetween()` (what changed, as a condition counts it), `movedIntoSince()` (a move into a column from the card's history, for `moveInto`), the `since` token of bounded waits (`encodeSince`/`decodeSince`), and the lines Hive types (`wakeLine`, `limitLine`) and shows (`watchLabel`). `main/watches.ts` keeps each workspace's watches in `.hive/watches.json` (loaded on first need, then checked against the board at once): `registerWatch` / `cancelWatch`, `evaluate()` on every `tasks-changed` (a watch that matches gets `fired`, its line), `deliver()` (removes the watch, then types the line with `sessions.sendPrompt` and a guard: the agent idle, the user not typing; refused, the watch comes back to be tried again on its next idle `session-status` or the 5-second tick, which also fires wait limits). `SessionManager.watchFor` (set by `initWatches()`) gives an agent's watch to `emitState`, which shows `ready`/`finished` as `watching` while there is one. `POST /v1/tasks/wait` in `servers.ts` registers watches (`wake`) or waits in place on `tasks-changed` events (bounded), and `watchKeepsQuitWaiting()` tells *Quit when agents finish* whether a watching agent counts.

**Tool replies** are lean: every character a tool returns goes into the agent's context and is paid for on each later turn. The Agent API keeps its full replies by default and has opt-in short ones (`?view=short` on task and project lists, `?history=false` on a card, `?days=false` on usage, `reply: "short"` on card changes, comments, reorders and starts); `servers.ts` builds them (`taskChange()` reports what changed in the card's history words, which `updateTask()` hands back through `opts.said`, and where the card is now). `hive-mcp.ts` asks for those and turns them into text with `shared/toolReplies.ts` (a line per card or project, a confirmation per change, notes as their text); everything else goes out as compact JSON. `tests/e2e/replysize.cjs` measures every tool against a busy workspace and holds each reply to a size.

## Removing projects

`main/projectRemoval.ts` hides, removes or deletes a project (`project:removalInfo`, `project:remove`, `project:restore`, `project:forget`, `project:takeRemovedData`). Hidden and removed projects are listed by folder name in `workspace.json` (`hiddenProjects`); `WorkspaceService.listProjectPaths()` and `isProjectPath()` leave them out, so everything that lists or names projects (the renderer, the Agent API, the board) stops seeing them without changes of its own. **Remove** packs the project's handovers (found with `projectHandovers()`, as the MCP server finds them) and cards into `<project>/.hive/removed` with a `manifest.json`, archives the cards (`archivedFor: 'project-removed'`) and moves the handovers to the Recycle Bin; **Restore** or the banner (`ProjectInfo.removedData`, from the manifest) unpacks it: the archived originals come back in the workspace they left, copies with new numbers anywhere else (`importCards()` maps the references). **Delete** sends the folder to the Recycle Bin first (watchers paused with `files.suspendWatching()`, resumed if it fails), then worktrees, handovers and cards, reporting what couldn't follow as `warnings`. Every way runs under a per-project guard with the project's starts fenced (`sessions.fenceStarts()`, checked in `assertStartsAllowed`); agents are stopped and the worktrees (`branchStatus(..., { strict: true })`, which throws when git fails), handovers (`projectHandovers(..., { strict: true })`, by exact name in the header) and cards are read again after the stop. `checkedWorktrees()` only lets through folders `git worktree list` gives for the project that don't contain the project or workspace and aren't another project. The dialog is `components/ProjectRemoval.tsx`, with the Settings → Workspace list and the restore banner.

## Windows app identity

The installed app uses the app user model ID `com.hive.desktop` (the Start menu and desktop shortcuts carry it, and each window sets it with `setAppDetails`), which gives the taskbar button and notifications the Hive name and icon. Dev and test builds run as `electron.exe` and use `com.hive.desktop.dev`, registered under `HKCU\Software\Classes\AppUserModelId` as "Hive Dev". Sharing one ID made Windows show Electron's name and icon for the installed Hive.

## Packaging and updates

`electron-builder.yml` builds an NSIS installer. `@lydell/node-pty` ships prebuilt N-API binaries (no native rebuild), unpacked from the asar archive together with `out/main/hive-mcp.js`, which both CLIs run through Hive's executable with `ELECTRON_RUN_AS_NODE=1`. Its Agent API calls use Node's `http`/`https` (`mcp/agentApiCall.ts`), not `fetch`: undici's 300 s limit on a reply's headers cut longer waits short (#371), so each call has its own deadline instead, a wait's being its longest plus a minute.

`updater.ts` wraps electron-updater. It turns off electron-updater's own auto-download and starts downloads itself, so *Download automatically* and skipped versions are honoured; `autoInstallOnAppQuit` follows *Install updates*. State changes go to the renderer as `update-state` events (`UpdateState`); the status bar item, update dialog, About and Settings (`components/Updates.tsx`) all render from that one state. **Restart and Update** sets a flag and calls the normal `requestQuit()`; `quitNow()` ends with `installNow()` (`quitAndInstall(silent, runAfter)`) instead of `app.quit()`, so the quit dialog, *wait for agents* and transcript backups all still apply. With `HIVE_UPDATE_FEED` (unpackaged builds only) the updater uses a generic feed from a config file in the profile, a separate download cache (`hive-test-updater`, or `HIVE_UPDATE_CACHE`'s `hive-test-updater-<k>` for an e2e lane), and never installs. Releases are published by `scripts/release.mjs` — see `RELEASING.md`.

## Permission mode of a running session

`LiveSessionState.permissionMode` is what the session is really in (Claude Code described here; Codex's comes from `thread_settings_applied` in its rollout and switches through its `/permissions` menu, see Providers). It starts as the launch mode and is updated from two sources: `readFooterMode()` in `sessions.ts` reads Claude Code's footer with `footerMode()` (`shared/claude.ts`) from the session's rendered screen: a `TerminalScreen` (`terminalScreen.ts`, `@xterm/headless`, one screen with no scrollback, resized with the pty through `spawnPty`'s `onResize`, disposed on exit) takes in the output, since Claude Code may redraw only the characters that changed (it does with `NO_COLOR`), which a text tail of the output misses, and `handleHook()` reads `permission_mode` from every hook. `setPermissionMode()` writes Shift+Tab (`ESC [ Z`) and waits up to 1.5 s per press for the footer to change, stopping when the target shows, the mode stops changing or the cycle comes round again. `canSwitchLive()` says which targets need `restartInMode()` instead (stop, wait for exit, `start({ resumeId, permissionMode })`). The permission mode is left out of the launch signature, so a changed setting doesn't raise "restart to apply"; instead `liveInfo()` calls `noticeModeSetting()`, which compares the effective mode with the one the session was configured with and, once per change, batches a "Switch Now" toast (`session.applyPermissionModes` → `applyModeSettings()`).

## Keyboard shortcuts

`Command.keybinding` in `commands.ts` is the default. `commandKeybinding(id)` resolves the one in force with `resolveKeybinding()`: the selected project's `config.keybindings` (only for categories in `PROJECT_KEYBINDING_CATEGORIES`), then `settings.keybindings`, then the default; `null` means none. Everything that shows or matches shortcuts (palette, menus, tooltips, `matchKeybinding`, the terminal's `isAppShortcut`) goes through it. `eventToKey()` names keys by `KeyboardEvent.code`. The editor (`components/Keybindings.tsx`) records in a capturing keydown listener and sets `recordingKeys` so the global handler in `App.tsx` stands aside. Global overrides are written with `settings:setKeybinding` (the settings deep merge can't delete a key); project ones replace the project's whole `keybindings` object.
